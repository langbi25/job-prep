础题
结果一路被追问到:
传统RAG差在哪里?
DeepResearch还算不算RAG?

差点给我问懵。
面试官:先说说，什么是RAG?
答:
RAG全称是Generation，也就是检索增强生成。
Retrieval-Augmented
它的核心思路是:模型回答问题前，先从外部知识库里找相关材料，再把这些材料放进上下文，让模型基于材料生成答案。
一个最常见的流程是:
文档 ->切chunk ->embedding ->向量库>top-k检索->拼进prompt->LLM生成答案
这个流程适合FAQ、产品文档问答、知识库检索这
类场景。
成“能引用外部资料回答”
它的价值是把模型从“只靠参数记忆回答”，变
面试官:那传统RAG最大的问题是什么?
传统RAG的问题不是完全不能用，而是它经常把“文档工作”简化成“文本片段召回”
短问答里这没问题。
但一旦进入复杂文档场景，就会出现三个典型问题。
第一，结构容易丢。
一份合同里的某一条，不只是几句话。它属于哪个章节、引用了哪个定义、下面有没有例外、附件里有没有补充说明，都会影响含义。
如果直接切成差不多长度的chunk，模型可能看到了
文字，却看不到它在文档里的位置。
第二，关系容易丢。
正文可能引用表格，表格里有金额和日期;主合同可能被补充协议修改;扫描件里可能有签章页。
flatchunk很难保住这些关系。
第三，很难复核。
很多业务场景里，答案好看不够。系统必须能回到原文，说明这个结论来自哪份文件、哪一页、哪一节，最好还能继续展开上下文。
所以传统RAG的核心短板可以概括成一句:它能找回文本，但不一定能保住文档状态。
面试官:什么叫文档状态?
答:
文档状态指的不是单纯的文本内容，而是文档在系统
里的结构、位置、关系和证据路径。
比如分析一批合同，判断哪些条款可能因为交易触发
consent或notice。
普通RAG可能只返回几段相似文本。
但真正可用的系统，至少应该知道:
这段文字来自哪份合同
它属于哪个章节
附件里有没有相关表格
补充协议有没有改过这条
这个结论能不能回到原文复核
所以document state 更像这样:Document -> Section -> Chunk -> Asset-> Metadata -> Source Path -> Graph Link-> Retrieval Trace
Agent拿到的就不是一堆孤立纸条，而是一个可以继
续探索的文档空间。
面试官:DeepResearch为什么看起来
不像传统RAG?
答:
DeepResearch 更近 Agentic RAG。
传统RAG是先把固定知识库切好chunk，每次问题
来了就做top-k召回。
DeepResearch的流程更像研究员做任务:
提出问题 ->搜索网页 ->打开来源 ->筛选信息->继续追问 ->汇总证据 ->生成报告
它不是完全不需要检索。
区别在于，检索不再只是外部模块，而变成Agent
推理过程中的一个动作。如果Agent每一步拿到的都是几个孤立chunk，它就很难像人一样在文档里移动。它只能不断重新检索、重新拼上下文、重新猜关系。
所以Agentic RAG的关键是:
不只是让模型会调用搜索工具，而是给它一个可以导航、可以引用、可以更新的文档状态。
面试官:如果让你设计复杂文档RAG，你
会怎么做?
答:
不会直接从 chunk size 和 embedding model 开
始调。
复杂文档RAG最容易出问题的地方，往往在更前面:文档进入系统时，结构、来源、表格、图片、附件关系有没有被保留下来。
所以会先加一层document memory。
这层不负责直接生成最终答案，而是负责把文档整理成Agent 可以工作的状态:
文档要有层级，不只是平铺chunk
chunk要带路径、来源和上下文
表格、图片、签章页、附件不能和正文断开
检索结果要能回到原文和章节
次重新top-k
Agent要能沿着文档结构继续展开，而不是每
这个思路可以参考一个开源项目 ontos-
ai/knowhere.它不是只做PDFtotext，而是把复杂文档变成Agent 可以工 document memory。
比如它会生成doc_nav.json，保留文档层级导航;生成chunks.json，保留片段路径、上下文和来源;图片、表格这类资产也会被抽出来，并通过关系和正文连起来。
更关键的是，它的检索更偏 evidence-first:先发现、导航、渲染证据，再让上层Agent基于证据写
答案。
这个方向可以概括成:
从 flat chunk + vector search,走向document memory + evidence retrieval.
面试官:这个和GraphRAG有什么区
别?
GraphRAG更强调实体关系和图推理。比如公司、人物、事件、指标之间的关系。
但图的质量依赖前面的文档处理。
如果文档一进系统就被切坏了，章节路径没了，表格和正文断了，引用来源丢了，那后面建图也会建在坏材料上。
可以把它们放在不同层:
Document Memory:保留文档结构、资产、路径、证据Vector Search/BM25:做相似检索和词面匹配 GraphRAG:做实体关系和跨文档推理Agent:决定下一步怎么查、怎么用证据
这样看，GraphRAG不是替代文档状态层。
它更像是在文档状态之上，继续做实体关系和跨文档
推理。
面试官:最后总结一下，RAG后面会怎么
演进?
答:
传统RAG解决的是:把相关文本找回来。
Agentic RAG要解决的是:
让模型在材料空间里行动。
复杂文档场景下，真正重要的是把文档从flatchunks变成可导航、可引用、可复核的document memory.
只有这样，Agent才不是每次拿几段文本重新猜，而是能沿着文档结构继续查、继续看、继续验证。
