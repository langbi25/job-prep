# 长期记忆和短期记忆怎么区分与保存？结构化信息和文本信息如何区分？会不会重复？

**Q：** 长期记忆和短期记忆怎么区分与保存?结构化信息和文本信息之间如何区分?会不会重复?

## 要点

- 我先按生命周期和用途区分：短期记忆是当前会话的上下文窗口，保存最近对话、工具调用结果，随会话结束或压缩而丢弃；长期记忆是跨会话持久化的用户偏好、事实、任务结论，写入外部存储供后续检索。
- 保存上，短期记忆直接放在 prompt 的 messages 里，按 token 预算做滑动窗口或摘要压缩；长期记忆写入向量库/数据库，用（填入：如 Redis+Milvus / PG+pgvector）持久化，检索时按 query 召回 top-k 注入上下文。
- 写入时机我做了区分：短期记忆每轮追加；长期记忆不是每句都写，而是用规则或 LLM 抽取「值得记」的事实/偏好/结论，再落库，避免噪声污染。
- 结构化信息我存成带 schema 的记录，比如用户画像表（user_id、偏好、约束、更新时间），字段明确、可精确查询和更新；文本信息存原文+embedding，走语义检索。
- 区分方式是在写入时做分类：抽取阶段判断这条内容是「实体/属性/关系」还是「一段叙述」，前者进结构化表，后者进文本库，并保留 source 指向原始对话。
- 去重上，结构化记录用主键或唯一约束（user_id+属性名）做 upsert，新值覆盖旧值并保留版本；文本记忆用 embedding 相似度阈值（如 0.9 以上）判重，命中则合并或更新而不是新增。
- 我还加了记忆的时效与冲突处理：每条记忆带时间戳和置信度，检索时优先新且高置信的；冲突时以最新用户明确表述为准，旧记录标记失效而不是物理删除。
- 权衡上，长期记忆不是越多越好，要控制召回数量和 token 预算，并定期做记忆整理（合并、过期清理），否则检索噪声和上下文膨胀会拖垮效果。

## 易错

- 只答「短期放上下文、长期放向量库」太浅，会被追问写入时机和去重策略。
- 结构化与文本二分不是绝对的，同一事实可能两边都存，要说明以哪边为准。
- 去重阈值和 upsert 键要能说出具体做法，否则会被认为没真正落地。
- 长期记忆的过期与冲突处理常被忽略，是深挖点。
