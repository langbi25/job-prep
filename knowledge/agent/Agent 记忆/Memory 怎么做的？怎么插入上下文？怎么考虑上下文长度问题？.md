# Memory 怎么做的？怎么插入上下文？怎么考虑上下文长度问题？

**Q：** Memory怎么做的?怎么插入上下文?怎么考虑上下文长度问题?

## 要点

- 我把记忆分成三层：会话内的短期记忆（最近 N 轮对话原文）、会话间的长期记忆（用户偏好、事实、任务结论）、以及可检索的外部知识库；三层用不同的存储和召回方式。
- 短期记忆我直接放在 prompt 的 messages 里，按轮次滑动窗口保留最近（填入：如 10 轮），超出部分触发摘要或落库，保证单次请求 token 可控。
- 长期记忆我用（填入：如 Redis / PostgreSQL / 向量库）存储，每条记忆带 user_id、类型、时间戳、置信度；写入前先做抽取和去重，避免同一事实反复入库。
- 插入上下文时我按「系统提示 → 长期记忆摘要 → 检索到的相关记忆 → 最近对话 → 当前用户输入」的顺序拼装，越稳定、越全局的内容放越前面，利于 KV cache 命中。
- 记忆召回我用混合检索：向量相似度召回语义相关记忆，再用规则按时间衰减和重要性加权排序，取 top（填入：如 5 条）注入，避免无关记忆干扰。
- 上下文长度我按 token 预算分配：系统提示和工具定义占（填入：如 20%），记忆召回占 30%，对话历史占 40%，留 10% 给模型输出，超预算就按优先级裁剪。
- 超长时我做分层压缩：先对早期对话做滚动摘要，再把摘要作为一条 system 消息保留；工具调用结果只保留关键字段，原始大 JSON 落库不塞进上下文。
- 写入时机上，我在每轮对话结束后异步抽取记忆，不阻塞主链路；对用户显式说「记住」的内容提高优先级，直接写入长期记忆。
- 权衡上，记忆召回越多越全但 token 成本和噪声越大，我通过离线评估召回准确率和端到端任务成功率来调 top-k 和摘要粒度。
- 召回后重排：向量先取 top-20，用 cross-encoder 或 LLM 重排取 top-3，相似度低于（填入：0.7）的直接不注入——比单纯调大 top-k 更能压住噪声。

## 易错

- 只讲向量库检索，没讲写入、去重和更新，会被追问记忆冲突怎么处理。
- 上下文超长只说截断，会被追问截断丢信息怎么办、有没有摘要。
- 记忆注入顺序影响 KV cache 和模型注意力，容易被追问为什么这么排。
- 长期记忆的过期和删除策略要能说清，否则被问隐私和存储膨胀。
