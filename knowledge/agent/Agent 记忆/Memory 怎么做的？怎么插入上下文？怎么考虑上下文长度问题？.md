# Memory 怎么做的？怎么插入上下文？怎么考虑上下文长度问题？

**Q：** Memory怎么做的?怎么插入上下文?怎么考虑上下文长度问题?

## 要点

- 我把 Memory 分成三层：短期对话缓冲、会话级摘要、长期向量库；短期缓冲保留最近（填入：N 轮）原始消息，摘要层按 token 阈值触发压缩，长期库存事实与偏好。
- 写入时机上，我在每轮对话结束后异步抽取结构化记忆（用户偏好、任务状态、关键实体），用 LLM 生成 JSON 后落库，避免阻塞主链路响应。
- 长期记忆用向量库（填入：Milvus/pgvector）存 embedding，同时保留原文和元数据（时间、来源会话、置信度），检索时按相似度加时间衰减排序。
- 插入上下文时我按「系统提示 → 长期记忆摘要 → 会话摘要 → 最近 K 轮原文 → 当前用户输入」拼装，长期记忆只取 top（填入：3~5）条，每条截断到（填入：200）字。
- 上下文长度我用 token 预算管理：给模型窗口留（填入：20%）给输出，剩余按优先级分配，超限时先丢最旧的原文轮次，再压缩会话摘要。
- 压缩策略是滑动窗口加摘要：窗口外的对话用 LLM 滚动摘要成要点，保留工具调用结果的关键字段，避免丢失任务状态导致重复调用。
- 检索长期记忆时我做相关性过滤，相似度低于（填入：0.7）的不注入，防止无关记忆污染上下文；同时去重，同一事实只保留最新版本。
- 权衡上，记忆越多召回越全但 token 成本和噪声越大；我通过离线评估（填入：召回率/答案准确率）调 top-k 和摘要粒度，而不是一味加大窗口。

## 易错

- 只讲向量库检索，没讲写入时机和抽取流程，面试官会追问记忆怎么产生。
- 上下文拼装顺序说不清，被追问「长期记忆放前面还是后面、为什么」时卡壳。
- 压缩只提截断不提摘要，容易丢工具调用历史导致重复调用，这是高频追问点。
- 没有 token 预算的具体数字，显得没真正上线调过。
