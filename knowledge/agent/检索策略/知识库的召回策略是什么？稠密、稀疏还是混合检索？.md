# 知识库的召回策略是什么？稠密、稀疏还是混合检索？

**Q：** 知识库的召回策略是什么?检索方式是稠密检索、稀疏检索，还是混合检索?

## 要点

- 我先说结论：我们线上用的是混合检索，稠密+稀疏双路召回后融合，不是单一方案。稠密负责语义泛化，稀疏负责关键词精确匹配，两者互补。
- 稠密检索用（填入：bge-m3 / text-embedding-3 等）把 query 和 chunk 编码成向量，走向量库（填入：Milvus / Qdrant / pgvector）做 ANN 检索，召回 topK 一般取（填入：20~50）。
- 稀疏检索用 BM25 或 SPLADE，解决专有名词、型号、错误码这类稠密向量容易丢的精确匹配；我们索引建在（填入：Elasticsearch / 向量库的 sparse 字段）。
- 融合用 RRF（倒数排名融合）或加权分数归一化，RRF 对两路分数量纲不敏感、不用调权重，我们线上用 RRF，k 取 60。
- 召回后加 rerank 精排：用 cross-encoder（填入：bge-reranker）对融合后的 top（填入：50）重排，取 top（填入：5~10）进上下文，这是效果提升最大的一步。
- 工程上做了 query 改写/多路查询扩展，以及按元数据（租户、文档类型、时间）做前置过滤，避免跨租户召回和过期文档污染。
- 效果评估用召回率@K 和 MRR 离线评测集，线上看答案采纳率和引用命中率；我们对比过纯稠密，混合+rerank 把召回率@10 从（填入：X%）提到（填入：Y%）。
- 权衡：混合检索索引和查询成本更高、链路更长，如果语料小且 query 以自然语言为主，纯稠密就够；关键词型业务（如日志、工单）稀疏权重应调高。

## 易错

- 只答“用了向量检索”就停，没讲稀疏那一路和融合方式，会被追问为什么不用 BM25。
- 被追问 RRF 和加权融合的区别、k 值怎么定，答不出融合原理。
- 被追问召回率和最终答案质量的关系，没提 rerank 和评测指标。
- 数字要真实：topK、召回率提升幅度必须是自己跑过的，别编。
