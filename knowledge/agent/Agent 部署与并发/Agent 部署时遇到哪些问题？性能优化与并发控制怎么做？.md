# Agent 部署时遇到哪些问题？性能优化与并发控制怎么做？

**Q：** Agent部署时遇到哪些问题?性能优化、并发控制怎么做?

## 要点

- 我先说结论：Agent 部署的难点不在单次推理，而在长链路、多工具、有状态带来的延迟抖动和并发下的资源争抢，我主要从性能、并发、稳定性三块治理。
- 部署形态上我把 Agent 服务拆成无状态的编排层和有状态的外设层：编排层用（填入：FastAPI/K8s Deployment）水平扩容，会话与记忆放 Redis/向量库，避免实例绑定状态。
- 性能瓶颈我先定位再优化：用链路追踪把一次请求拆成 LLM 推理、工具调用、检索、序列化几段，实测占比大约是（填入：LLM 60%/工具 25%/检索 15%），优化优先打最大头。
- LLM 侧优化：流式输出降低首 token 延迟，对可并行的工具调用改成并行 function call，简单意图走小模型或规则路由，命中缓存的请求直接复用结果。
- 工具调用侧优化：给每个工具设超时和重试上限，慢工具异步化，把多次串行检索合并成一次批量查询，减少往返次数。
- 并发控制上我用信号量/令牌桶限制同时在飞的 LLM 请求数，按（填入：模型配额）设上限，超出排队或降级到小模型，防止打爆上游限流。
- 会话级并发我用会话 ID 加分布式锁保证同一会话串行，避免多轮上下文互相覆盖；不同会话之间完全并行，锁粒度只到会话。
- 稳定性上做超时、熔断、降级三件套：工具连续失败触发熔断，LLM 超时降级到兜底回复，并用幂等键防止重试导致工具重复执行。
- 容量与成本上我按 QPS 和平均 token 数估算并发实例数，用队列削峰，并监控 P99 延迟、错误率、token 消耗三个核心指标做扩缩容依据。

## 易错

- 只讲优化手段不讲怎么定位瓶颈，面试官会追问你的 profiling 方法和具体数据。
- 并发控制只提加锁，没区分会话级锁和全局限流，容易被追问锁粒度和死锁。
- 忽略工具调用的幂等和重试放大问题，重试风暴是线上常见事故。
- 数字全是估算没有真实监控支撑，会被质疑是否真上过线。
