# 压缩上下文时丢失工具调用历史，导致模型重复调用工具，怎么解决？

**Q：** 压缩过程中会丢失工具调用历史，导致模型重复调用工具，怎么解决?

## 要点

- 结论：压缩不能只保留自然语言摘要，必须把「工具调用记录」当作结构化状态单独持久化，压缩后以状态快照形式回填，而不是靠摘要复述。
- 机制：工具调用历史包含 tool_call_id、函数名、参数、返回结果、状态（成功/失败/进行中），模型靠这些字段判断「已做过什么」，摘要丢失后只能重试。
- 工程做法一：压缩时把工具调用抽成结构化列表（call_id、name、args_hash、status、result_digest），与摘要一起写入上下文，摘要只描述意图，状态由列表承载。
- 工程做法二：在 Agent 侧维护外部状态机/任务清单，每步工具调用后更新，压缩后从状态机重建「已完成步骤」提示，不依赖对话历史。
- 工程做法三：对幂等性差的工具加去重层，用 args_hash + 时间窗做调用缓存，重复调用直接返回缓存结果，作为兜底而非主方案。
- 工程做法四：压缩触发前先做「状态固化」，把当前任务进度、已调用工具、待办步骤写成一段结构化 checkpoint，再压缩历史对话。
- 权衡：结构化状态会占 token，需按重要性分级保留（进行中 > 失败待重试 > 已成功），已成功且结果可摘要的只留 digest。
- 边界：对长流程任务，压缩频率要调低或改用分层记忆（短期全量 + 长期摘要），避免每轮压缩都丢状态；对只读工具可放宽，对写操作必须严格。

## 易错

- 只做摘要压缩，不保留 tool_call_id 和参数，模型无法判断是否已调用。
- 把工具结果全文塞回上下文，压缩等于没压，token 反而更高。
- 忽略失败/进行中的调用，压缩后模型重复执行写操作造成副作用。
- 追问：压缩后如何验证没丢状态？需答出回放或断言检查。
