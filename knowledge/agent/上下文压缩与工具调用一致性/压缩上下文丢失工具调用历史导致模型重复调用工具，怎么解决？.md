# 压缩上下文丢失工具调用历史导致模型重复调用工具，怎么解决？

**Q：** 压缩过程中会丢失工具调用历史，导致模型重复调用工具，怎么解决?

## 要点

- 结论：压缩不能只保留自然语言摘要，必须把工具调用历史作为结构化状态单独持久化，压缩后按需回填，保证模型看到的调用链完整。
- 机制：工具调用是「请求-响应」成对事件，压缩时若只摘要文本，模型会丢失「已调用过什么、参数是什么、返回什么」的事实，只能重新发起调用。
- 工程做法：在消息序列中给每个 tool_call 和 tool_result 打上 call_id 与状态标记（pending/success/failed），压缩时按 call_id 聚合，保留最近 N 轮完整调用对。
- 压缩策略：对历史工具结果做「结果摘要 + 原始结果引用」双写，摘要进上下文，原始结果存外部存储（如 Redis/对象存储），模型需要时用 call_id 回查。
- 回填机制：压缩后生成一份「已执行工具清单」注入 system 或上下文头部，列出工具名、关键参数、结果状态，模型据此判断是否已调用过。
- 幂等兜底：工具层实现幂等键（如基于参数 hash 的 request_id），即使模型重复调用，服务端去重返回缓存结果，避免副作用。
- 触发时机：按 token 阈值（如上下文窗口 70%~80%）或轮次触发压缩，优先压缩工具结果正文，保留调用元数据，避免过早压缩导致信息缺失。
- 权衡：保留全部调用历史会占上下文，需在「信息完整」与「token 成本」间取舍；可对失败调用保留完整信息，成功调用只留摘要。

## 易错

- 只做文本摘要，不保留 call_id 和参数，模型无法判断是否已调用。
- 压缩后未回填已执行工具清单，模型仍会重复调用。
- 工具层无幂等，重复调用产生副作用（如重复下单）。
- 压缩阈值设置过低，频繁压缩导致调用链断裂。
