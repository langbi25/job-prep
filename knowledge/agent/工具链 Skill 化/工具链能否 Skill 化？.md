# 工具链能否 Skill 化？

**Q：** 工具链能否Skil化?

## 要点

- 结论：能，但不是把工具简单包装成函数，而是把「工具调用 + 参数校验 + 错误恢复 + 结果解析」沉淀为可复用的 Skill 单元。
- Skill 的定义：面向 Agent 的可复用能力包，包含工具描述（name/description/参数 schema）、调用示例、失败重试策略和输出格式约定。
- 机制上，Skill 化 = 工具注册表 + 统一调用协议（如 MCP/OpenAPI）+ 执行沙箱；Agent 通过描述检索 Skill，而非硬编码工具名。
- 工程做法：先盘点工具链，按「高频、稳定、幂等」三原则筛选可 Skill 化的工具，低频或强交互的工具暂不封装。
- 每个 Skill 必须带参数 JSON Schema 和 few-shot 调用示例，否则 LLM 选错工具或传错参数的概率显著上升。
- 错误处理要内建：超时重试、幂等键、降级返回，Skill 内部消化可恢复错误，只把不可恢复错误抛给 Agent 决策。
- 可观测性：记录每次 Skill 调用的入参、耗时、结果码，用于评估工具选择准确率和后续 prompt 优化。
- 权衡：Skill 化提升复用和可维护性，但增加抽象层和调试成本；工具链频繁变更时，维护 Skill 描述的成本可能超过收益。
- 边界：有状态、长事务、需要人工审批的工具不适合直接 Skill 化，应保留为人工节点或拆成「预检 + 执行」两步。

## 易错

- 只封装函数不写描述和示例，LLM 无法正确选择工具。
- 忽略幂等设计，重试导致重复下单/重复写入。
- 把所有工具都 Skill 化，抽象层过重、调试困难。
- 未考虑工具版本变更，Skill 描述与实现脱节。
