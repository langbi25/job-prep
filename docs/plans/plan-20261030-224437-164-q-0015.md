## 一、目标

在项目里落地「工具链Skill化」能力：盘点工具链并定义 Skill 候选清单

## 二、项目现状推断

- 服务层函数（kb_service / coverage_service 等）只能被 FastAPI 路由调用，没有统一的工具注册表与参数 schema，LLM 无法自主编排这些能力（依据：痛点1）
- 唯一的外部能力入口是 REST API，没有 MCP/Skill 层，接入 Claude Code、Cursor 等客户端要重复写胶水代码（依据：痛点2）
- 工具调用缺少统一的可观测性（入参/耗时/错误码），线上问题只能翻日志（依据：痛点3）
- 部分操作非幂等（如重复建卡、重复投喂），重试有副作用（依据：痛点4）
- 项目为单人维护、单机部署（2C2G Docker），不能引入重型基础设施，且需保持现有 REST API 兼容（依据：约束）

## 三、实施步骤

### 1. 盘点工具链并定义 Skill 候选清单
- 改什么：在项目根目录新增 docs/skill_inventory.md，列出所有服务层函数（kb_service、coverage_service、review_service 等），按「高频、稳定、幂等」三原则打分，筛选出 5~8 个首批 Skill 候选（如 create_card、search_knowledge、get_coverage、submit_review 等），并标注每个候选的输入输出、幂等性、错误码。
- 为什么：先明确边界，避免盲目封装；同时为后续注册表提供数据基础。
- 工作量：2｜风险：低。仅文档工作，不影响现有代码。

### 2. 实现轻量级 Skill 注册表与参数 Schema
- 改什么：新增 app/skills/registry.py，定义 Skill 元数据类（name、description、parameters JSON Schema、examples、retry_policy、idempotency_key），并提供注册与查询接口。首批将 3 个高频只读工具（search_knowledge、get_coverage、list_cards）包装为 Skill，每个 Skill 附带 2 个 few-shot 调用示例。
- 为什么：统一注册表是 Skill 化的核心，参数 Schema 和示例能显著降低 LLM 选错工具或传错参数的概率。
- 工作量：6｜风险：中。需设计合理的 Schema 结构，避免过度抽象；只读工具风险低。

### 3. 为写操作增加幂等键与错误恢复策略
- 改什么：在 app/skills/idempotency.py 中实现基于 SQLite 的幂等键存储（key = skill_name + 参数哈希），对 create_card、submit_review 等写操作 Skill 强制要求幂等键；在 Skill 执行器中内建超时重试（最多 2 次）和降级返回（如返回缓存结果或明确错误码）。
- 为什么：解决重试副作用问题，让 Skill 内部消化可恢复错误，只把不可恢复错误抛给 Agent。
- 工作量：8｜风险：中。需确保幂等键存储不成为性能瓶颈（SQLite 单机可接受）。

### 4. 实现统一调用协议与可观测性埋点
- 改什么：新增 app/skills/executor.py，提供统一的 execute(skill_name, params) 入口，记录每次调用的入参、耗时、结果码到 SQLite 表 skill_call_log；同时暴露一个轻量 MCP 兼容端点（/mcp/skills 列表 + /mcp/call），复用现有 FastAPI 应用，不引入新服务。
- 为什么：统一协议让 Claude Code、Cursor 等客户端可直接接入，可观测性为后续优化提供数据。
- 工作量：10｜风险：中。MCP 端点需保持简单，避免影响现有 REST API；日志表需定期清理。

### 5. 编写 Skill 调用测试与验收脚本
- 改什么：在 tests/test_skills.py 中为每个 Skill 编写单元测试（正常调用、参数错误、幂等重试、超时降级），并新增 scripts/skill_acceptance.py 脚本，模拟 Agent 连续调用 3 个 Skill 完成「搜索知识→创建卡片→查询覆盖率」的编排流程，输出调用日志和耗时。
- 为什么：提供可重复的验收信号，证明 Skill 层可用且稳定。
- 工作量：6｜风险：低。测试代码不影响生产逻辑。

### 6. 接入一个真实客户端并对比效果
- 改什么：使用 Claude Code 或 Cursor 通过 MCP 端点连接本地服务，让 Agent 自主完成一次「根据面经缺口创建卡片」的任务；记录改造前（手动调 REST API 写胶水代码）和改造后（Agent 自主编排）的耗时与代码行数。
- 为什么：验证 Skill 化对真实工作流的提升，为面试提供对比数据。
- 工作量：4｜风险：低。仅验证，不影响现有功能。


## 四、验收标准

- [ ] 运行 `pytest tests/test_skills.py -v` 全部通过，覆盖正常调用、参数校验失败、幂等重试、超时降级四类用例。
- [ ] 运行 `python scripts/skill_acceptance.py` 输出完整调用链日志，包含每个 Skill 的入参、耗时、结果码，且总耗时 < 2 秒。
- [ ] 通过 MCP 端点（/mcp/skills）能列出至少 5 个 Skill 及其 JSON Schema，Claude Code 能成功调用 search_knowledge 并返回结果。
- [ ] 重复调用 create_card 同一参数时，第二次返回相同 card_id 且不产生新记录（幂等键生效）。
- [ ] skill_call_log 表中可查询到每次调用的记录，字段包含 skill_name、params、duration_ms、status_code。

## 五、可量化指标

- 可被 LLM 自主调用的工具数量：0 → 5+
- 接入新客户端所需胶水代码行数：约 200 行 → 0 行（直接走 MCP）
- 工具调用平均耗时可观测比例：0% → 100%（通过 skill_call_log）
- 重复操作副作用发生率：偶发 → 0（幂等键覆盖写操作）

## 六、取舍与风险

- 没有直接上完整 MCP 框架，而是用 FastAPI 实现轻量 MCP 兼容端点：避免引入新服务，符合单机 2C2G 约束，但牺牲了部分协议完整性。
- 没有把所有服务函数都 Skill 化，只选高频、稳定、幂等的 5 个：降低维护成本，但低频工具仍需手动调用。
- 幂等键用 SQLite 存储而非 Redis：避免引入新组件，但并发写入时可能成为瓶颈（当前规模可接受）。
- 错误恢复策略内建在 Skill 层而非交给 Agent：减少 Agent 决策负担，但降低了灵活性，不可恢复错误仍需 Agent 处理。
