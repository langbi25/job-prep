# 改造方案：随着用户对话轮数增加，Context会出LLM 的Token窗口限制，你会如何设计上下文管理策略?

## 一、目标

在项目里落地「Context管理」能力：建立 Token 计量与预算分配器

## 二、项目现状推断

- 项目已有模拟面试多轮问答模块，但档案未说明当前上下文如何拼接与截断，推断为简单拼接全部历史（依据：核心模块含「模拟面试（多轮问答、逐题评分、整体报告）」，且痛点未提及上下文管理）。
- 已有 bge-small-zh 向量检索与 SQLite FTS5 双路检索能力，可复用为长期记忆召回通道（依据：技术栈「bge-small-zh 向量检索」、检索模块「FTS 关键词路 + 向量语义路 + RRF 融合」）。
- 知识库以 Markdown 为唯一事实源 + SQLite 索引，适合作为「可检索的长期记忆」而非把全文塞进 prompt（依据：知识库「Markdown 为唯一事实源（knowledge/*.md）+ SQLite 索引 + 向量」）。
- 当前规模小（5 场面经、55 题、7 张卡），单轮上下文压力尚不突出，但模拟面试多轮 + 检索内容叠加后 token 会快速膨胀（依据：现状规模「5 场面经、55 道题、7 张卡」）。
- 缺少统一的 token 计量与上下文组装层，服务层函数只被路由调用，难以在面试链路中插入预算控制（依据：痛点 1「服务层函数只能被 FastAPI 路由调用，没有统一的工具注册表与参数 schema」）。

## 三、实施步骤

### 1. 建立 Token 计量与预算分配器
- 改什么：新增 app/context/token_budget.py：封装 bge-small-zh 同源 tokenizer 或 tiktoken 的计数函数 count_tokens(text)；定义 Budget 类，按模型窗口（如 8k）预留输出 1k、安全余量 512，剩余按 system 15% / 检索 25% / 历史 60% 分配；在模拟面试路由 interview_router 的每轮请求前调用，输出预算日志。
- 为什么：没有计量就没有控制，先让 token 占用可见，才能谈截断与压缩。
- 工作量：4｜风险：tokenizer 与线上模型不完全一致导致估算偏差，需留安全余量。

### 2. 实现滑动窗口 + 关键轮次锚定
- 改什么：新增 app/context/window.py：固定保留 system prompt 与最近 N 轮（默认 6 轮）；对更早轮次按「是否含题目 ID / 评分结论 / 用户明确约束」打标，锚定保留，其余进入待压缩队列；在 interview_service 组装 messages 时替换原全量拼接。
- 为什么：近期交互连续性优先，同时不丢失关键事实，改动集中在组装层，风险可控。
- 工作量：6｜风险：锚定规则过粗可能保留冗余，需用日志观察命中率。

### 3. 异步摘要压缩旧轮次
- 改什么：新增 app/context/summarizer.py：对超出窗口的旧轮次调用 LLM 生成 Key Points（事实/进度/约束三段式），结果写入 SQLite 表 conversation_summary（session_id, summary, token_count, created_at）；面试链路读取最新摘要注入 system 区；摘要任务用 FastAPI BackgroundTasks 异步执行，不阻塞当轮响应。
- 为什么：把线性增长的历史压成有界摘要，是突破窗口限制的核心手段。
- 工作量：8｜风险：摘要丢失细节或引入幻觉，需保留原文可回溯并做摘要质量抽检。

### 4. 长期记忆按需检索注入
- 改什么：复用现有 FTS5 + bge-small-zh 向量双路检索，新增 app/context/memory_retriever.py：以当前用户问题为 query，检索知识卡片与历史摘要 Top-K（默认 3），经 RRF 融合后按预算裁剪注入；在 interview_service 中与滑动窗口结果合并。
- 为什么：项目已有检索基建，复用成本低，避免把全部知识库塞进 prompt。
- 工作量：6｜风险：检索噪声进入上下文干扰回答，需设置相关性阈值与条数上限。

### 5. 上下文组装可观测性与降级
- 改什么：在 app/context/assembler.py 统一出口打印结构化日志：session_id、各分区 token 数、压缩触发次数、检索命中数、总 token 与预算占比；超预算时按「检索 → 摘要 → 最旧轮次」顺序降级裁剪；错误码统一为 CTX_OVER_BUDGET / SUMMARY_FAILED。
- 为什么：线上问题可定位，且降级策略保证永不因超窗报错。
- 工作量：5｜风险：日志量增加，需控制采样与字段长度。

### 6. 补测试与对比实验
- 改什么：新增 tests/test_context_budget.py：构造 20 轮对话，断言总 token 不超预算、关键轮次必保留、摘要表有记录；跑一组改前/改后对比脚本，记录平均输入 token、超窗报错次数、单轮延迟。
- 为什么：用可复现数据支撑简历数字与面试讲述。
- 工作量：4｜风险：测试数据构造耗时，可先用脚本生成模拟对话。


## 四、验收标准

- [ ] 运行 pytest tests/test_context_budget.py 全绿，覆盖「20 轮对话不超预算」「关键轮次保留」「摘要落库」三个用例。
- [ ] 模拟面试连续 20 轮后，日志中 ctx_total_tokens 始终 ≤ 预算上限，且无 CTX_OVER_BUDGET 报错。
- [ ] 查询 conversation_summary 表，每超过窗口 6 轮即新增一条摘要记录，token_count 明显小于被压缩原文。
- [ ] 对比脚本输出改前/改后平均输入 token 与单轮 P95 延迟，改后 token 下降且延迟增幅 < 20%。
- [ ] 检索注入日志显示每轮 Top-K ≤ 3 且带相关性分数，可人工抽检 5 条确认无噪声。

## 五、可量化指标

- 20 轮对话平均输入 token：改前约 6000+（线性增长）→ 改后稳定在 3500 以内
- 超窗报错次数：改前偶发 → 改后 0
- 单轮 P95 延迟：改前 X ms → 改后增幅 < 20%（异步摘要不阻塞）
- 上下文有效信息密度（关键轮次保留率）：目标 100%，冗余轮次压缩率 ≥ 60%

## 六、取舍与风险

- 不用「只保留最近 N 轮」的纯滑动窗口：会丢失早期关键约束和题目上下文，改为窗口 + 关键轮次锚定。
- 不用同步摘要：会拉高当轮延迟，改用 BackgroundTasks 异步生成、下一轮生效，牺牲一点实时性换响应速度。
- 不把知识库全量注入：token 成本高且引入噪声，改为复用现有双路检索按需 Top-K 注入。
- 不引入外部向量数据库或消息队列：受单机 2C2G 约束，复用 SQLite + 现有向量能力，避免重型基础设施。

**遇到的问题**（都是真踩到的，不是假设）

1. **方案第二节的"项目现状推断"是错的**：`mock_service` 是**逐题独立评分**，根本不拼多轮历史，
   "推断为简单拼接全部历史"不成立。项目里真正的多轮在 `console_service`（`HISTORY_TURNS=6`
   硬截断 + 轮内工具结果无上限）。改造点据此改到对话台，否则会去优化一个不存在的瓶颈。
2. **锚定规则第一版失效**：约束轮的 token 也要占历史预算，第 17 轮起约束自己就被挤掉了
   （A/B 里"约束保留 16/20"）。根因是把"约束"和"id/评分"当成同级锚定。
   改成分级：P0 约束最近 4 条永不丢，更早的降级为 P1 参与竞争。
3. **摘要被包成 JSON**：`_chat_json` 非 tools 分支强制 `response_format=json_object`，
   DeepSeek 于是把整段摘要塞进 `{"type":"json_object","content":"…"}`。
   加 `json_mode=False` 分支解决——prompt 要的是段落，就不该开 JSON 模式。
4. **摘要写了但永远用不上**：`_history` 只取 `HISTORY_TURNS*2 = 12` 条，正好等于窗口大小，
   assembler 看不到任何窗口外消息，`summary_used` 恒为 false。
   改成取 40 条交给 assembler 去挑——**在取数层截断，等于替组装层做了决定**。
5. **摘要和原文重复计价**：摘要注入后，被它覆盖的消息仍留在历史里，同一段内容花两份钱
   （实测 history 538 + summary 198 tokens）。按 `covered_to_id` 剪掉后 history 降到 166。
6. **DeepSeek 的 json_object 要求 prompt 里出现 "json" 字样**，否则直接 400（校准脚本踩到）。
7. **环境里没有 pytest**，也不该为跑测试给它加依赖。测试写成 pytest 风格函数 +
   `__main__` 运行器，两种方式都能跑。

**与方案的偏差**

| 方案 | 实际 | 原因 |
|---|---|---|
| 按 8k 窗口、预留输出 1k | 窗口按真实 64K，另设 `soft_cap=12000` | 能塞 64K ≠ 该塞 64K；成本与延迟才是日常约束，软上限可调 |
| 接入 `interview_router` / `interview_service` | 接入 `console_service`，`mock_service` 未接 | 见问题 1：模拟面试没有多轮历史，接进去是空转 |
| 摘要检索"知识卡与历史摘要 Top-K" | 卡全局检索；摘要**只在会话内**按 2-gram 匹配 | 跨会话摘要噪音大（上个话题的结论会被当成本话题前提） |
| 测试覆盖 3 个用例 | 9 个 | 加的用例锁的都是实际踩到的坑（重复计价、末条工具结果、极端全锚定） |
| — | 额外做 `ctx_json` 落库 + 前端显示 | 账本只在日志里等于没有；界面上看得见才会有人关心 |

## 九、效果对比（改前 → 改后）

三个口径同批对话（20 轮，每轮助理回复约 1200 字，预算 12000 tokens）：

| 指标 | full（全量拼接） | naive6（改前：6 轮硬截断） | ctx（改后） |
|---|---|---|---|
| 第 20 轮输入 token | 17737 | 5318 | 7134 |
| 峰值 | 17737 | 5332 | 7152 |
| 均值 | 9322 | 4663 | 5551 |
| 超预算轮次 | **7/20** | 0/20 | 0/20 |
| 关键约束保留 | 20/20 | **6/20** | **20/20** |

单轮长物料（1 次投喂 → 8 次工具调用 × 2600 字）：

| 指标 | 改前 | 改后 |
|---|---|---|
| 单次请求输入 token | 17516 | 7772（−56%） |
| 是否超预算 | 是 | 否（裁 7 条工具结果） |

其他：

| 指标 | 数值 | 说明 |
|---|---|---|
| 测试 | 9/9 通过 | `python tests/test_context_budget.py` |
| token 估算误差 | −34.7% / +11.9% / −7.5%，均值 −10% | 对照 API `prompt_tokens`；千字级样本 ±12% 内 |
| 摘要压缩 | 595 字符 → 372 字符 | 短对话压缩比低（1.6×），长对话才有意义 |
| 真实链路 | 一轮 1115 / 12000 tokens | `summary 85 + retrieval 466 + history 130 + system 420` |

**结论要诚实**：改后比"6 轮硬截断"多用约 30% 的 token（5318 → 7134），
换来的是约束保留从 6/20 变成 20/20。**这不是"省 token"的故事，是"同样的钱买更多有效信息"的故事**——
真要省 token，把 `soft_cap` 调到 6000 就行，代价是更早触发降级。

## 十、总结

一句话：**上下文管理的目标不是"塞得下"，是"在预算内不丢关键信息，且丢的时候说得清"**。

三件真正起作用的事：分级锚定（约束 > 引用 > 普通轮）、窗口外摘要（有界但不失忆）、
按需检索（不把知识库倒进 prompt）。三件都是"少给一点、给对一点"，没有一件是"压缩算法"。

最值得记住的教训是问题 4：**在取数层截断，等于替组装层做决定**。
`_history` 只取 12 条时，摘要逻辑写得再好也永远不会被触发——功能"实现"了，
但没人验证它在真实数据上是否真的生效。所以后来给每一轮都加了账本（`ctx_traces` + 前端显示），
让"这轮到底喂了什么"变成可查的事实，而不是靠读代码推断。
