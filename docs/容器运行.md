# 容器运行

本机现状：Docker Desktop 装在 `E:\Docker`（**不在默认路径，`docker` 命令不在 PATH**），
WSL2 后端，分配 8GB 内存。引擎版本 29.9.3。

## 1. 为什么命令要写全路径

`docker` 不在 PATH，直接敲会报"无法识别"。两种办法，选一种：

```powershell
# 办法一：临时加进当前会话
$env:PATH = "E:\Docker\resources\bin;" + $env:PATH

# 办法二：每次写全路径
& 'E:\Docker\resources\bin\docker.exe' compose ps
```

**必须加 PATH 才能构建。** 构建时 Docker 会去调 `docker-credential-desktop.exe` 拉取基础镜像的
凭据，那个程序也在 `E:\Docker\resources\bin`；不加 PATH 会直接报：

```
error getting credentials - err: exec: "docker-credential-desktop": executable file not found in %PATH%
```

启动后两条入口任选：

## 3. 数据在哪

| 内容 | 位置 | 说明 |
| --- | --- | --- |
| 数据库 `kb.sqlite` | named volume `job-prep_jobprep_data` | 挂到容器 `/app/data` |
| 向量模型缓存 | named volume `job-prep_model_cache` | 挂到 `/root/.cache/huggingface/hub` |
| 知识库、面经、收件箱、报告、评测集 | 项目目录下对应文件夹 | bind mount，Windows 侧可直接看 |

**数据库为什么不用 `./data` 绑定挂载**：WSL2 访问 `/mnt/e` 走 9p 文件系统，SQLite 的 WAL 在这种
文件系统上会随机报 `database is locked`，写入吞吐也掉一个数量级。放 named volume（ext4）才稳。

代价是不能直接拷目录。**现在已自动化**（2026-11-13 起），compose 里的 `backup` sidecar
跑**三层快照**（2026-11-18 升级为 PITR-lite）：

| 层 | 频率 | 保留 | 覆盖窗口 |
| --- | --- | --- | --- |
| micro | 每 5 分钟（`BACKUP_MICRO_SEC`，0 关） | 12 份 | 近 1 小时 |
| hourly | 每小时整点（`BACKUP_HOURLY`） | 24 份 | 近 1 天 |
| daily | 每天 02:00（`BACKUP_AT_HOUR`），启动即跑一次 | 7 份 | 近一周 |

| 项 | 值 |
| --- | --- |
| 实现 | `scripts/backup_db.py`（SQLite backup API，不锁库不停服，`--tier` 分层）+ `backup_loop.py` |
| 产物 | `backups/kb-{tier}-{时间戳}.sqlite3.gz`，daily 约 4MB / 1281 spans |
| 轮转 | 按层隔离（daily 的清理绝不碰 micro/hourly），先备份成功再删旧份 |
| RPO | ≤5 分钟（micro 在时）；之前是 24h |

为什么三层：库 ~10MB 时一次快照（backup API + integrity_check）<2s，5 分钟一份跑得起。
SQLite 没有原生 WAL 归档，秒级真 PITR 需要 Litestream（Go 依赖）——决策记录见
规划-架构演进.md D7；当前用"频率换粒度"，恢复点 = 目标时刻之前最近的快照。

为什么用 sidecar 而不是 Windows 计划任务：计划任务只在登录会话里可靠，本机 `schtasks` 还被安全策略
禁用；sidecar 跟 compose 一起起停、`restart: unless-stopped` 天然扛重启，服务没跑时也没有新数据可丢。

```powershell
docker logs job-prep-backup-1 --tail 5    # rc=0 + 三层各自的 spans/blobs 数量
Get-ChildItem backups\*.gz                # 现有快照
scripts\backup.bat                        # 手动补一份（容器没跑会退回本机 venv）
```

**为什么不 `cp kb.sqlite`**：WAL 模式下最新写入在 `-wal` 里，单拷主库会"备份成功但少了最后几条"；
而且管道式拷贝可能拷到半写状态。backup API 做的是事务级一致性快照，跑完还会 `PRAGMA integrity_check`。

**按时间点恢复（PITR-lite，2026-11-18 实测）**：

```bash
python scripts/restore_pitr.py --list                          # 列出所有恢复点
python scripts/restore_pitr.py --at "2026-11-18T00:53:30"      # 演练恢复到临时目录
python scripts/restore_pitr.py --at "..." --out restored.sqlite3   # 落到指定文件
```

脚本选"目标时刻之前最近的快照"（绝不选未来的），解压 + integrity_check + 行数对账，
报告丢失窗口。**不指定 `--out` 时只写临时目录，绝不碰在线库**；覆盖在线库前先停服务、
先 `backup_db.py --tier daily` 备份现状。

实弹演练（2026-11-18）：00:53:23 快照 A → 插入标记卡 → 00:53:45 快照 B；
`--at 00:53:30` 恢复结果无标记卡、`--at 00:53:50` 有标记卡——按时间点选层正确，双向 PASS。

**恢复演练（restore_drill，证明"备份能恢复"）**：

```powershell
python scripts\restore_drill.py          # 最新备份：解压+完整性+行数对账+抽样读
```

验证要点：`integrity_check` 返回 `ok`，且 spans 数量与备份时一致（空库也能"恢复成功"，不看数量等于没验）。

**坑**：backup 服务挂 `jobprep_data` 时不能加 `:ro`。WAL 模式下即使只读，SQLite 也要建 `-shm`
共享内存文件，只读挂载直接报 `unable to open database file`。脚本内部用 `mode=ro` 打开，写权限只服务
于 `-shm` 映射。

## 4. 时区

容器默认 UTC。`docker-compose.yml` 里已经加了 `TZ: Asia/Shanghai`，**不要删**。

不设的后果不是"时间显示差 8 小时"这么轻：span 的 `start_ts` 会写成 UTC，混进历史数据
（本地时区写入）后，trace 列表按时间排序全乱，`按天统计` 会把晚上 8 点之后的数据算到前一天。
这问题排查起来非常费劲——数据都在，只是顺序和日期错了。

验证方式：

```powershell
docker exec job-prep-api-1 python -c "import datetime;print(datetime.datetime.now())"
```

输出应该和你手机上的时间一致。

## 5. 已知的几个坑

**volume 警告**：`up` 时会打印

```
volume "job-prep_jobprep_data" already exists but was not created by Docker Compose
```

无害。这个 volume 是首次部署时手工创建并导入了现有数据的（`docker volume create` + 拷贝
`kb.sqlite`），compose 只是不认识它的来源。要消除它，可以在 compose 里声明 `external: true`，
但那样换机器首次部署会直接失败，所以保留警告更划算。

**端口冲突**：容器占 8765。如果之前用 `start.bat` 在本地跑过，要先停掉本地的 uvicorn，
否则容器起不来（`port is already allocated`）。

**`ui` 服务已删除**：原来 compose 里还有个跑 Streamlit（8501）的 `ui` 服务，那是前端改 Vue
之前的旧界面，FastAPI 早就直接托管 `frontend/dist` 了。留着它只是白占一个容器和端口。

**镜像里没有 node/npm**：前端产物 `frontend/dist` 必须在构建镜像**之前**就在本地构建好
（`cd frontend && npm run build`）。`.dockerignore` 特意没有排除 `frontend/dist`，但排除了
`node_modules` —— 后者 15 万个文件，进了构建上下文会让 `COPY` 卡十几分钟甚至报路径过长。

**WSL2 虚拟机时钟漂移（2026-11-17 实测）**：宿主休眠唤醒后，WSL VM 的时钟可能慢了约 3 小时，
期间容器里写的时间戳（span、job_runs）全是漂移时刻的值；Docker Desktop 同步后自愈（实测同一次
会话内，几分钟后的写入就恢复正常了）。自愈前的历史数据是"时钟噪音"，看时间线时留意。
排查口诀：`docker exec job-prep-worker-1 date` 对比宿主 `date`，不一致就重启容器
（`docker compose restart`）让进程重新拿时区与时间。

## 6. 和本地直接跑的关系

两种方式不冲突，但**共用同一个 8765 端口，只能开一个**。

| | 容器 | 本地 `start.bat` |
| --- | --- | --- |
| 依赖隔离 | 完全隔离 | 用项目 `.venv` |
| 改代码生效 | 要 `--build` 重建 | 重启 uvicorn 即可 |
| 数据库位置 | named volume | `./data/kb.sqlite` |
| 适合 | 长期跑、给别人复现 | 开发调试 |

改代码时用本地跑更顺手；只想让它一直在那儿跑着，用容器。

**注意两边数据是分开的。** 容器里产生的对话/span 不会出现在本地 `./data/kb.sqlite`，反之亦然。
切换前如果要保留数据，先按第 3 节备份再导入。

## 7. Langfuse（自托管观测后端）

业务容器通过 OTLP 把 span 双写到 Langfuse；**本地 `kb.sqlite` 仍是唯一事实源**，
Langfuse 只是分析层副本，它挂了业务与本地面板完全无感。

```powershell
$env:PATH = "E:\Docker\resources\bin;" + $env:PATH

# 首次：建共享网络（api 容器靠它用服务名访问 langfuse-web）
docker network create obs

# 启动 / 停止（--env-file 必须带，密钥在 .env.langfuse 里）
docker compose -f deploy/langfuse/docker-compose.yml --env-file deploy/langfuse/.env.langfuse up -d
docker compose -f deploy/langfuse/docker-compose.yml --env-file deploy/langfuse/.env.langfuse ps
docker compose -f deploy/langfuse/docker-compose.yml --env-file deploy/langfuse/.env.langfuse logs -f langfuse-web
docker compose -f deploy/langfuse/docker-compose.yml --env-file deploy/langfuse/.env.langfuse down   # 卷保留
```

起来后浏览器打开 <http://127.0.0.1:3000>，登录 `admin@local.dev / Jobprep-Lf-2026!`
（首启自动创建，见 `.env.langfuse`）。业务侧配置在根目录 `.env` 的
`TRACING_ENDPOINT / TRACING_HEADERS / OBS_BACKEND / LANGFUSE_*` 各变量。

### 对账与验收

BatchSpanProcessor 导出失败是**静默丢弃**（这是刻意的：观测挂了不能影响业务），
所以别拿 Langfuse 当完整事实源，要定期和本地对账：

```powershell
# 本地 span 数
docker exec job-prep-api-1 python -c "import sqlite3;print(sqlite3.connect('/app/data/kb.sqlite').execute('SELECT count(*) FROM spans').fetchone())"
# Langfuse 侧：GET /api/observability/backend 看 reachable；面板里 trace 数对照
```

验收清单：跑一轮真实对话后 Langfuse 出现新 trace 且树结构与 Traces.vue 一致；
停掉 langfuse-web 再对话，业务不受影响、本地 span 照常落库。

### 镜像拉取的坑（2026-11-13 实测）

- `docker.io` 的 minio/bitnami 被 registry 返回 `denied`（加速站限制），换 `cgr.dev/chainguard/minio` 直连可用；
- `docker.langfuse.com` 可拉但网络不稳，中途 EOF 时**重跑同一条命令即可续传**；
- Docker daemon 走 `127.0.0.1:7890` 系统代理，代理软件没开时 cgr.dev 会报
  `connectex: No connection could be made`——先把代理开着再 pull。

### 首次部署踩过的三个坑（改配置后要 `--force-recreate langfuse-web`）

1. **v4.79 的初始化要求 `LANGFUSE_INIT_ORG_ID` 和 `LANGFUSE_INIT_PROJECT_ID` 必须显式设置**，
   只给 NAME 的话整组 INIT 变量被静默忽略（web 日志有 warn，业务无报错，表现是注册页而不是自动建号）。
   且 compose 的 `environment` 是白名单——`.env.langfuse` 里加了变量还不够，
   必须在 compose 里也列出（本文件已列全，别删）。
2. **web 必须设 `HOSTNAME: 0.0.0.0`**。Next.js standalone 拿 Docker 注入的 HOSTNAME（容器主机名）
   当绑定地址，只绑容器 eth0 IP；跨网络（obs）访问它的另一块网卡 IP 会 Connection refused。
   症状：容器内 `wget 127.0.0.1:3000` 被拒、宿主 curl 得到空响应（exit 52）。
3. **改 `--env-file` 内容不会触发容器重建**（compose 不比对 env-file 内容）。
   改完密钥/初始化配置后要 `up -d --force-recreate langfuse-web`。

### 验收结果（2026-11-13）

一轮真实编排对话后：Langfuse 收到 41 条 observations（AGENT/CHAIN/TOOL/RETRIEVER/GENERATION
类型齐全）；`v2/observations` 接口用固定 key 鉴权 200；停掉 langfuse-web 再跑一轮对话，
业务 200 正常回答、本地 spans 照常 +9，重启 web 后自动恢复。

## 8. API 鉴权与审计（2026-11-13 起）

`.env` 里的 `APP_TOKEN` 开启后，**所有 `/api/*` 都要求令牌**；`/health`、前端静态页、
`/docs` 放行（healthcheck 不能带 token，页面本身没有数据）。

- 浏览器：首次打开页面会弹框要求输入令牌，存 localStorage 后自动带上，只需输入一次；
- curl / 脚本：`-H "X-API-Token: <token>"` 或 `-H "Authorization: Bearer <token>"`；
- `APP_TOKEN` 留空 = 完全关闭鉴权（本地脚本/测试零开销）；
- MCP 不受影响：stdio 靠进程边界，HTTP 侧用它自己的 `MCP_TOKEN`。

审计（`audit_log` 表）只记两类请求：**写操作**（POST/PUT/DELETE/PATCH，含被参数
校验拒绝的）和**被拒的 401**。GET 不记；body 一律不落库——审计表不存简历内容。
查询接口：`GET /api/obs/audit?days=7`（返回 total、denied_401 和明细）。

```powershell
$token = "<你的 APP_TOKEN>"
# 看最近被拒的请求
curl.exe -s --noproxy "*" -H "X-API-Token: $token" "http://127.0.0.1:8765/api/obs/audit?days=1"
```

## 9. 观测噪音：FastAPI 自带埋点（2026-11-13 定位并关闭）

**现象**：Langfuse 里 12 小时积了 8535 条 span，其中 8504 条（99.6%）是
`fastapi.endpoint` / `fastapi.dependencies` / `fastapi.serialization` / `GET /health`，
真实业务 span 只有 23 条。根源是 FastAPI 0.162+ 内置 ASGI telemetry：**激活条件就是
「全局 TracerProvider 已被配置」**，而 `tracing.configure()` 之前调了 `trace.set_tracer_provider()`，
于是 Docker healthcheck（每 15s 一次）每个请求都生成 4 条 span。

**修法**：`configure()` 不再注册全局 provider。我们所有 span 都由 `_tracer` 直接从自有
provider 取，本来就不依赖全局；副作用是"只有显式埋的点才出去，第三方库自动埋点一律不出去"。
回归测试 `test_global_provider_stays_unconfigured` 锁住这条约束（断言全局 tracer 拿到的
是 `NonRecordingSpan`）。

**顺带纠正一个误判**：此前以为"每个 span 被重复导出 15 倍"。实际是 v2 observations 接口
用游标分页、我用了 `page=` 参数，15 页返回同一批数据；外加 ClickHouse `events_full` 是
ReplacingMergeTree，`count()` 会把未合并的副本算进去（raw 232 / uniqExact 23）。
**对账要用 `uniqExact(span_id)` 和本地 `count(*)` 比，不要用 raw `count()`。**

```bash
# 正确对账姿势
docker exec langfuse-clickhouse-1 clickhouse-client --query \
  "SELECT uniqExact(span_id) AS spans, uniqExact(trace_id) AS traces FROM default.events_full"
docker exec job-prep-api-1 python -c "import sqlite3;print(sqlite3.connect('/app/data/kb.sqlite').execute('SELECT count(*),count(DISTINCT trace_id) FROM spans').fetchone())"
```

清理历史噪音（Langfuse 副本可随时重建，本地库才是事实源）：

```bash
docker exec langfuse-clickhouse-1 clickhouse-client --query "TRUNCATE TABLE default.events_full"
docker exec langfuse-clickhouse-1 clickhouse-client --query "TRUNCATE TABLE default.events_core"
```

## 补充：Docker / Docker Desktop / WSL 三者关系与本次踩的坑（2026-11-17）

**关系一句话**：Docker Desktop（装在 `E:\Docker`）是管理器，它把 Linux 引擎跑在一个叫
`docker-desktop` 的专用 WSL2 发行版里；本机的 `Ubuntu-20.04` 只是**另一个普通 WSL 发行版，
里面没有任何 docker 二进制**（`which docker` 找不到是正常的）。docker CLI 只在 Windows 侧
`E:\Docker\resources\bin\docker.exe`。所以"docker 在 wsl 里"的直觉是错的——**wsl 是后端，
CLI 在 Windows**，不用 wsl.exe 也能操作 docker。

本次踩的坑，全记下：

1. **Git Bash 里加 PATH 用 POSIX 形式**：`export PATH="/e/Docker/resources/bin:$PATH"`。
2. **`docker compose up -d --build` 不一定会重建所有容器**：mcp 与 api 共用同一镜像，但本次
   api 重建了、mcp 没动（compose 只重建它认为配置变化的）。共用镜像的服务要
   `docker compose up -d --force-recreate mcp` 逐个确认，否则跑的还是旧代码。
3. **容器端口是 8765 不是 8000**：api 监听 8765（宿主映射同名），容器内探活
   `http://127.0.0.1:8765/health`。
4. **wsl.exe 的 stderr 是 UTF-16 编码**（如"localhost 代理"警告），管道进 Git Bash 会变成
   乱码/binary；且 NAT 模式下 WSL 不支持 localhost 代理（提示无害）。要拿 WSL 输出，
   落文件 + `tr -d '\0'` 转码。
5. **限流调参影响压测**：压本机服务要同时调高 `RATE_LIMIT_RPS` **和** `RATE_LIMIT_IP_RPS`，
   压测端全是同一 IP，IP 桶（默认 10/s）会先拦掉九成请求——测的是限流不是容量。

**一个未解之谜记录在案**：2026-11-17 凌晨容器重建后 5 分钟内，宿主串行突发出现过
429 但应用计数器为 0（应用日志证实 429 未经过应用进程）——疑似 Docker Desktop 端口
转发在重建窗口期把部分连接路由到了旧后端残留。之后并发突发复测，响应体 / 计数器 /
日志三方完全一致（172.18.0.1 被限 26 次、127.0.0.1 被限 25 次，与突发规模吻合）。
若再现，先查 `docker logs job-prep-api-1 | grep "rate limited"`——应用内计数与日志必须
同步增长，不同步就是请求根本没进应用。

## 11. 阶段 A：worker 与 web 容器（2026-11-17）

架构演进路线的第一步：**进程职责分离**。之前三种后台形态三种写法（告警线程在 api、
调度线程在 api、备份 sidecar 独立容器），现在统一成"一个进程一种职责"——
调度在阶段 A 就搬走了，告警线程到阶段 C 续（第 14 节）才真正搬进 worker 的 job：

| 容器 | 职责 | 变化 |
| --- | --- | --- |
| api | 纯无状态请求面（HTTP） | `JOBS_ENABLED=0`，调度循环不再在本进程跑 |
| worker | 定时任务调度（`python -m app.worker`） | **新增**，接走 job runner |
| backup | 每日备份 sidecar | 不变 |
| web | nginx：静态资源 + `/api` 反代 | **新增**，补齐交付形态 |
| litellm / mcp | 网关 / 外部接入 | 不变 |

### 为什么 worker 要独立成容器

- api 变纯请求面是未来一切扩展的前提（多副本、蓝绿都从"api 无状态"开始）；
- 调度循环崩溃 / 卡死不再拖累在线请求（与 backup sidecar 同一逻辑）；
- 资源画像独立：任务进程的 CPU/内存尖峰不挤占请求路径。

### 跨进程的两个机制（都依赖 `/app/data` 共享卷）

1. **文件锁互斥跨容器成立**。`job-*.lock` 落在 DATA_DIR（named volume），worker、
   api、backup 看到同一个文件——手动触发按钮（api）撞上定时执行（worker）时，
   后到的一方记 `skipped_locked`，不会双跑。实测：api 手动触发 prune_spans 成功
   （worker 当时未持锁），执行历史记 `attempt=1 success`。
2. **写竞争靠 busy_timeout 排队**（`app/core/db.py`，`SQLITE_BUSY_TIMEOUT_MS`
   默认 5000）。WAL 单写者：api 写业务表、worker 写 `job_runs` 撞上时排队等锁，
   不再立刻抛 `database is locked`。重建后四容器并发写，日志零 locked 错误。

### worker 接管的过程（实测）

```
[worker] registry synced: 1 jobs（新增 1）: prune_spans
[worker] scheduler on: 每 30s 扫一轮到期任务
```

api 侧对应打印 `job scheduler disabled (JOBS_ENABLED=0)`。worker 启动即扫一轮：
`prune_spans` 的 `last_ts` 距上次超 6h → 立即执行，执行历史照记。
观测面板 `GET /api/obs/jobs` 的数据源不变（jobs/job_runs 表），api 进程里
`app/core/jobdefs.py` 注册同一份任务定义供面板与手动触发使用。

### 单进程模式不受影响

本地 `start.bat` 直跑 uvicorn 时不设 `JOBS_ENABLED`（默认 1），调度线程照旧在
api 进程里跑——两种形态共用同一份任务定义与同一套执行历史表。

### web（nginx）容器

- 镜像 `frontend/Dockerfile`：`nginx:alpine` + `COPY dist`（与 api 镜像同一约定：
  构建机不依赖 node，dist 由宿主机 `npm run build` 产出）；
- `frontend/nginx.conf`：`/api/` 反代到 `api:8765`（URI 原样透传）、`/health`
  直通、`/assets/` 长缓存（hash 文件名，30 天 immutable）、LLM 编排类接口的
  `proxy_read_timeout` 放宽到 300s；
- 限流取真实客户端 IP：nginx 设 `X-Forwarded-For`，api 侧
  `RATE_LIMIT_TRUST_PROXY=1` 时取首段。前提是入口收敛到反代——8765 仍对外开放时
  直连客户端可伪造 XFF（本机自用可接受，对外暴露时关闭该开关或收端口）；
- 实测：`GET /` 200（text/html）、资源 200 + 30 天缓存头、`/health` 透传、
  `/api/stats` 带 token 200。

## 12. 混沌演练（阶段 B，2026-11-17）

```powershell
python scripts\chaos_drill.py kill-api        # 进程崩溃 → restart 策略 → RTO
python scripts\chaos_drill.py sever-litellm   # 停 LLM 网关 → 熔断三态实弹
python scripts\chaos_drill.py cpu-limit       # 限 1 CPU 复跑压测 → 瓶颈定位
python scripts\chaos_drill.py all             # 顺序跑三个
```

docker CLI 要在 PATH（见第 1 节）；演练前确认六容器 healthy。

### 实测结果

| 演练 | 结果 | 关键数字 |
| --- | --- | --- |
| kill-api | PASS | 容器确认重启（StartedAt 变化），热启动 **RTO 3.4s**，业务探针恢复 |
| sever-litellm | PASS | 5 次连接失败即打开；打开期间调用 **80ms 快速失败**；恢复探针成功即闭合（退避 30→60s 跟随） |
| cpu-limit | 数据有效 | 见下表——瓶颈不在 CPU |

CPU 限额对照（限流关闭、带 token，同日同条件配对压测）：

| 场景 | 并发 1 | 并发 4 | 并发 8 |
| --- | --- | --- | --- |
| 不限 CPU | 224 rps / P95 6ms | 291 / 23ms | 200 / 122ms |
| 限 1 CPU | 219 rps / P95 6ms | **294 / 23ms** | 190 / 129ms |

**结论：吞吐与 CPU 配额无关——瓶颈在 SQLite 单写者锁，不在算力。** 扩容方向是
存储层（换库/读写分离），加核无效。这比"压测有拐点"多了半步：知道拐点是什么造成的。

### 演练挖出的 4 个真 bug/坑（这才是演练的价值）

1. **`docker kill` 不触发 restart 策略**（restarts=0 实锤）：守护进程把它当作人为
   停止。模拟崩溃必须让进程"自己死"——app/main.py 内置 SIGUSR1 钩子（`os._exit(137)`），
   `docker exec <api> python -c "import os,signal; os.kill(1, signal.SIGUSR1)"`。
2. **命名空间内 kill PID1 的 SIGKILL 被内核忽略**：第一版演练"kill -9 1"后
   /health 秒回、报 PASS——容器根本没死，RTO 是假数据。演练脚本必须校验
   StartedAt 变化（防假阳性已内置）。
3. **`docker network disconnect + connect` 会丢内嵌 DNS 注册**：IP 直连通、服务名
   NXDOMAIN，`docker restart` 都救不回来，只能 `--force-recreate`。所以断网演练
   改用 `docker stop/start`（语义也更真实：网关进程死亡）。
4. **两个产品级 bug**：console chat 响应体漏了 `error` 字段（200 + 空错误让客户端
   分不清"答好了"和"这轮没跑成"，已修）；load_test.py 默认 base-url 指向 8000 端口
   且预检不拦连接异常（错误率 100% 的假数据，已修：默认 8765 + 预检拦异常）。

### 其他实测细节

- **熔断的 open 不会自己闭合**：三态机只在"有请求进来"时才从 open 转半开——
  干等永远不会恢复，演练要主动发探针（脚本已内置）。
- **CPU 限额的撤销**：`--cpus=0` 不是合法值，用 `docker update --cpu-quota=-1`。
- 压测对照要**关限流**（.env 加 `RATE_LIMIT_ENABLED=0` + 重建 api），测完删掉重建；
  不关的话 95% 请求被 429 挡住，测到的是闸门不是容量。

### 尚未做

演练编排/定时执行（现在是手工脚本）、把 chaos_drill 接进 CI（需要自托管 runner，
GitHub Actions 的容器环境不是本机拓扑）。

## 13. 容量采样与扩容决策（阶段 C，2026-11-17）

`capacity_sample` 是 worker 里的定时任务（默认 300s），采一次写一行
`capacity_samples`，保留 30 天。判定逻辑与阈值在
`app/services/capacity_service.py`，路线与理由见 `docs/规划-架构演进.md`。

```bash
# 看当前判定与趋势（refresh=true 立即补采一次）
curl -s -H "X-API-Token: $TOKEN" "http://127.0.0.1:8765/api/obs/capacity?refresh=true"

# 手动触发一次采样（走 job runner，执行历史照记）

# 面板
open http://127.0.0.1:8080/metrics      # 「扩容决策（触发条件驱动）」卡
```

实测（六容器 healthy、空闲状态）：库 10.3 MB / WAL 0.2 MB / 写锁等待 0 ms /
挡住率 0% / load1 0.56（12 核）/ `capacity_sample` 执行 3 ms → 四项判定全部
未触发。真实数据量下库会更大，趋势看几天才成形（20 条样本 = 100 分钟）。

### 验证探测真的有效（可复现）

```bash
# 在 api 容器里另起一个进程占住写锁 4 秒
docker exec -d job-prep-api-1 python -c "
import sqlite3, time
c = sqlite3.connect('/app/data/kb.sqlite'); c.execute('BEGIN IMMEDIATE')
time.sleep(4); c.rollback()"
sleep 1
curl -s -H "X-API-Token: $TOKEN" "http://127.0.0.1:8765/api/obs/capacity?refresh=true"
# → sample.lock_blocked=1, lock_wait_ms≈251；postgres 判定为 warn（样本 <20，先继续采样）
# 验完清掉注入样本：
# docker exec job-prep-api-1 python -c "import sqlite3; c=sqlite3.connect('/app/data/kb.sqlite'); c.execute('DELETE FROM capacity_samples WHERE lock_blocked=1'); c.commit()"
```

**注意两个设计点**：

- 探测预算 250 ms，所以 `blocked=1` 的样本 `lock_wait_ms` 会落在 250 左右——
  它表示"写者至少要等这么久"，不是精确值。
- 分布类指标（P95 / 挡住率）在样本 < 20 时只给 `warn`：刚部署时两条样本里有
  一条排队就宣布"该换库"，是拿噪声当结论。

## 14. 告警判定（阶段 C 续，2026-11-17/18）

告警规则一共 8 条：错误率、慢调用、成本、工具失败、编排失败，加上容量三条
（库体积、写锁排队、库增速）。

### 分级路由与静默时段（2026-11-18）

| 机制 | 配置 | 行为 |
| --- | --- | --- |
| 分级 | 代码常量 `RULE_SEVERITY`（8 条全有映射） | `error_rate` 与"库已满"是 **critical**（值得被叫醒的两类），其余 warning |
| 路由 | `ALERT_WEBHOOK_URL_CRITICAL` / `_WARNING`，未配兜底到 `ALERT_WEBHOOK_URL` | critical 走值班通道、warning 走群；generic 报文带 `level` 字段 + 消息前缀双保险 |
| 静默 | `ALERT_QUIET_START` / `_END`（支持跨午夜 23:00→07:00，两端相等=未配置） | 窗口内**只落库不推送**（delivered=0 + 原因）——"夜里报过什么"必须可见 |

两个口径：
- **静默记录也占冷却**：否则静默一过，积压的每轮记录会全部补推出来。
- `send_test` 走 info 级（warning 通道）——测试告警不该吵醒 critical 通道。

踩坑记录：测试里 `db.get_conn().execute(UPDATE)` 链式再 `db.get_conn().commit()`
会被连接池借出检查**回滚**（第二次借出看到 `in_transaction=True` 就回滚上个
事务——防"忘 commit"的保护）。UPDATE 和 commit 必须用同一个连接对象。

### 谁来跑：从 api 线程搬到 job

以前判定跑在 api 的守护线程里（`alerts.start_background()`），这和阶段 A 立的
"一个进程一种职责"矛盾——api 表面上是请求面，实际背着一个定时线程。现在：

| 部署形态 | 判定在哪跑 | 判断依据 |
| --- | --- | --- |
| 容器（compose） | `worker` 的 `alerts_check` job，默认 60s | api 设 `JOBS_ENABLED=0`，调度器没起 |
| 单进程直跑（start.bat） | api 内的线程（行为不变） | 调度器在本进程起了 |

两者互斥，同一时刻只有一份判定。搬进 job 之后还多了个好处：**检查本身有执行
历史**（`job_runs`），以前线程挂了只打一行 `[alerts] check failed`，没人会看见。

```bash
# 看检查有没有在跑（last_status=success、间隔 60s）
curl -s -H "X-API-Token: $TOKEN" http://127.0.0.1:8765/api/obs/jobs | python -m json.tool | head -20
# 手动触发一次
curl -s -X POST -H "X-API-Token: $TOKEN" http://127.0.0.1:8765/api/obs/jobs/alerts_check/run
# 告警历史 + 配置 + 送达失败数
curl -s -H "X-API-Token: $TOKEN" "http://127.0.0.1:8765/api/obs/alerts?days=7"
```

面板：指标页「告警历史（近 7 天）」卡，带"发测试告警"按钮（`POST /api/obs/alerts/test`）。

### 容量三条的判定口径

| 规则 | 触发条件 | 为什么这么定 |
| --- | --- | --- |
| `capacity_db_size` | 体积 / 上限 ≥ 80%（100% 升 critical） | 80% 是准备期，100% 才是必须动手 |
| `capacity_write_lock` | 近 30 分钟 ≥3 条采样中，被锁挡住 ≥5% | **不用 P95 作触发面**：探测预算 250ms，挡住一次 P95 就 ≥250ms，两条样本就能让 P95 超线——那是统计假象 |
| `capacity_db_growth` | 按当前增速 ≤30 天到上限，且 7 天样本 ≥20 | 斜率至少要有 100 分钟样本才稳 |

### 没配 webhook 也会判定

这是有意的：**"规则在工作但推不出去"必须可见**。此时告警照常落库
（`delivered=0` + error 说明原因），冷却拉长到 `ALERT_LOCAL_COOLDOWN_MIN`（默认
360 分钟），避免每 30 分钟写一条一模一样的记录把历史淹掉。面板上这条会显示
"未送达"——看到它就该去配 webhook 了。

实测（2026-11-17，容器内、未配 webhook）：

```
POST /api/obs/alerts/test  → delivered: False
                             error: ALERT_WEBHOOK_URL 未配置，仅落库不推送
GET  /api/obs/alerts       → total: 2, deliver_failed: 1
```

容量规则的链路也验过：一次性把 `ALERT_DB_SIZE_RATIO` 设 0 触发 `capacity_db_size`
（10.3 MB / 2048 MB），消息与落库正确，验完删除了那条注入记录。

### 关掉告警

`ALERT_CHECK_SEC=0` 表示不注册该任务（与单进程模式"不启动线程"语义一致）；
不是"每 10 秒跑一次"——间隔下限 10s 只对非零值生效。
