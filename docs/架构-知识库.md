# 架构：知识库（Job Prep KB）

日期：2026-10-30　状态：与代码同步（提交 cdd1281 之后）

---

## 一、一句话

**`knowledge/` 下的 Markdown 是唯一事实源，SQLite 是状态库与索引库，FTS 与向量是两份可重建的派生索引。**
所有写入都先落 Markdown 再落库，所有读取都可以从 Markdown 重建——这条不变量决定了整个架构的取舍。

这样做的现实原因：你会在 Obsidian 里手改卡片（改要点、加 related、标 mastery），
如果数据库是真相源，手改就会被下一次写库覆盖；反过来把 md 当真相源，重启时一次全量同步就能收编。

---

## 二、三层结构

```
写入（5 条通道）        真相源                 索引 / 状态                 读（4 个消费方）
─────────────────      ─────────────────      ────────────────────       ─────────────────
手写建卡        ┐       knowledge/**.md        kb_cards + kb_cards_fts    混合检索 hybrid_search
AI 建卡（审批）  │  ──▶  frontmatter 元数据 ──▶  （触发器双向同步）    ──▶  评分上下文 context_builder
面经自动抽题     │      正文：要点 / 易错        embeddings（向量）          飞轮匹配 _match_card
模拟面试补洞     │                              mastery / srs_due           复习调度 review_service
实战卡回灌       ┘                              （状态，不回写 md 正文）      知识库页面 /api/cards
```

### 1) 真相源：`knowledge/{domain}/{topic}/{title}.md`

```markdown
---
id: kb-bigdata-flink-001          # 主键，全局唯一，建卡时生成
domain: bigdata                  # backend / bigdata / agent / project / cs
topic: Flink                     # 主题，决定目录、覆盖匹配、上下文注入
title: Flink 窗口机制
mastery: 0                       # 掌握度 0~5（状态字段，同步进库）
srs_due: ""                      # 下次复习日期
tags: ["高频"]
related: []                      # 互链卡片 id（实战卡 ↔ 原子卡）
source: manual                   # manual / agent / mock / ingest
created: 2026-10-26
updated: 2026-10-26
---

# 标题
**Q：** 题目原文
## 要点
- 一行一条，结论→机制→工程→权衡
## 易错
- 一行一条坑点
```

- 目录即分类：`domain/topic` 两级，`id` 里也编进 domain/topic 缩写（`kb-bigdata-flink-001`），
  好处是看 id 就知道归属，坏处是 topic 改名后 id 仍旧（这是有意的：id 稳定优先于可读性）。
- 正文结构固定三段（标题 / Q / 要点 / 易错），因为 `card_to_md()` 是生成的唯一出口，
  手改的人只要不破坏 frontmatter，正文随便写。
- **状态字段（mastery / srs_due / last_review_at）以库为准**：`sync_all()` 收编时只补缺失行，
  不覆盖已有 mastery/srs_due——否则每次重启都会把复习进度清零。
- **收编会把正文读回来**：`parse_md_body()` 从 `## 要点` / `## 易错` / `**Q：**` 解析出正文，
  空库重建时得到的是真卡而不是"有卡但点不开"的空壳卡（空壳卡比无卡更危险：让人以为会了）。
- **status 只在首次收编时读 frontmatter**：库里已有这行就只同步 `file_path`。
  "这张卡还收不收"是维护者的判断，存在库里；md 跟着标记，但不反向覆盖。

### 2) 索引 / 状态库：`data/kb.sqlite`

| 分组 | 表 | 职责 |
|---|---|---|
| **知识层** | `kb_cards` | 卡片的投影（title/question/points_json/pitfalls_json/related_json/tags + 状态 + file_path） |
| | `kb_cards_fts` | FTS5 **外部内容表**，content=`kb_cards`，由触发器维护 |
| | `embeddings` | `(entity_type, entity_id)` → 向量 JSON + `text_hash` |
| **题目层** | `question_pool` | 题目池（text/aliases/qtype/topic/freq_count/merged_into） |
| | `question_fts` | 题目 FTS5 外部内容表 |
| | `question_occurrences` | 题目 × 面经（`UNIQUE(question_id, interview_id)`） |
| | `feed_interviews` / `ingests` | 面经归档与投喂状态机 |
| **反馈层** | `mistakes` / `mastery_events` / `srs_reviews` | 错题、掌握度变更流水、复习记录 |
| | `mock_sessions` / `mock_answers` | 模拟面试与逐题评分 |
| **飞轮层** | `coverage_reports` | 每场面经一份作战地图（`UNIQUE(interview_id)`，重跑覆盖） |
| | `interview_outcomes` | 真实面试结果回录（校准预测） |
| | `improvement_plans` | 项目改造方案（**不进知识库**，只是施工单） |
| **治理层** | `agent_actions` / `runs` | HITL 审批队列（pending/approved/rejected/failed）、Agent 轨迹 |
| | `console_messages` | 对话台每轮消息 + `trace_json`（工具名/入参/结果预览）+ `ctx_json`（本轮 token 账本），会话按 `session_id` 分组 |
| | `conversation_summary` / `ctx_traces` | 窗口外旧对话的三段式摘要（`covered_to_id` 防重复压）、每次组装的上下文账本（2026-11-05 上下文管理改造） |

关键约束：

- FTS 用 **external content + 触发器**，不用代码手工塞。踩过的坑：合并同义题、改题面时手工同步漏了，
  表现为"明明有这道题却搜不到"。触发器是数据库层保证，绕不过去。
- FTS 列名必须与真实列**一一对应**，否则 FTS5 回读列值时拼出 `SELECT T.<col>` 直接报错。
- `embeddings.vector` 存 JSON 文本，不引向量库服务：几千条 numpy 暴力余弦 <10ms，
  2C2G 的机器装不起 Milvus/pgvector。换手点固定在 `embedder.search_similar()`，接口不变。

### 3) 派生索引：FTS + 向量

- **FTS 路**：`kb_cards_fts MATCH`，bm25 排序，精确命中强（`Tungsten-sort`、`RDB`）。
- **向量路**：`bge-small-zh`（512 维，fastembed 本地跑，不烧 token），语义召回强（"消息不丢"≈"可靠性"）。
- 两者由 `hybrid_search()` 用 **RRF（1/(60+rank)）** 融合，不做分数归一，免调参。
- `ensure_all_indexed()` 负责补齐 + **清理残留**：卡片归档/合并后向量还在的话，向量路（无 status 过滤）
  会把归档卡继续捞出来，表现为"明明归档了还在推荐"。

## 三、写入：5 条通道，一个收口

| 通道 | 入口 | 是否经 LLM | 是否经人工 |
|---|---|---|---|
| 手写建卡 | `POST /api/cards` → `kb_service.create_card` | 否 | 人自己写 |
| AI 建卡 | `POST /api/agent/cards/draft` → `agent_actions(pending)` → 审批 | 起草 | **必须** |
| 面经抽题 | `ingest_service.confirm_ingest` | 抽题 | 质检勾选（对话台自动过质量闸门，人只在被拦下时确认） |
| 模拟面试缺口 | `review_service`（均分<4 自动补卡） | 评分 | 否（自动，可回滚） |
| 实战回灌 | `POST /api/plans/{id}/experience` → `agent_actions(pending)` → 审批 | 起草 | **必须** |

无论哪条通道，最终都走同一个函数 `kb_service.create_card()`：分配 id → 写 md → 写 `kb_cards` → **立刻建向量**。

> 最后一步是 2026-10-30 补的：原先向量只在启动时批量建，导致"建卡→立刻起草改造方案"时
> 匹配不到刚建的卡（`card_id=None`），实战卡失去互链目标，飞轮断在第三步。

### 不变量（改动时别破坏）

1. md 先于 db：先写 md 再插库；插库失败就把刚写的 md 删掉。顺序反过来（先插库再写 md）
   出问题会留一行**指向不存在文件的卡**——`sync_all()` 是 md→db 单向的，补不了这个方向，
   那行卡永远读不到内容。md 写成功但库没写成功则相反：下次启动 `sync_all()` 会收编回来。
2. 一行卡 ↔ 一个 md：`domain/topic/title` 三者相同会算出同一个相对路径，两张卡写同一个文件，
   后写的把前一张的内容覆盖掉（库里两行、md 只剩一份）。撞名时 `create_card` 会把卡号缀进文件名：
   `标题 (kb-bigdata-spark-002).md`。
3. `points_json` 是数组的 JSON 字符串，`ensure_ascii=False`——中文要点必须是可读的。
4. `related_json` 双向：`link_related()` 同时改两张卡 + 两边 frontmatter。
5. 归档用 `status='archived'`，**不删** md——删了就没法复盘"我为什么放弃这张卡"。
   归档标记同时写进 md 的 frontmatter（`status: archived` + `merged_into`）：md 是事实源，
   只改库的话，换台机器用 md 重建库时归档卡会以 active 身份复活。

## 三·五、答案三态：抽取阶段就把"要不要建卡"分流掉

面经里不只有题目，还有楼主自己写的答案。原来的抽取只拿题面，把答案连同"答得对不对"
一起丢掉了，结果所有题一个待遇：都当"没有答案"，都走模型从零起草。

现在抽取阶段（`prompts/extract_interview.yaml` v3）多判三件事，逐题落在 `question_pool` 上：

| 字段 | 取值 | 写在哪 |
|---|---|---|
| `doc_type` | interview / single_question / answer_snippet | `ingests.extracted_json` |
| `answer_completeness` | none / partial / complete | `question_pool.answer_completeness` |
| `answer_points_json` | 从原文答案拆出的要点 | `question_pool.answer_points_json` |
| `answer_gaps_json` | 原文缺了哪些要素 | `question_pool.answer_gaps_json` |

三条下游路径：

```
complete  → 答案规范化（prompts/card_from_answer.yaml）→ source: extract 的卡，审批可批量过
partial   → 已抽到的部分写进 answer_points，缺的由模型起草 → source: agent 的卡，逐条审
none      → 不写 answer_points，模型从零起草            → source: agent 的卡，逐条审
```

三个设计决定，都是踩过的坑：

1. **判定不在建卡阶段做，也不全在抽取阶段做完**。抽取只做判定 + 提议，真正的建卡发生在
   `confirm_ingest` 之后——因为题目进池前没有 `question_pool.id`，提前建卡只能编一个假 id，
   审批通过后落库找不到题（悬空的 `question_id`）。
2. **`complete` 也过审批**。理由不在"模型可能编"，而在 `context_builder` 会把
   `answer_points_json` 的前 4 条塞进模拟面试的评分上下文——参考答案错一条，污染的是整轮打分，
   而且这种污染是静默的（你只会觉得"打分怎么这么松"）。所以只给"批量批准"的便利，不给自动落库。
3. **说 `none` 却抽出答案文本 → 升 `partial`**；说 `complete` 却列了 gaps → 降 `partial`；
   说有答案但文本为空 → 降 `none`。三条都在 `llm.extract_interview` 里做，因为模型自报的
   枚举值会自相矛盾，而判定错 = 数据流向错。

评测单开一组（`evals/extract_judge_cases.jsonl` + `eval_extract_judge`），除了常规准确率，
专门盯两列：`complete_precision`（误判 = 污染评分基准）和 `bare_recall`（漏判 = 该建的卡没建）。

## 四、读取：4 个消费方，三种检索档位

### 档位（`rag_service.search(mode=...)`）

| 档位 | 链路 | 用途 |
|---|---|---|
| `fts` | 2-gram 前缀 OR + bm25 | 基线，评测对照组 |
| `hybrid` | FTS + 向量 → RRF | 默认 |
| `full` | 改写 3 条 query → 各自 hybrid → 融合 → LLM listwise rerank | 知识库页面"深度搜" |

### 五个消费方

| 消费方 | 用什么 | 为什么这么选 |
|---|---|---|
| 知识库页面 | `search()` + 子串 LIKE + IDF | 页面要"能搜到我记得的词"，IDF 让"记忆"压过到处都有的"Agent" |
| 评分上下文 | `context_builder.build_eval_context` | 只注入**同主题**卡片（跨主题=噪音，曾把 Kafka 卡塞进幻觉题导致系统性压分），1500 字预算 |
| 飞轮匹配 | `_match_card`（纯向量 + 阈值） | 要判断"这题我有没有卡"，同主题 0.75 / 跨主题 0.85，主题先归一化 |
| 复习调度 | `srs_due` + `mastery` | SRS 间隔 [1,2,4,7,15,30] 天，按掌握度取档 |
| **Agent 工具** | `harness.search_kb`（2026-10-30 新增） | 让模型自己决定查什么：返回要点原文 + `card_id` + `confidence`，空壳卡显式标 `warning` |

### 阈值是量出来的，不是拍的

6 张卡 × 55 题的实测分布：同主题真实覆盖 **0.83~0.99**，跨主题噪声 **0.50~0.68**。
所以同主题取 0.75、跨主题取 0.85。早期用单一 0.50，把"Spark shuffle"误配到"Redis 缓存"
（0.533），覆盖率虚高到 24%；改完后掉到 5~7%——**那是真实值**。

## 四·五、Agent 入口：对话台（2026-11-04）

之前的 Agent 能力都藏在各页面按钮后面（"生成计划""起草建议"），人还是编排器：
点哪、点什么、下一步去哪，全由人串。对话台把这件事反过来——**人只说要什么，Agent 自己拆步骤调工具**。

```
用户一句话 → console_service.chat()
             ├─ _env_snapshot() 预注入状态（卡数/待审/最近面经/最近采集）→ 省掉一轮工具往返
             ├─ 合并工具集：harness 6 个只读 + agent_tools 7 个（其中 5 个写）
             ├─ ReAct 循环 ≤8 步：模型决定调谁、连着调、最后用人话汇报
             └─ trace 落库 console_messages.trace_json（工具名/入参摘要/结果预览 300 字）
```

### 两道闸门，分工不同

| 闸门 | 位置 | 拦什么 | 为什么这么放 |
|---|---|---|---|
| 模式闸门 `MODE`（contextvars） | 工具实现第一行 | assist 模式下所有写工具**直接返回拒绝**，不执行 | prompt 里写"请不要写"是软约束，模型不听话时没有兜底 |
| 质量闸门 `auto_pool_gate` | 抽取之后、入池之前 | 0 题 / 题面 <4 字 / >40 题 / 缺 doc_type | 2026-10-31 那 12 张重复卡就是"抽完直接入池"的产物 |

**建卡不在 Agent 手里**：`create_card` 只可能从 `decide(approve=True)` 调用，Agent 最多把草稿写进
`agent_actions(status='pending')`。这是项目从第一天起的不变量，对话台没有为"自动化"破例。

### 实测（真实 LLM，2026-11-04）

| 输入 | 步数 | 结果 |
|---|---|---|
| "知识库多少活卡、几张待审" | 0（环境快照已够） | 1.3 秒答对，未浪费工具调用 |
| "收这份面经"（5 题） | 3 | 入池 5 题 → 起草 3 张待审卡 → 跑通作战地图；`kb_cards` 变化 **0** |
| "用最近一份面经跑作战地图" | 1 | 7 题 / 预测 3.3 / 缺口 4，与直接调服务的结果一致 |

顺带发现并修掉一个真 bug：`analyze_interview` 的 SQL 把 `q.id` 别名成 `qid`，循环里却读 `q["id"]`，
于是**任何有题的面试都会 IndexError**，作战地图对所有真实面经都是崩的（详见坑 6）。

### 上下文怎么进模型（2026-11-05）

对话台的 messages 不再手拼，全部经 `app/context/assembler.assemble()`：

```
token_budget(计量) → window(选) → summarizer(压) → memory_retriever(取) → assembler(装+降级+记账)
```

- **窗口**：最近 6 轮必留；更早的分级锚定——P0 用户约束（最近 4 条）永不丢，P1 引用（业务 id / 评分）
  预算不够就丢。纯滑窗会把"只用 SQLite，别引 Redis"这类约束滑掉，而模型不会报错。
- **摘要**：窗口外的对话压成「事实/进度/约束」三段落 `conversation_summary`，
  后台跑、下一轮生效；`covered_to_id` 保证不重复压，被覆盖的消息也不再进历史（否则重复计价）。
- **检索**：复用 `hybrid_search` 取 Top-3 卡片；摘要只在会话内按 2-gram 匹配（跨会话噪音大）。
- **降级顺序固定**：检索 → 摘要 → 最旧轮次，每降一级写 `ctx_traces.degraded_json`；
  真守不住时宁可标 `CTX_KEEP_CONSTRAINT` 也不静默丢约束。
- **轮内裁剪**：ReAct 循环的工具结果单独裁（8 步 × 2600 字比历史更容易爆）。

实测（20 轮 × 1200 字回复）：改前 6 轮硬截断 token 恒定 5318 但约束只剩 6/20；
改后 7134 且约束 20/20；单轮长物料 17516 → 7772。完整取舍见 `docs/复盘-上下文管理.md`。

## 四·六、RAG 看板（2026-11-05）

侧边栏「RAG 看板」，一屏回答三个问题：库里有什么、检索有多准、缺口在哪。

**后端 `app/api/rag_board.py`，两个接口：**

| 接口 | 做什么 |
|---|---|
| `GET /api/rag/board` | 知识库构成 + 最新 `evals/results-*.json` + 图谱节点边，一次返回 |
| `POST /api/rag/eval` | 现跑一遍评测。`with_llm=false` 只跑 fts/hybrid（约 2 秒、0 次 LLM 调用）；`true` 才跑 full（改写 + LLM 重排） |

三个取舍：

1. **评测读文件、不现算**：19 用例 × 2 档要几秒，full 档还要 19×2 次 LLM。看板要秒开，
   重评是显式按钮。重评走 `importlib` 加载 `scripts/run_evals.py`——评测逻辑只有一份，
   CLI 和看板不会漂移。
2. **指标直接对标 `evals/thresholds.json`**：达标记绿、未标记红。现在 hybrid hit@5 0.737
   与 fts 0.789 都没过 0.85 的线，看板上是红色——**难看但真实**，比调低阈值体面。
3. **图不是知识图谱**：库里没有实体关系抽取，边只有三种真实关系——域→主题→卡（层级）、
   卡↔卡（`related_json`，全库仅 2 条）、卡→题（题目池 `related_card_ids_json`，16 题）。
   所以页面上明确写「这不是知识图谱」。把覆盖率图伪装成知识图谱，面试里一问就穿。

**为什么无卡题单独一类**：47 个灰点就是覆盖缺口本身。图上看得见「一半题目悬空」，
比表格里 25% 这个数字更有说服力。

**口径陷阱（2026-11-06 起用关系表收敛）**：题↔卡关系已升级为一等关系表
`card_question_links(question_id, card_id, match_method, confidence, created_at)`，
json 列降级为镜像（写路径双写，读路径走表）。`match_method` 区分 legacy（存量回灌）/
drafted（Agent 建卡）/ manual（页面建卡）/ vector（相似度判定的自动挂接）。
看板 16/63 与作战地图 31% 的口径差就此可解释：前者是「去重后题面有关联卡」

两个数从同一张表出，看板 hint 里直接展示分桶。原口径说明：
看板的「题目→卡关联率」是 16/63 = 25%（`related_card_ids_json` 直接关联），
作战地图的覆盖率是 19/62 ≈ 31%（按题目出现次数加权、且接受 `_match_card` 的向量匹配）。
两个数字都对，但**分母和判定方式不同**，别在简历上混用。

## 四·七、知识库分层视图（2026-11-06）

侧边栏「知识库」页默认进入分层模式：把 L0~L3 的分层架构变成可点的树，
题目池不再是独立页面才看得到的孤岛，而是挂在树上的 L3。

**后端 `app/api/kb_tree.py`，一个接口：`GET /api/kb/tree`**，一次返回：

- `layers`：每层计数（域/主题/卡 active+archived+hollow/题 linked+orphan/关联边 by_method/面经数）；
- `domains[] → topics[] → {cards[], questions[]}`：整棵树带内容，前端三级过滤全在客户端做（量级 <200）。

**题目归层规则（从强到弱，透明可解释，不搞黑盒相似度）**：
1. `card_question_links` 已关联卡 → 跟卡走（关系表是一等公民）；
2. 未关联但题面 topic 与某主题同名 → 借宿该主题（`topic_home` 映射）；
3. 都没有 → 「未归类」桶。**这个桶不是垃圾箱，就是覆盖缺口清单本身**
   （当前 41/63 题在里面，和 RAG 看板的 orphan 口径一致）。

**两个详情接口支撑「点进去看」**：

| 接口 | 给什么 |
|---|---|
| `GET /api/cards/{id}`（扩展） | 卡详情 + `linked_questions`（L2→L3 向下指针） |
| `GET /api/questions/{qid}`（新增，stats.py） | 题面 + 别名 + `linked_cards`（含 match_method）+ `occurrences` 面经出处（L3→L4 证据链：哪家公司哪一轮问的） |

**前端 `Cards.vue` 双模式**：分层（默认，层级总览条 + 域/主题/内容三栏，卡和题点开抽屉互跳）
+ 平铺列表（原视图原样保留，服务端 FTS 搜索）。无卡题在列表里打红标「无卡」，
题目抽屉里一键「AI 起草建卡」直达审批中心。

**和 RAG 看板的分工**：board 回答「检索质量怎么样」，分层视图回答「每层都有什么数据、
数据之间怎么连」——前者是质量仪表盘，后者是内容地图。

## 四·八、MCP 接入层（2026-11-09）

知识库除了网页和内置 Agent，还对外暴露成一个 **MCP server**——任何支持 MCP 的宿主
（Claude Desktop / Cursor / WorkBuddy）都能直接查它。接入方式见 `docs/MCP接入.md`。

```
MCP 客户端 → [app/mcp/gateway] → service 层 → SQLite / 向量 / knowledge/*.md
                  ↓
            mcp_calls（每次调用一行）
```

**代码位置**

| 文件 | 职责 |
|---|---|
| `app/mcp/gateway.py` | 注册表（8 个）、统一执行、结果截断、调用日志 |
| `app/mcp/tools.py` | 带类型的对外签名（`Annotated[..., Field(description=…)]` → inputSchema） |
| `app/mcp/server.py` | MCPServer + 资源/提示词 + stdio / streamable HTTP + BearerGuard |
| `app/api/mcp_board.py` | 看板数据、试跑、现场评测 |
| `scripts/mcp_eval.py` | 契约档 + 选择档评测（CLI 与页面共用） |

**四个设计判断**

1. **工具按「一次对话回合能完成的任务」切，不按表 CRUD**：只暴露 8 个（读 6 写 2）。
   拆到 12 个以上就开始互相抢活，模型的选择错误率随工具数上升。
2. **返回按 token 预算设计**：列表只回摘要（id + 标题 + 一个判断依据），全文靠
   `get_card` 二次下钻；单次结果硬截断 6000 字符。工具结果和检索结果一样会进上下文。
3. **写操作只产草稿**：`draft_cards` / `ingest_text` 产审批动作，不落库；页面「试跑」
   直接拒绝写工具。MCP 客户端是外部输入，不能给它一条绕过人审的写通道。
4. **单一事实源**：工具是 service 的薄壳，不复制业务查询。REST、内置 Agent、MCP
   三条入口共用同一条实现——多读路径分叉是这个项目已经付过学费的坑（坑 6）。

**可观测**：`mcp_calls(tool, client, args_json, args_hash, status, error, latency_ms,
result_chars, result_preview, read_only)`。stdio 传输下 stdout 就是协议管道，
不能 print 日志，结构化落库是唯一不破坏协议的手段。

**评测两档，回答两个不同问题**

| 档位 | 做法 | 回答的问题 | 成本 |
|---|---|---|---|
| 契约 | 固定参数直接打读工具 | schema/实现/返回是否可靠 | 约 2 秒，0 次 LLM |
| 选择 | 只给工具清单 + 自然语言请求，让模型选 | 工具描述够不够清楚、模型会不会用错 | 24 次 LLM 调用 |

指标：契约通过率、工具选择准确率（含「不该调工具」的负例）、参数准确率、
端到端成功率（分母只算真正执行的读用例）、越权率（只读请求误用写工具，上限 0）。

**实测（2026-11-09，24 用例）**：契约 16/16；工具选择 24/24、参数 100%、端到端 100%、越权 0；
调用 117 次，p95 103ms（首次检索 1.1s 是 embedding 冷启动）。
部署前后对比：接 MCP 之前 REST/Agent 两条入口就够用，MCP 的收益是**可接入性**，
成本是多一套 schema 要同步、调试链路变成「模型 → 宿主 → server → service」四段。

**这一轮抓到的两个「不是代码 bug 的 bug」**

1. `e2e_rate` 分母把写工具和负例也算进去了，看着只有 0.667——指标定义错比实现错更常见，
   一个分母就能让好系统显得很糟。
2. 写类用例第一轮全挂：请求写「帮我给这道题建张卡」，无状态服务里「这道题」没有指代，
   模型要求澄清是**正确行为**。修的是用例（带上题号 `q-0007`），不是代码。
   评测第一次跑出来的往往是「假设错了」，不是「实现错了」。

## 五、六个必须记住的坑（面试可直接讲）

1. **中文 FTS 是坏的**：unicode61 把连续中文当**一个** token，整句中文一条都召回不了。
   解法：查询端自己切 2-gram 并加**前缀通配**（`"数据"*`），文档侧同样被切成长 token，精确匹配全落空。
2. **2-gram 足够召回、不够判重**：判重用 3-gram 重合预筛 + `difflib.ratio ≥ 0.9` 裁决，
   向量只在 ≥0.95 时兜底。
3. **事务内重建索引会死锁**：`confirm_ingest` 持写事务时调 `ensure_all_indexed()`，
   它会开第二个连接写 `embeddings` → `database is locked`。默认 `ensure_index=False`。
4. **`INSERT OR IGNORE` 会静默丢题**：`UNIQUE(question_id, interview_id)` 冲突时吞掉整条，
   表现为"18 道题只进 10 道"。改成显式判重 + 普通 INSERT。
5. **向量索引是独立索引，不随 status 变**：归档卡不清向量 = 永远被推荐。
   现状：`_archive_card` 与 `rag_service.rebuild` 的 stale 清理已双保险
   （实测归档卡残留向量 0/12），embeddings 另加 `model` 列记生成模型，
   换模型时只重嵌不匹配的行，防止新旧向量混算余弦。
6. **别名改了，下游取值没跟着改**：`analyze_interview` 里 `SELECT q.id AS qid`，循环里却读
   `q["id"]` —— `sqlite3.Row` 只按键名取值，于是任何有题的面试都 `IndexError: No item with that key`。
   这个 bug 活了很久没被发现，原因值得记：① 接口有 try/except 兜底成 400，页面上只是"没数据"；
   ② 空面经（0 题）不报错，看着像"能跑"；③ 覆盖率另有 `evolution_report()` 走的是另一条正确的
   查询，指标一直有数，掩盖了地图本身是坏的。修完后 6 场面经才第一次都有地图。
   **教训**：同一份数据的多个读路径，要么共用一条 query，要么就等着它们悄悄分叉。

## 七、已知债务

1. **覆盖率低不是架构问题，是数据量问题**：55 题 7 卡，缺口 48 题。最高优先动作永远是
   把 freq≥2 的无卡题建卡（题目池「补齐高频无卡题」）。
2. **`data/kb.sqlite` 不进版本库**（.gitignore），意味着换机器要靠 `knowledge/` 重建卡片，
   但题目池/错题/掌握度会丢。要做的是导出/导入脚本（`scripts/export_state.py`），还没写。
3. **单机 SQLite 写并发上限**：目前单用户够用；多实例部署要换 Postgres + pgvector，
   换手点已收敛在 `embedder` 与 `get_conn()` 两个地方。
4. **FTS 与向量的一致性只在启动/显式调用时保证**，新增卡已补即时索引，但**改卡**（编辑要点）
   还没有即时重建向量——目前靠启动时 `text_hash` 变化兜底。
5. **空壳卡（已修，2026-10-30）**：`kb-bigdata-flink-002`（数据倾斜，高频 3 次）与
   `kb-bigdata-gen-001`（实时数仓）曾是"有卡无要点"——覆盖率算它们有卡，复习/评分/Agent
   却读不到内容，比"无卡"更危险（让人以为会了）。已走 `fill_card` 动作补成 9 条要点 + 4 条坑点，
   评测 `empty_point_hits` 从 8 降到 0。
   注意补内容会改变向量分布：hit@3 从 0.929 微降到 0.857（两张卡开始竞争同一批 paraphrase 查询），
   这属于语料变密的正常代价，不是回归。
6. **重复建卡的闸门只挡了一半（未修）**：`draft_cards` 只跳过"已经有待审草稿"的题，
   挡不住"卡已审批通过、但覆盖统计仍判它无卡"——那会再起草一次、人再批一次。
   2026-10-31 晚上的抽题测试就这么攒出 12 张重复卡（Agent 记忆 ×5、Spark Shuffle ×4、
   上下文压缩 ×3、RAG ×2），已用 `scripts/dedupe_cards.py` 归档到 4 张保留卡上
   （active 33 → 23）。根治要在起草前加一次 `_match_card` 判定，让"有卡就不起草"变成硬约束。
7. **混合检索的融合权重压不住 FTS 噪声（未修）**：卡片侧 FTS 用中文 bigram OR 展开，
   召回高但精度低；RRF 又给 FTS 和向量同权，结果 `hybrid hit@5 0.643 < fts 0.714`——
   融合反而变差。表现是 paraphrase 查询（"进程挂了内存里的东西还能找回来吗"→Redis 持久化）
   被一堆只共享个别 bigram 的长卡挤掉。方向：FTS 路加"命中 ≥2 个 bigram"的门槛，
   或给两路不同权重（向量 0.7 / FTS 0.3），再跑评测定参。
8. **对话台没有流式输出（有意为之，但代价真实）**：一轮 3~4 次 LLM 往返 + 1~2 次抽取，
   前端只能转圈等 20~60 秒。取舍是"把每步摊开"胜过"字一个个蹦"——不过长材料投喂时
   用户等待感明显，下一步该做的是**分阶段进度**（当前跑到哪一步），而不是逐字流。
9. **跨轮记忆只有 6 轮硬截断**（`HISTORY_TURNS`），超出的对话不再进上下文；也没有摘要压缩。
   会话很长时会"忘记最开始说过什么"。要做的是滚动摘要，别急着上向量记忆——先看真实会话有多长。
10. **`agent_tools._ingest_text` 里"起草卡"是尽力而为**：`draft_cards` 抛错只降级成
   `cards_drafted.error`，入池结论仍然返回成功。这是故意的（卡没起成不该否定入池），
   但汇报时模型可能只念"已入池"、忽略那句 error——前端 trace 里能看见，别只看总结。
11. **长材料仍会顶穿预算（未修，2026-11-05）**：用户粘 2 万字面经时，那 2 万字必须完整进
   prompt（截断等于让他白粘），单轮必然超 `CTX_SOFT_CAP`，只能记 `CTX_USER_OVERSIZE`。
   正解是"先落盘再引用 id"，把最坏一轮从 17k 压到 5k 以内。详见 `docs/复盘-上下文管理.md` 第 6 节。
12. **摘要只有"能注入"，没有"压得对不对"（未修）**：摘要质量没人抽检。最危险的是两条冲突的
   约束被压成一条（"只用 SQLite" 和 "可以引 Redis" 合并成一句），看似守住了信息，实则误导。
   要做的是抽 20 份人工打分，专盯「约束」段。
