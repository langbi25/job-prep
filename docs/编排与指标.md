# 编排的边界与指标（2026-11-15）

这一轮补两组东西，都是"平时不显形、出事才发现没有"的：

- **编排的边界**：模型、钱、时间、失败——四件原来全靠默认值兜着的事；
- **指标**：把三张台账拼成"哪里慢、哪里贵、哪里在失败"，并把三条新告警接上去。

编排主体（DAG 规划、角色工具权限、并行、断点续跑、critic 重跑）已经建好，这轮
不加新角色、不加新 DAG 能力——**先把边界立住**。理由在后面"没做什么"里写。

---

## 一、角色 → 模型路由

### 为什么现在才做

LiteLLM 网关刚进部署，模型切换从"改代码"变成"改一行配置"。但真正值得做路由的
不是"能切"，而是**四个角色的成本结构完全不同**：

- `researcher` 只做查证，输出短、调用次数多；
- `analyst` / `critic` 的输出直接决定答案质量；
- 全局换模型只能二选一，等于让查证也背上推理模型的单价。

### 配置与实现

```bash
# .env：只给需要的角色换模型，没配的角色回落 LLM_MODEL
ORCH_ROLE_MODEL='{"analyst":"deepseek-reasoner","critic":"deepseek-reasoner"}'
```

- `orchestrator.role_model(role)` 读环境变量，按原始串缓存解析结果，改完即时生效；
- JSON 写坏 → 退回全局默认，绝不让编排起不来；角色名拼错 → 出现在 `warnings` 里
  （静默忽略会让人查很久"我明明配了 reasoner"）；
- 模型透传到 `llm._chat_json(model=...)`：**只覆盖单次调用**，台账与 span 记的是
  实际模型，不是全局默认——两种模型单价差一倍，记错名字的钱是"错得看不出来"的那种错。

### 实测 A/B（同一目标，真实数据）

目标：「基于我的知识库和最近的面经，判断当前最薄弱的两个主题，给出这周该补什么、按什么顺序补」。

| | A 全 chat | B analyst/critic 用 reasoner |
|---|---|---|
| 步骤数 | 4 | 3 |
| 费用 | ¥0.1608 | ¥0.2417（**1.50x**） |
| 时长 | 60.6s | 81.5s（1.35x） |
| tokens | 42,223 | 47,538 |
| 答案字数 | 650 | 866 |
| critic 问题数 | 3 | 5（**更多**） |

分步费用差异（最能说明问题的一列）：

| 步骤 | A | B |
|---|---|---|
| researcher | ¥0.0642 | ¥0.0670 |
| **analyst** | **¥0.0104** | **¥0.1143（11x）** |
| writer | ¥0.0163 | ¥0.0219 |
| critic | ¥0.0226 | —（B 的 DAG 只有 3 步） |

**结论不是"reasoner 更好"，是"reasoner 更长、更爱下判断"**：

- B 的答案确实更有判断力——它反驳了"按频次补"的默认思路，改用"缺口等级"排序，
  并主动声明"排序对权重敏感"；
- 但 critic 在 B 里挑出的**无依据断言更多**（5 条 vs 3 条）：它把"有卡 kb-xxx
  含 9 个要点"这类上游没给过的细节写得理直气壮。更长 ≠ 更可靠。
- 默认因此**保持全 chat**。路由是"按任务开"的旋钮，不是默认更优解。

## 二、成本闸门

### 规则

```bash
ORCH_MAX_COST_CNY=0.5      # 单条计划的费用上限（元）
```

- 检查点在**每批派发前**，不打断正在跑的批次：杀线程会让"这一步做了什么"变成空白，
  而每一步都在花钱，留半截结果 + 明确的 stop 原因更有用；
- 中止的步骤标 `skipped` 而不是 `failed`：它们没跑过，标 failed 会虚报失败率；
- 终态 `capped` 单独成态，不和 `partial` 混：前者调预算/拆 DAG，后者修 bug。

### 实测（上限设 ¥0.01，必然触发）

```
status=capped  stopped_by=cost  cost=¥0.0288
s1 researcher done ｜ s2 analyst skipped ｜ s3 writer skipped
error: 成本闸门：本次已花 ¥0.0266，超过上限 ¥0.01
```

**第一版有个洞，实测才看出来**：闸门只拦步骤，`synthesize` + `critique` 照跑，
capped 之后又花了 ¥0.011（总费用比上限高 4 倍）——门只关了一半。修法是中止后
直接拼已完成步骤的原文、不再调模型（`_halted_answer`），复验后 ¥0.0397 → ¥0.0288。

**仍会超额，且要如实说**：闸门是**批次粒度**。一批 3 步并行出发时拦不住其中一步，
所以单批的花费可能直接越过上限（本例上限 ¥0.01、单批花 ¥0.0266）。要更精确只能
按调用计费做硬中断，代价是把"这一步做到一半"变成常态，不值。

## 三、截止时间

```bash
ORCH_DEADLINE_S=300        # 整条计划的墙钟上限
```

- 从**进函数**开始算（含规划），不是只给执行留满额；
- 批次超时取 `min(STEP_TIMEOUT_S, 剩余时间)`：截止时间是整条计划的承诺，
  不能因为"一批 3 步各自 180 秒"就被突破。

实测（`ORCH_DEADLINE_S=0`，进函数即过期）：

```
status=timeout  stopped_by=deadline  cost=¥0.0022（只剩规划那一次）
三步全 skipped，error：截止时间到：已超过 0 秒
answer：截止时间到，未做汇总。没有任何步骤跑完。
```

**兜不住的那一段**：规划本身（¥0.002~0.005）发生在闸门之前。要连它一起管，
就得先有个"要不要规划"的判断，那是另一个问题（见"没做什么"）。

## 四、步骤失败重试

原来单步失败 → 下游全部跳过，一次 429 就能让整条计划报废。现在：

- 只重试 **retryable** 的失败（`LLMError.retryable` / 并发等待超时 / 步骤超时）；
- 只重试**一次**（边际收益递减，无限重试是烧钱黑洞）；
- 重试时**收窄上下文**：上游结论砍半 + 工具往返次数减 1。原样重来往往还是同样的
  超长/超时，砍掉细节换一次机会更有用；
- `step.retries` 落库，指标里能看到"重试过几个步骤"。

不可重试的错误（400 参数不合法）原样重试必败，重试只是把一次失败变两次——这条有
单测钉住。

## 五、指标：把三张台账拼起来

`GET /api/obs/metrics?days=7`（`app/services/metrics_service.py`），数据源是
`llm_usage` / `tool_calls` / `agent_plans`，**不走 Phoenix/Langfuse**：
"今天花了多少钱、哪个工具在失败"不该依赖一个外部服务是否在线。

### 四条口径（比数字本身重要）

1. **失败行计入分母**。`llm_usage` 从 2026-11-12 起失败也落账，只统计成功行会把
   "调 5 次挂 2 次"算成 100% 成功。
2. **失败行的耗时不进成功调用的分位数**。等 30 秒才报错不是"模型变慢"。
3. **分位数用最近秩**，不插值。3 个样本的 P95 必须落在真实样本上，插值会造出
   一个不存在的耗时，看着精确其实误导。
4. **软停单列**。`capped` / `timeout` 不算失败，单独给 `soft_stop_rate`；
   `success_rate`（一次跑成的比例）与 `hard_failure_rate`（实现有问题的比例）
   两个都给。

### 真实数据（2026-11-15，窗口 7 天，含本轮验证自己产生的调用）

| 维度 | 结果 |
|---|---|
| LLM | 530 次调用，1 次失败（0.19%），¥4.22，P50 1.7s / P95 10.0s |
| 按场景 | console:assist 186 次 ¥2.09（P95 14.8s）｜**unknown 84 次 ¥0.76**｜memory_extract 106 次 ¥0.29｜console:auto 65 次 ¥0.37｜orchestrate:analyst 5 次 ¥0.16（**P95 41.1s**，reasoner 那一步） |
| 工具 | 298 次，真实失败 3 条（**1.0%**），另有 10 条策略拒绝，P95 157ms |
| 编排 | 24 条计划：done 17 / partial 2 / failed 1 / capped 2 / timeout 2，一次跑成 70.8%，软停 16.7%，均 ¥0.047、2.8 步 |

> `orchestrate:analyst` 的 P95 41 秒是个有用的数字：推理模型的延迟不是"贵一点"，
> 而是单步能顶别人一整条计划。这也是"默认不路由"的另一个理由。

### 指标一上线就抓到两个问题

**① 工具失败率是假的。** 13 条 error 里 **11 条是"只查不改模式拒绝写工具"**——
`remember` 6/6 全被拒、`draft_cards` 6 次里 5 次，全被记成 `status=error,
error_kind=failed`。这不是工具坏了，是闸门在工作。

修法：`agent_tools._denied` 返回机器可读的 `error_kind: policy_denied`，
dispatch 认这个字段（不再从文案猜），台账单列一类；指标里拒绝**不计入失败率**
（分母也扣掉，因为根本没执行），但仍出现在失败分类里——"模型总想写库"本身值得看。
历史行用 `db._ensure_columns` 里的幂等回填对齐，否则假失败还要再跑 14 天。

回填后同一窗口：298 次调用、3 条真实失败（**1.0%**）、10 条策略拒绝单列——
6.2% 里有 5 个百分点是假的。

**② `unknown` 场景吃掉 21% 的钱。** 84 次调用、¥0.76 没有 scene 标签，
说明还有调用点没打 `set_scene`。这是下一步要补的（不是这轮的范围），
但它现在**在页面上看得见**，而不是藏在总额里。

### 页面

新增「指标」页（`frontend/src/views/Metrics.vue`）：四张卡（今日成本/预算进度、
调用与失败率、P50·P95、编排一次跑成率）+ 按天成本柱 + 场景表 + 工具表（含失败分类）
+ 编排终态/步骤状态/步骤实际模型。与「可观测中心」分工：那边看单条链路的内部结构，
这边看整体趋势。

## 六、告警从 2 条到 5 条

新加三条，都带样本保护（样本太少任何比率都不可信，宁可不报）：

| 规则 | 触发 | 关键阈值 | 为什么需要 |
|---|---|---|---|
| `cost_spike` | 今日成本 ≥ 日预算 80%，**或** ≥ 近 7 日均值 3 倍 | `ALERT_COST_MIN_CNY=0.5` 绝对下限 | 只看预算会漏"平时 5 分、今天 2 块"；只看倍数会在几分钱时乱报 |
| `tool_failure` | 窗口内工具失败率 ≥ 30% | `ALERT_TOOL_MIN_CALLS=5` | 一个工具坏了整体错误率可能只有 5%；策略拒绝不计入 |
| `plan_failure` | 编排硬失败率 ≥ 50% | `ALERT_PLAN_MIN_PLANS=3`，窗口 180 分钟 | 编排稀疏，5 分钟窗口永远凑不满样本；capped/timeout 不算失败 |

复用原有纪律：没送达也落库（delivered=0）、冷却查表不查内存、判定失败只打日志。

## 七、没做什么，以及为什么

- **递归子编排**（步骤里再拆子计划）：失败面是指数级的——一步变一条 DAG，一条
  DAG 又有 5 步，出错后"哪一层花超了/哪一层幻觉"几乎无法定位。当前 5 步 + 4 角色
  已经够拆常见任务；真需要更深，该由人拆，而不是让模型递归。
- **按调用硬中断的成本闸门**：见"仍会超额"。批次粒度是有意选择。
- **critic 的 `retry_steps` 为空时不重跑**：A/B 两次 critic 都判 `ok=false`，
  但都没点名该重跑哪一步，于是 `_retry_round` 直接返回。**这是已知缺口**：
  critic 会挑错，但"挑错"和"可执行的返工指令"之间还差一环。下一步值得做的是
  让它必须给出 `step_id + 缺什么证据`，否则判 `ok=true`。
- **LLM spend tracking 迁到网关**：台账必须和 span / 评测 / 归因在同一张表里才查得动。

## 九、子 agent 打点与意图分析（2026-11-16 晨）

指标页上线后能回答"编排整体贵不贵"，回答不了两个更细的问题：
**四个子 agent 角色各自跑得怎么样**、**用户都在拿 agent 干什么**。这一轮补上。

### 子 agent 角色级打点

原始数据其实一直在落库，缺的只是聚合（不用改任何采集点）：
- `llm_usage.scene` = `orchestrate:{role}` → 每角色的 LLM 调用/费用/延迟/失败
- `tool_calls.source` = `agent:{role}` → 每角色的工具调用/失败/策略拒绝/常用工具
- `agent_plans.steps_json` → 每角色的步骤终态（完/挂/弃）、重试、实际模型、步费用

`metrics_service._agents()` 按 role 把三源拼成一张表（`GET /api/obs/metrics`
的 `subagents.roles`）。两个口径决定：
- **主控（plan/synthesize/critique）归 `main` 栏，不混进角色**：它们没有工具
  没有权限，一次 synthesize 的钱可能顶 researcher 查一下午，混进来"哪个角色
  贵"就答不准；
- **未知场景后缀（如 `orchestrate:typo`）直接丢弃**，指标宁可少一行也不能串账。

### 意图分析

`app/agents/intent.py`：意图枚举六类（查状态/分析诊断/写作产出/规划安排/
纠错复盘/其他），**规则关键词优先，LLM 兜底**。规则命中的目标是确定性的，
零成本零延迟；规则接不住的模糊目标才多一次几十 token 的分类调用。
分类在编排最前执行，挂在 `agent.intent` 子 span 上，费用算进本条计划。

三个设计决定：
- **单标签**。一个目标一个主意图——"平均每意图费用"在多标签下没有意义；
- **幻觉枚举不映射**。模型报出不存在的类别按 other 处理并带 `unknown:` 标记，
  "模型在乱分类"这件事必须在指标里看得见；
- **分类失败退 other + method=error**。意图是观测不是功能，绝不能让编排挂掉。

落库：`agent_plans.intent` 列（`db._ensure_columns` 补列，老行 NULL）；
emit `{"type":"intent"}` 事件；result 带意图；续跑沿用首跑的落库值不重分类
（两次分类结果不同统计口径就漂了）。

指标（`intents.items`）：按意图聚合条数/成功率/硬失败率/软停率/平均费用/
平均耗时/平均步数。**unknown 单列不回填 other**——"没分过类"和"分出来是
其他"是两回事，混着看会把兜底类占比抬高。

前端指标页新增两张卡：意图分析表、子 Agent 运行视图（角色/L/费用/P95/
工具/步骤/重试/主要模型/常用工具）。

### 没做什么

- **意图只打在编排上**。单 agent 聊天已有 skill 路由（turn_facts.skill 就是
  它的"意图"），再叠一层意图只会两个口径打架；
- **不做置信度落库**。LLM 自报置信度没校准过，存下来只会让人误信；
- **告警没加意图维度**。窗口内每意图样本太少（日均几条），按意图设阈值
  只会做误报机器，等意图样本积累够了再说。

## 十、入口限流与上游熔断（2026-11-16 晚）

指标页能回答"哪里慢、哪里贵、哪里在挂"，但拦不住两种事故：
**瞬时洪水**（1 秒 200 个请求打崩 2C2G）和**上游持续 5xx**（每个请求都耗满 90s
超时，把 4 路并发池占死，连带正常请求一起排队）。这两件事都不是"观测"能解决的，
必须在链路上加闸。补完之后，第 4 条 JD 里点名的"限流 / 熔断"才算真的落地。

### 限流：令牌桶两层，只拦 /api

`app/core/ratelimit.py`，挂在中间件最外层（先限流再验 token——洪水不该享受
"先解析 token 再拒绝"的待遇，鉴权也不该被刷爆）。

- **全局桶**：保护整机（SQLite 单写者 + 4 路 LLM 池都是硬约束）。默认 20/s，
  突发 40；本地一个人用永远打不满。
- **按 IP 桶**：默认 10/s、突发 20。内网场景主要是防前端 bug 造成请求风暴。
- **只拦 `/api/*`**：静态资源一次页面加载就是十几个文件，限流会把正常刷新打成 429；
  `/health` 更不能拦，否则 healthcheck 会把容器判死（这两条各写了测试）。
- 被拒返回 **429 + `Retry-After`**（按缺额算，不是拍一个固定值）。
- **空桶惰性回收**：每 256 次检查清一遍 300s 没动静的 IP，否则扫端口/伪造来源
  就是内存炸弹。

两个实现细节是踩出来的：
- **浮点容差**：`0.1s × 10/s = 0.9999999…`，刚好补满一个令牌时会把人在门外卡一次。
  比较带 `1e-9` 容差。
- **时钟回拨**：`_refill` 遇到 `now < last` 必须把基准挪到 now 并重算，直接 return
  会让桶永久空着（VM 挂起恢复时会发生）。

### 熔断：三态机，只认上游健康类失败

`app/core/circuit.py`，接在 `llm._chat_json` 的**并发池之前**：打开期间立刻抛
`CircuitOpenError`——不占池、不耗 90s 超时。这是"雪崩"和"快速失败"的分水岭。

四条边界各对应一次踩坑：
1. **429 不算熔断失败**。它是上游"你太快了"并带 `Retry-After`；算进熔断会把
   短期限流升级成整段不可用。
2. **400 不算**。我们请求体不合法，重试必败但上游是健康的——让它触发熔断等于
   "自己写错字把上游封了"。
3. **半开只放一个探针**。放开全部 = 刚恢复就被打回原形。
4. **按 `上游|模型` 分键**。换模型时互不牵连，旧键自然冷却。

退避：首次打开 30s，探针再失败则 30→60→120→240→300（上限），成功一次归零。
`CircuitOpenError` **刻意不是 LLMError**：它不是"这次失败"，而是"现在别试"，
不能被上层"retryable 就重试"的逻辑再送进去。

### 指标与配置

`GET /api/obs/metrics` 多了 `guards` 段（`ratelimit` / `circuit`），
**进程内计数、重启归零**，与上方按天窗口无关——前端卡头上写明了这一点，
否则会被误读成"近 7 天限流了 3 次"。

配置全在 `.env`：`RATE_LIMIT_*`（5 个）、`CIRCUIT_*`（4 个），
`RATE_LIMIT_ENABLED=0` / `CIRCUIT_ENABLED=0` 可整体关闭。
