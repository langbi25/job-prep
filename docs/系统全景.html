01一句话定位

它不是聊天机器人，是一套「知识资产 + 学习调度 + Agent 执行 + 自我诊断」的组合体。用户面对的只有一个对话框，但每次对话背后要回答四个问题：我到底记过什么（知识库）、我今天该练什么（SRS 调度）、这题我为什么答不好（错题与归因）、以及——这个回答为什么不好，系统能不能自己发现并改（回合事实 → 评测 → prompt 版本）。

所以系统的边界不是「对话」，而是一条从面经原件到复习卡、从一次失败回答到一次 prompt 改版的完整流水线。Agent 是这条流水线唯一的操作入口：它只能通过 17 个工具去动数据，而所有会破坏知识资产的写操作（建卡、改卡）都必须落到 agent_actions(pending) 等人工审批。

输入：非结构化材料

面经帖、复盘文档、项目经历、模拟面试录音转写。ingests 是状态机，抽完不直接入池——先过质量闸门。

中间：可计算的学习资产

题池 question_pool（129 道）+ 知识卡 kb_cards（37 张，markdown 为事实源）+ 题卡关系表。

输出：可验证的改进

复习排期、薄弱主题、作战地图覆盖率、改造方案、以及评测报告里的分数变化。

一句话记住架构：文件是事实源，SQLite 是可查询的投影；Agent 是唯一入口，审批是唯一写岔口；观测是本地主存、外部后端只是旁路视图。

02六层架构

六层从上到下依赖，任何一层都不反向调用。最上面是「谁在用」，最下面是「凭什么记得住」。层与层之间的接缝刻意做得很少——这是单人项目能长期维护的前提。

读法：上层依赖下层，虚线不存在——没有下层反向回调上层的情况，这也是它好测的原因（每层都能单独起）。
绿色= 有状态、有循环的运行时；紫色= 可替换的能力件（换模型、换检索、换 prompt 都在这层）；蓝色= 横切关注点，任何一层都能调，但不被任何一层依赖。

为什么这样分层，而不是「一个大 service」

三个接缝是被现实逼出来的，不是为了好看：

  1. 运行时与能力层分开：运行时管「一轮怎么跑、跑几段、什么时候停」，能力层管「拿什么材料、调哪个工具」。混在一起的后果是——想给评测脚本单独跑一次检索，得先伪造一整轮对话。
  2. 工具层只有一个合并点（harness_admin.all_tools()）：面板上看到的工具、模型能用的工具、技能白名单校验的工具，必须是同一份。早期手工拼两遍，出现过「面板显示停用了，技能白名单还能调用」的半停用状态。
  3. 观测是横切而不是一层：tracing.span() 是上下文管理器，任何地方都能开 span，但它不参与业务判断。所以观测后端挂了，业务零感知；反过来，业务逻辑里也没有一句「为了埋点」的分支。

03一轮对话的生命周期

用户在输入框敲一句话，到看见第一个字，中间有六个阶段。这张图同时画了主链和写侧——因为「这一轮发生了什么」和「这一轮被记成了什么」是两件事，而后者才是自进化能成立的前提。

流式与落账是解耦的：SSE 先把 stream_id 还给前端，对话在后台线程跑，结束时把账写完。所以「用户看到回复」和「系统记住这轮」之间有时间差，这也是为什么 turn_facts 的 feedback 允许事后回填。

三个容易被忽略但很关键的细节

写工具串行、只读并发 同一批 tool_calls 里，连续只读可以并发；一旦遇到写工具就串行，且必须过 MODE 闸门。 两个写工具并发落库，SQLite 直接 database is locked；更糟的是「只查不改」模式下照样写入。

04三条数据主线

整个系统只有三条主线。判断一个功能该不该做，先问它服务哪条线——如果一条都不服务，那就是装饰。

三条线的交汇点在 turn_facts：它既是 A/B 线的效果证据（这轮用了哪张卡、命中几条检索），也是 C 线的输入。这也是为什么这张宽表值得单独存在——分析的每个口径都从这里出发，不再现 join 六张表。

05部署与运行

单机部署，一台 Windows + Docker Desktop（WSL2 后端）。业务侧两个容器，观测侧一个可选的六容器栈。这不是「简化版」，而是有意为之的形态：SQLite 单写者决定了不可能水平扩，那么就把纵向做深。

为什么数据库用 named volume 而不是 ./data 绑定挂载：WSL2 的 /mnt/e 走 9p 协议，SQLite 的 WAL 在这种文件系统上会随机报 database is locked，写入吞吐还会掉一个数量级。代价是备份不能直接拷目录，得走容器里的备份脚本——所以才有那个 sidecar。

06数据模型（ER）

37 张实体表看着多，但按「回答什么问题」可以切成四簇。真正的主键不是 id，而是 trace_id——它把一轮对话在运行时、账单、观测三处的记录缝在一起。

四条虚线含义不同：实线= 数据库外键或显式引用；虚线= 逻辑关联但没有外键（受 SQLite 写入顺序限制，spans / turn_facts 都刻意不加 FK，避免并行写入时整行丢失）；右侧绿色虚线= 跨簇缝合键 turn_facts.trace_id。

07关键不变量

这些不是「设计原则」那种漂亮话，是已经付过代价换来的规矩。每一条后面都跟着一次具体的故障或一个具体的坑。

不变量含义违反后的真实后果
文件是事实源，库是投影 知识卡以 knowledge/**/*.md 为准，启动时 sync_all() 全量收编；技能与 prompt 同理。 手改 md 后被库覆盖，或者库改了 md 没变——两边漂移后，谁是真的就说不清了。
建卡必须人工审批 Agent 只能往 agent_actions(pending) 里写提案，审批通过才执行。 2026-10-31 一次性产生 12 张重复卡，就是「抽完直接入池、没人看」的产物。
SQLite 单写者 永远 --workers 1；工具写操作串行；连接按线程缓存复用。 多 worker 只会互相抢写锁，吞吐不升反降，还随机 database is locked。
span 本地主存，外部后端是旁路 调用树先落 spans，OTLP 导出失败不重试、不报错、不影响业务。 依赖外部后端 = 崩溃那几秒的调用树直接消失，而崩之前的树恰恰是唯一线索。
trace_id 是唯一缝合键 一轮对话的 spans / llm_usage / tool_calls / turn_facts 共用同一个 trace_id。 对不上账：页面上看到 3 次 LLM 调用，台账里 5 行，谁也解释不了差额。
降级必须留账 上下文超预算时的每一步降级都写进 ctx_traces.degraded_json 与 turn_facts.degraded_json。 「这轮为什么没给检索材料」变成玄学——而这正是回答质量下降的头号原因。
失败也要落账 llm_usage.status=error、tool_calls.error_kind、alerts.delivered=0 都会写一行。 只记成功时，「调了 5 次其中 2 次 429」在台账里根本不存在，看起来像「只调了 3 次、很顺」。
进料 ≠ 入集 失败会话自动进 data/eval_intake.jsonl，人工标注并 promote 后才进 golden。 未标注的素材混进评分口径，评测分数会随机漂移，门禁从此不可信。
测试不碰真实数据目录 conftest 统一 EVAL_INTAKE=0，DB 走临时文件。 跑一次测试就往素材池里倒几十条垃圾，还得手工清。

08观测、运维与门禁

观测这块的设计目标只有一句：出问题时，证据还在本机。所以数据分三层落，越往下越可靠。

第一层 · 本地 spans（事实）

一行一个 span，属性存 JSON 但关键维度单列（name / kind / duration_ms / status），所以「哪个工具最慢」是 ORDER BY 而不是解 JSON。

保留：普通 14 天；含 error 或 ≥5s 的 trace 整条留 42 天；超容量保险丝从最老的删，跳过受保护 trace。

第二层 · 全文 blob

prompt 原文、工具入参、返回值 gzip 后单独存，按内容 hash 去重；属性里只留 ⟦全文 N 字符⟧ 预览，点开才取。

实测：43 条引用里 1 条重复（约 2%）。所以这项的价值是「防」不是「省」——一旦父子 span 记同一段 prompt，重复会成倍出现。

第三层 · 旁路导出（视图）

OTLP 推到 Phoenix 或 Langfuse。失败不重试、不报错；对账口径用本地行数比后端条数。

Langfuse v4.79 三个坑：INIT 白名单、web 必须 HOSTNAME=0.0.0.0、改 env 需 force-recreate。

告警：判定在本地，推送到外面

后台线程每 ALERT_CHECK_SEC（默认 60s）扫一次滚动窗口，两条规则：

规则口径为什么这么定
error_rate窗口内 parent_id IS NULL 的 span 中 status='error' 占比 > 50%，且顶层调用 ≥ 10异常沿 span 链向上传播，一次失败会标红多层；拿全部 span 当分母，阈值形同虚设。顶层调用才是「一次请求」的单位。
slow_calls窗口内 duration_ms ≥ 10000 的 span 数 ≥ 3单次慢可能是网络抖动，三次以上才是趋势。

三条工程细节：冷却查表不查内存（重启不丢状态）；没送达也落库（delivered=0 + error，让「告警系统失联」本身可被发现）；样本保护（凌晨一两次失败不会触发 100% 告警）。报文支持 generic / 企业微信 / 钉钉三种，配好后 POST /api/obs/alerts/test 一键验收链路。

还软的部分（诚实清单）

项现状什么时候会疼
水平扩展单进程单写者，这是 SQLite 的物理边界，不是疏忽。多人同时用、或要做团队版时必须换 PG。现在不做是对的选择。
向量检索fastembed 内存索引 + 线性扫描。37 张卡没问题，千级开始延迟线性恶化（代码里已埋告警）。卡片过千，或换 embedding 模型时要整体重嵌。
token 计数按字符估算预算，未接 tiktoken。对中文偏差可接受但不精确。上下文卡在预算边缘时，估算误差会让「该降级」变成「请求超限」。
引用溯源检索命中带 file_path，但生成侧没有回引标注。回答里说「你记过 X」时，点不到那张卡，可信度打折。
评测规模77 golden + 12 任务，能防大回归，但统计置信度不足以支撑「提升 3%」这种结论。想量化某次 prompt 改版的小幅收益时，样本不够。
前端自动化无 E2E；当前环境的截图接口不可用（超 10MiB），UI 验证靠 node 断言 + 分包内容核对。改 Traces 这类重交互页面时，回归靠手工点。
自动进料闭环失败例自动进池已做，但 promote 到 golden 仍需人工标注触发。长期不跑 promote，素材池只进不出，等于没闭环。
去重收益跨 span 去重已上，但实测重复率仅 2%——价值在「防未来翻倍」，不在「现在省空间」。如果有人误以为它省了大量磁盘，会做出错误的容量规划。
最该警惕的不是「功能不够」，而是「口径分裂」。这个项目历史上最严重的两次事故——「待复习 3 张 vs 25 张」、「作战地图 31% vs 看板 25%」——都不是代码写错，而是同一件事有两个算法。所以现在所有聚合类指标都要求：唯一写入点 + 唯一读取口径。turn_facts 和 card_question_links 就是为这件事存在的。

10下一个瓶颈

按「现在最可能先坏」排序，不是按「看起来最酷」排序。前两项是真正会咬人的。

#瓶颈症状修法
1 自动进料停在半程 素材池只进不出。失败例躺在 data/eval_intake.jsonl 里，没人 promote 就永远不进 golden，C 线断在最后一公里。 加一个「待标注」队列视图 + 定期提醒；或按失败规则自动推荐候选。
2 向量检索线性扫描 卡片规模上涨后，每轮装配上下文的检索延迟线性增长；代码里已有告警但没换手。 embedder.search_similar 是预留的换手点，换 Chroma / sqlite-vec 都不动调用方。
3 预算靠字符估算 中英混排时估算偏差可达 20%+，导致降级判断滞后或过早。 接 tiktoken（或模型自带 tokenizer），把 token_budget.count_tokens 换成精确实现。
4 回答不可溯源 检索命中了哪张卡、哪道题，只存在账本里，回复正文里看不见。 生成侧回引 [[card_id]]，前端渲染成可点芯片 + 悬停预览要点。
5 任务级样本太少 12 条任务只够发现「整类挂掉」，发现不了「某方向退化 5%」。 扩到 30+ 条，并把真实会话里成功的复杂任务也纳入（不只失败例）。

明确不做的：多租户 / RBAC、HTTPS、PITR 与异地副本、镜像 CI 构建推送、限流。理由统一——单人内网使用，这些是成本而不是能力。判断标准是信号，不是清单：等真的有人要用、或者真出过一次事故，再补。

如果只能记住这张文档里的一句话：这套系统的复杂度不在「对话」，而在让每一次对话都留下可归因的痕迹——trace_id 缝合调用树与账单，turn_facts 把四类信号压成一行，degraded_json 记录每次妥协。功能可以少，痕迹不能断；痕迹一断，自进化就是幻觉。
