# 归因引擎 v1（P3）

## 定位

自进化闭环（评测 → 归因 → 分析 → 优化 → 再评测）的第二环：

```
run_evals（挂没挂）──→ attribution（为什么挂）──→ P4 优化执行器（改什么）──→ 再评测（真的好没）
```

## 设计决策

1. **规则先行，v1 不用 LLM**。六类根因对应六条确定性检测规则：可单测、可复现、零成本。
   LLM 归因（跨案例模式发现）留给 v2——规则先把全量日志压成结构化嫌疑列表，LLM 输入成本和幻觉面都小一个量级。
2. **多源接入，规则对字段缺失宽容**。三个来源：
   - 评测报告 `evals/results-*.json`（主路径）
   - Agent 运行轨迹 `runs` 表（`--runs`）
   - 上下文降级记录 `ctx_traces` 表（`--ctx`）
3. **闭合性**：所有失败要么归入六类，要么进 `unattributed`（judge 校准类）。"归不进去"本身是信号，不能悄悄丢。
4. **宁可少报不可错报**：轨迹归因只有 200 字 result preview 可用，只归因能确定的（异常/上限/预算裁剪/没调数据工具），不硬猜。

## 六类根因

| 规则 | 含义 | 典型证据 | 修复方向 |
|---|---|---|---|
| `retrieval_miss` | 检索未召回 | 期望卡完全不在返回结果；跨检索层双挂 | 补卡/补索引 |
| `low_confidence` | 召回低置信 | 召回但没进 top1；命中但 low 置信；无卡题误标高置信 | rerank/相似度标定/query 改写 |
| `no_data_reference` | 没引用 | must_mention 缺失（含具体缺哪项） | prompt 引用约束 + harness 校验重试 |
| `wrong_tool` | 工具选错 | 工具数不足；产出前没调任何数据工具 | 工具 description 改写 |
| `context_degraded` | 上下文降级 | 评分空上下文探针命中；ctx_traces degraded 非空 | 预算重分配/补主题卡 |
| `format_violation` | 格式违规 | JSON 解析失败；max_iters；预算违规被裁 | schema 约束 + harness 归一化 |

跨层证据是关键区分：**FTS 与 hybrid 双挂 → 知识缺口（补卡）；FTS 挂而 hybrid 好 → 分词问题（不用补卡）**。

## 用法

```bash
python scripts/run_attribution.py --runs --ctx --digest docs/归因-最新评测.md
python scripts/run_evals.py --skip-llm --attribute   # 评测后自动归因，摘要写回评测报告
```

## 产出结构（evals/attribution-*.json）

- `failures[]`：单条失败 → {rule, severity, evidence, suggestion}
- `clusters.by_rule / patterns`：按规则聚合 + 同案例共现模式（共现 = 单独修一类可能无效）
- `top_issues`：severity × count 排序的修复优先级
- `optimizer_input`：给 P4 的结构化输入——`ingest_targets`（补卡清单）/ `prompt_fixes` / `calibration_watch`
- `digest_md`：人读摘要（也是 P6 复盘中心的素材源）

## 实测（2026-11-11）

对最新 skip-llm 报告：57 案例扫出 12 条失败，Top1 = 检索未召回 ×10，
其中 5 条 hybrid/工具层双挂（进程挂了内存找回、数据倾斜、时间窗口切法、数据分布不均、Redis 断电恢复）
——都是真实知识缺口，`optimizer_input.ingest_targets` 已列出待补卡清单。
