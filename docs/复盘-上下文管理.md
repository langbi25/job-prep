# 复盘：给一个单机 Agent 项目补上上下文管理

> 对应题目：q-0063「随着用户对话轮数增加，Context 会撞上 LLM 的 Token 窗口限制，你会如何设计上下文管理策略？」
> 对应方案：`docs/plans/plan-20261105-000910-400-q-0063.md`　实施日期：2026-11-05
> 项目：job-prep（FastAPI + SQLite + 本地向量检索，跑在 2C2G 单机上）

---

## 1. 改造背景

这个项目有个对话台：一句"把这份面经收进去"，Agent 自己走完 存档 → 抽题 → 过闸门 → 入池 →
起草待审卡 → 跑作战地图，再汇报结果。它是我每天真在用的东西。

用久了发现两个具体问题，都不是"理论上会撞窗口"，而是**已经在发生的**：

1. **一轮之内就能把上下文撑起来**。一次投喂触发 8 次工具调用，每次工具结果截断到 2600 字，
   光工具结果就 2 万字符；再加上用户粘进来的面经原文（上限 2 万字）。实测一次请求
   17516 tokens —— 单轮就顶到窗口的 1/3。
2. **跨轮全靠一个常量硬截断**。`HISTORY_TURNS = 6`，只取最近 6 轮。问题是这个项目里
   很多话是说一遍就要一直生效的：**"这套系统只跑 2C2G，不要引入 Redis / 向量库"**。
   这句话在第 1 轮说完，第 8 轮就被滑出窗口了，而模型完全不知道自己违背了约束——
   从上下文里根本看不出来。

第 2 点比第 1 点更危险：撞窗口会报错，你能看见；丢约束不报错，你只会觉得"它今天怎么这么傻"。

## 2. 方案选型

**先纠一个前提**：我一开始以为要给"模拟面试"加多轮管理，翻代码发现 `mock_service` 是
**逐题独立评分**，压根不拼历史。真正的多轮在对话台。所以方案里"接入 interview_service"
这一条直接作废——**优化一个不存在的瓶颈是最容易犯的错**。

四个决策，每个都写清楚"不选什么、为什么"：

| 决策 | 选了什么 | 不选什么，为什么 |
|---|---|---|
| 历史怎么截 | 最近 6 轮必留 + **分级锚定**更早的轮次 | 不用纯滑窗：约束会被滑掉且无感知 |
| 锚定怎么判 | 字面特征（约束词 / 业务 id / 评分数字） | 不让模型每轮判一次"这轮重要吗"：太贵、且判不稳定 |
| 窗口外怎么办 | LLM 压成三段式摘要（事实/进度/约束），落库 | 不直接丢；也不用向量库做"长期记忆"——2C2G 装不起，且跨会话检索噪音大 |
| 检索要不要 | 复用已有 FTS + 向量双路，按需 Top-3 | 不把知识库全量注入：既贵又会让模型分心 |

**一个我改了三版才想清楚的点**：锚定不能只有一级。第一版把"约束"和"id/评分"同级锚定，
结果锚定轮自己也要占预算，第 17 轮起约束就被挤掉了（A/B 里"约束保留 16/20"）。
最终改成：

- **P0 约束**（必须/不要/记住/统一用…）：最近 4 条**永不丢**；
- **P1 引用**（业务 id、评分结论）：预算不够时从最旧的开始丢。

为什么 P0 只保护 4 条而不是无限：**保护必须有上界**。一段"每句都是要求"的对话如果全保护，
等于没有预算。第 5 条及更早的约束降级成 P1 公平竞争——这是取舍，不是 bug。

## 3. 实施过程

新增 `app/context/` 五层，每层可以单独测、单独换：

```
token_budget  →  window  →  summarizer  →  memory_retriever  →  assembler
   (计量)        (选)        (压)            (取)              (组装+降级+记账)
```

| 层 | 关键实现 | 说明 |
|---|---|---|
| `token_budget` | CJK×0.7 + ASCII×0.28 估算；`Budget` 按 system 15% / 检索 25% / 历史 60% 分 | 不装 tiktoken：它算 OpenAI 的切分，和 DeepSeek 不同源，装了也白装 |
| `window` | 分级锚定 + 预算内丢弃 | 保留顺序：最近 N 轮 > P0 > P1 > 普通轮 |
| `summarizer` | 三段式摘要落 `conversation_summary`，`covered_to_id` 防重复压 | 后台跑，下一轮生效 |
| `memory_retriever` | 复用 `rag_service.hybrid_search`；摘要只在会话内匹配 | 不做跨会话记忆 |
| `assembler` | 唯一出口，降级顺序 **检索 → 摘要 → 最旧轮次**，每轮写 `ctx_traces` | 降级必须可查，不然"为什么没给材料"是玄学 |

两个必要的外围改动：

- **轮内裁剪**（`enforce_inflight`）：ReAct 循环里工具结果一轮轮堆，这是最容易爆的地方。
  三档收紧：非末尾裁到 600 字 → 连末尾一起裁 → 全部裁到 200 字。
  "保护最后一条工具结果"是偏好不是保证——工具结果可以再取一次。
- **账本可见**：`ctx_traces` 表 + `console_messages.ctx_json` + 前端一行小字：
  `输入 1115 / 预算 12000 tokens · 含历史摘要`。鼠标悬停看分区明细。
  账本只写日志等于没有，界面上看不见就没人关心。

## 4. 踩坑

按"发现顺序"，都是真跑出来的：

**坑 1｜锚定轮自己也会被挤掉。** 第一版锚定是"留在 kept 里"就完事，但 kept 还要过历史预算这一关，
超了就从最旧的开始丢——而最旧的恰好是第 1 轮的约束。表现是 A/B 第 17 轮起"约束保留"从 20 掉到 16。
→ 改成分级：P0 由 `protected_ids` 显式保护，预算循环只动 P1 和普通轮。

**坑 2｜摘要被模型包成了 JSON。** 摘要表里存进去的内容是
`{"type":"json_object","content":"事实：…"}`。原因是 `_chat_json` 非 tools 分支一律带
`response_format=json_object`，DeepSeek 只好把整段话塞进一个 JSON 对象里。
→ 加 `json_mode=False` 分支。**prompt 要的是段落，就不该开 JSON 模式**；
顺带发现 DeepSeek 的 json_object 还要求 prompt 里出现 "json" 字样，否则 400（校准脚本踩到）。

**坑 3｜摘要写了，但永远不会被用上。** 这条最值得说。功能"实现"了、测试也过了，
但真实会话里 `summary_used` 恒为 false。原因：`_history` 只取 `HISTORY_TURNS*2 = 12` 条，
**正好等于窗口大小**，assembler 永远看不到被挤出去的消息，自然也轮不到摘要上场。
→ `_history` 改成取 40 条交给 assembler 挑。
结论一句话：**在取数层截断，等于替组装层做了决定**。单元测试测不出这种问题，
只有把账本摊在界面上、真跑一轮才看得见。

**坑 4｜摘要和原文重复计价。** 摘要注入后，被它覆盖的那几条消息还留在历史里，
同一段内容花两份钱（实测 history 538 + summary 198 tokens）。
→ 按 `covered_to_id` 把已覆盖消息剪掉，history 降到 166。

**坑 5｜极端场景下"守预算"和"守约束"会打架。** 20 轮里每轮都带约束词时，
预算压不住。这时的正确行为不是悄悄删约束，而是**如实记账超预算**：
标记 `CTX_KEEP_CONSTRAINT`，让 `ctx_traces` 里能看见。测试也锁的是这个取舍，不是"必须 ≤ 预算"。

**坑 6｜环境里没有 pytest。** 单机部署不想为跑测试加依赖。
→ 测试写成 pytest 风格函数 + `__main__` 运行器，`pytest tests/` 和 `python tests/test_context_budget.py` 都能跑。

## 5. 效果对比

同批对话、同一预算（12000 tokens）、20 轮，每轮助理回复约 1200 字：

| 指标 | full（全量拼接） | naive6（改前） | ctx（改后） |
|---|---|---|---|
| 第 20 轮输入 token | 17737 | 5318 | 7134 |
| 峰值 | 17737 | 5332 | 7152 |
| 均值 | 9322 | 4663 | 5551 |
| 超预算轮次 | **7/20** | 0/20 | 0/20 |
| 关键约束保留 | 20/20 | **6/20** | **20/20** |

单轮长物料（1 次投喂 → 8 次工具调用 × 2600 字）：**17516 → 7772 tokens（−56%）**，裁掉 7 条工具结果。

token 估算误差（对照 API 返回的 `prompt_tokens`）：三条探针 −34.7% / +11.9% / −7.5%，均值 −10%。
千字级样本稳定在 ±12% 内。**这个误差不用修**：软上限 12000 vs 窗口 64000，
10% 的估算误差换不回任何风险，真正起作用的约束是 soft_cap。

真实链路一轮的账本：`system 420 + summary 85 + retrieval 466 + history 130 = 1115 / 12000`。

**结论要诚实**：改后比"6 轮硬截断"多用约 30% 的 token（5318 → 7134），
换来约束保留从 6/20 到 20/20。这不是"省 token"的故事，是**同样的钱买更多有效信息**。
真要省，把 `soft_cap` 调到 6000 就行，代价是更早触发降级——旋钮在配置里，不在代码里。

## 6. 后续

还没做的，按优先级：

1. **长材料先落盘再引用 id**。现在用户粘 2 万字面经，这 2 万字必须完整进 prompt（否则白粘），
   于是单轮必然超预算，只能记 `CTX_USER_OVERSIZE`。正解是先把原文写进 inbox，
   prompt 里只放 `ingest_id` + 摘要，让工具自己去读——这一条能把"最坏一轮"从 17k 打到 5k 以内。
2. **摘要质量抽检**。现在只有"能不能注入"，没有"压得对不对"。该做的是抽 20 份摘要人工打分，
   尤其盯 `约束` 段有没有被合并错（两条冲突的约束被压成一条最危险）。
3. **模拟面试的报告链**。`overall_report` 现在把每题的答案截到 300 字再拼，题多了也会涨。
   逐题评分不进历史，但报告是一次性全量拼接，属于"另一条该接 assembler 的路径"。
4. **估算换真实**。DeepSeek 的 tokenizer 没有公开实现，但接了多模型后可以按 provider 拿 usage
   反过来做在线校准（现在只有离线三条探针）。
