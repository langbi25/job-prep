# 架构演进规划（容器化之后）

> **一句话**：容器解决的是"怎么交付"，之后的主轴不是"上微服务"，而是
> **进程职责分离 → 故障注入常态化 → 容量决策可测**。Postgres / Redis / K8s
> 全部由触发条件驱动，条件没到就不动——这不是保守，而是把"暂时不换"也变成
> 一个有数据支撑、可复核的结论。

本文对应三个阶段（A/B 已完成，C 于 2026-11-17 完成），其中**第 3 节的触发条件
表是核心**：它把架构决策从"感觉库有点大了"变成"库 10.3 MB / 上限 2048 MB、
写锁 P95 0ms、挡住率 0%"，每条都能在面板上看到、在代码里找到、在测试里钉住。

---

## 1. 现状拓扑（2026-11-17）

| 容器 | 职责 | 状态语义 |
| --- | --- | --- |
| `api` | 纯 HTTP 请求面（SSE 流、业务接口） | 无状态，`JOBS_ENABLED=0` |
| `worker` | 定时任务调度（`python -m app.worker`） | 有状态（锁 + 执行历史） |
| `web` | nginx：静态产物 + `/api` 反代 | 无状态 |
| `backup` | 每日冷备 sidecar | 有状态（写 data 卷） |
| `litellm` | LLM 统一出口（网关） | 无状态 |
| `mcp` | 对外 MCP 协议面（`profiles: ["mcp"]`） | 无状态 |

已实测的工程数据（都是本机实弹，不是估算）：

- **508 条单测全绿**；CI 门禁 = pytest + 前端构建 + compose 配置校验 + 镜像构建；
- 混沌演练：进程崩溃 **RTO 3.4s**（容器确认重启）、网关断连时 **80ms 快速失败**并自愈闭合；
- 压测拐点 **4~8 并发**；1 CPU 与不限配额吞吐几乎无差（291 → 294 rps @并发4）；
- 跨三进程并发写 SQLite，日志 **零** `database is locked`。

## 2. 三阶段路线

### 阶段 A：进程职责分离（已完成，2026-11-17）

把 job runner 从 api 进程里搬出来，api 变纯请求面。

- `app/worker.py` + `app/core/jobdefs.py`（api/worker 共享任务定义）；
- `PRAGMA busy_timeout=5000`（跨进程写排队，之前只有 span 连接设了）；
- `web` nginx 容器补齐交付形态；`RATE_LIMIT_TRUST_PROXY` 还原真实客户端 IP。

**为什么先做这个**：多副本、蓝绿、灰度全都以"api 无状态"为前提；先拆进程，
后面每一步都便宜。代价是多一个容器的内存（约 200MB）和跨进程写竞争——前者
可接受，后者已被 busy_timeout 兜住并实测验证。

### 阶段 B：故障注入常态化（已完成，2026-11-17）

容器带来的独有能力：kill 进程、断网、限资源都变成一行命令。

- `scripts/chaos_drill.py`：`kill-api` / `sever-litellm` / `cpu-limit`；
- 演练挖出 4 个真 bug/坑（`docker kill` 不触发 restart、命名空间内 kill PID1 被
  内核忽略导致假 PASS、`network disconnect` 丢内嵌 DNS、chat 响应体漏 `error` 字段）。

**结论性发现**：**瓶颈不在 CPU，在 SQLite 单写者**。这条直接决定了阶段 C 的
判定权重——扩容讨论的重心必须是存储层，而不是加核。

### 阶段 C：容量决策可测（本次）

`app/services/capacity_service.py` + `capacity_samples` 表 + `capacity_sample`
定时任务（5 分钟）+ `GET /api/obs/capacity` + 前端「扩容决策」卡。

## 3. 触发条件表（核心）

阈值全部是 `capacity_service.py` 里的常量（`evaluate()` 是纯函数，28 条测试钉住），
当前读数取自容器实测。

| 决策项 | 触发条件 | 当前读数 | 判定 | 触发后怎么做 |
| --- | --- | --- | --- | --- |
| **换 Postgres** | 库 ≥ 2048 MB<br>或 写锁等待 P95 > 200ms（≥20 样本）<br>或 被锁挡住率 > 1%（≥20 样本） | 10.3 MB<br>P95 0ms<br>0% | ✅ 未触发 | 先补仓储接口再换库，别让 SQL 散在业务里 |
| **api 横向扩副本**（前置 Redis） | `API_REPLICAS > 1`<br>（或库侧已触发 → 先换库） | 1 副本 | ✅ 未触发 | 先接 Redis 存限流桶/熔断状态，再起第二副本 |
| **垂直扩容（加 CPU）** | `load1 / 核数 > 1.0` | 0.56 / 12 = **0.05** | ✅ 未触发 | 先确认瓶颈真是 CPU：实测 1 CPU 与 12 CPU 吞吐无差 |
| **多机 / K8s** | 人工（需多机、多环境、跨机容灾） | — | ⚪ 人工 | 单机 12 核 + 文件卷，上 K8s 是负优化 |

三个"为什么现在不做"的具体理由：

1. **Postgres**：库 10.3 MB，写锁 P95 0ms，挡住率 0——换成网络数据库只会多一跳
   网络和一个运维对象。触发线定在 2 GB 不是"SQLite 撑不住"（它能到 TB 级），而是
   **运维动作撑不住**：冷备 + 校验 + 恢复演练这条链路在 2 GB 内是分钟级。
2. **Redis**：单副本时限流桶与熔断状态放进程内存是**语义正确**的。一旦多副本，
   每个副本各自计数等于阈值翻 N 倍——所以 Redis 是"多副本的前置条件"，不是
   独立目标。代码里把这条因果写进了 `replicas` 的 `action` 字段。
3. **多副本**：请求面不是瓶颈。压测显示并发 8 时吞吐反而下降（SQLite 单写者），
   此时加副本只会让排队更长——所以 `replicas` 在库侧触发时给出的建议是"先换库"。

## 4. 采什么、为什么这么采

| 信号 | 取法 | 为什么是它 |
| --- | --- | --- |
| 库文件字节 | `PRAGMA page_count × page_size` | 备份/恢复时长的直接来源 |
| WAL 字节 | `kb.sqlite-wal` 文件大小 | 写并发高时鼓起来，checkpoint 跟不上就是信号 |
| 写锁等待 | 独立连接 `BEGIN IMMEDIATE` 计时（预算 250ms） | 直接量化"别人要排队多久" |
| 被锁挡住 | 同上，等满预算仍拿不到 | 写事务已经长到影响别人 |
| 写入量代理 | 热表 `MAX(rowid)` 之和的增量 | 没有 `rows written` 计数器，rowid 上界是最便宜的代理 |
| load1 / 核数 | `os.getloadavg()` / `os.cpu_count()` | 回答"机器是否吃满"（容器内是宿主视角） |

**为什么主动探测而不是统计错误**：应用层的 `database is locked` 只在**等满
busy_timeout（5s）之后**才出现。等 3ms 就拿到锁的排队在日志里完全看不见，而那
正是"快该换库了"的早期信号。探测能测到这个区间。

**为什么采样放 worker**：api 是请求面，不该给自己挂定时器，重启还会断档；
worker 本来就是定时进程，且它读的是跨进程写锁，视角与 api 一致。

**为什么 5 分钟一次**：一次探测最坏占 250ms 写锁（只在真有长事务时），5 分钟
一次对业务无可感影响；而"日增速"这种指标的时间常数是小时级，用不着秒级采样。

**判定的两个防噪设计**（都是实测踩出来的）：

- **分布类信号要够样本**：P95 / 挡住率在 `样本 < 20` 时只给 `warn`，不给
  `triggered`。刚部署时两条样本里有一条排队就宣布"该换库"，是拿噪声当结论。
  （实弹验证：注入 4s 写锁后 P95 = 251ms、挡住率 50%，面板显示的是"先继续采样再判"。）
- **跨度不足 1 小时不报增速**：两个点差几分钟，除出来的日增速能差十倍，贴到
  面板上会被读成"明天就爆"。

## 5. 决策记录

| # | 决策 | 理由 | 代价 / 何时推翻 |
| --- | --- | --- | --- |
| D1 | job runner 拆成独立 worker 容器 | api 无状态是一切扩展的前提；调度崩溃不拖累请求 | +1 容器约 200MB；内存紧张时改 profile 按需启动 |
| D2 | 跨进程写用 `busy_timeout=5000` 而不是重试 | 写事务都是毫秒级，排队比"失败再试"更简单也更可预期 | 真有长事务时会等 5s 才报错——这是**期望行为**，错误应当暴露 |
| D3 | nginx 只做静态 + 反代，不上 SSR | 前端是 SPA，SSR 会引入 Node 运行时和一层缓存失效问题 | 若首屏 SEO 成为需求再评估 |
| D4 | 暂不换 Postgres | 见 §3 第 1 条 | 库 ≥ 2GB 或写锁 P95 > 200ms（≥20 样本） |
| D5 | 暂不上 Redis | 单副本时进程内状态语义正确 | `API_REPLICAS > 1` |
| D6 | 不做分布式锁 / 不上 K8s | 单机文件锁够用；单机上 K8s 是负优化 | 真实多机部署 |
| D7 | PITR 用"三层快照"而不是 Litestream 流式复制 | 库 10MB、快照 <2s，5 分钟粒度够用且零新依赖；Litestream 是 Go 二进制，为秒级 RPO 引入运维面不划算 | RPO 要求进到秒级、或库大到频繁快照撑不住 IO |

## 6. 什么会改变这些结论

架构不是"一次定终身"，这些信号出现时应该重新评估（都已接进面板或告警）：

- 面板 `postgres` 变 `triggered` → 排期换库（先补仓储接口）；
- 样本里 `lock_blocked_rate` 长期 > 1% → 先查慢事务（可能是某次批处理/迁移写法不对），
  不一定真要换库；
- `load/cpu` 长期 > 0.7 → 先看是不是压测/批量任务在跑，再谈加核；
- `API_REPLICAS` 要改成 2 → 必须同时上 Redis，否则限流阈值实际翻倍（这条比换库更容易被忽略）。
