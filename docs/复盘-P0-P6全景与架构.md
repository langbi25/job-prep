# 复盘：自进化 Agent 平台 P0~P6 全景与架构

> 写于 2026-11-11，P6 收官。本文是复盘中心的新用例素材：
> 覆盖 P0~P6 全部七期（含 P6 自身），含全景架构、数据流、设计决策与踩坑清单。

## 一、全景架构

整个系统是一个**自进化 Agent 平台**，六层结构，外层观测内层进化：

```text
┌─────────────────────────── 消费层 ───────────────────────────┐
│  前端 (Vue3)：知识库 / 模拟面试 / 学习计划 / 审批中心 / 进化报告 / 复盘中心  │
└──────────────────────────────┬──────────────────────────────┘
                               │ REST + SSE
┌──────────────────────────────┴──────────────────────────────┐
│  入口层：FastAPI 路由 · MCP Server (stdio + streamable HTTP)   │
│  · 内置 Agent (harness 工具循环)  ← 三条入口同一工具实现        │
├─────────────────────────────────────────────────────────────┤
│  进化闭环层（P2~P4，本项目的核心增量）                          │
│  ┌─────────┐    ┌─────────┐    ┌─────────┐    ┌─────────┐   │
│  │ 评测引擎  │ →  │ 归因引擎  │ →  │ 优化执行器│ →  │ 再评测   │   │
│  │eval_suite│    │attribution│   │optimizer │   │(gate 判定)│  │
│  └────┬────┘    └────┬────┘    └────┬────┘    └─────────┘   │
│       │ 双写          │ failure      │ prompt_versions 表      │
│       ▼              │ report       │ 晋级/回滚 + 快照交换      │
│  Phoenix 分析层       ▼              ▼                        │
│  (只读分析，不执行)   optimizer_input ──→ 候选改写 → eval gate  │
├─────────────────────────────────────────────────────────────┤
│  业务层：知识卡片 (SRS) · 题目池 · 模拟面试 · 学习计划 · 复盘中心(P6) │
│  · 审批闸门：所有写操作经 agent_actions(pending) 人审后生效       │
├─────────────────────────────────────────────────────────────┤
│  基础层：SQLite · FTS/hybrid 检索 · DeepSeek LLM · prompts/*.yaml │
├─────────────────────────────────────────────────────────────┤
│  观测层 (P0/P1，横切)：OTel 5 类 span → Phoenix/Langfuse       │
│  contextvars 场景标签 · 惰性装配（不配=零开销）                  │
└─────────────────────────────────────────────────────────────┘
```

跨业务通用化由 P5 保证：**specs/business_lines.yaml 是业务线唯一定义点**，
config 派生、工具 enum、标签、默认值、评测文件路径共六处消费点全部读 spec，
新增业务线 = YAML 加条目 + 灌数据，零代码改动，漂移由测试拦截。

## 二、七期演进与数据流

| 期 | 主题 | 一句话交付 | 关键不变量 |
|---|---|---|---|
| P0/P1 | 可观测地基 | OTel 5 类 span 埋进 6 处，接 Phoenix | 不配置 = 零开销；观测不拖垮主流程 |
| P2 | 评测双写 | 43 runs 本地评测双写 Phoenix | 本地是唯一事实源，平台只做分析层 |
| P3 | 归因引擎 | 六类根因规则 + 聚类 + optimizer_input | 每条失败都有归属（unattributed 兜底） |
| P4 | 优化执行器 | prompt 候选改写 + gate 自动晋级/回滚 | 文件是事实源，表是台账；文件状态与表状态一致 |
| P5 | 业务线 spec | 单点配置 + 六处消费点 + 漂移测试 | 唯一定义点，一致性靠测试不靠约定 |
| P6 | 复盘中心 | 文档→考点→建题→建卡走审批，前后端+Agent 编排 | 题目可入池，卡片绝不直写（一律过审批闸门） |

端到端进化闭环一条命令：

```bash
python scripts/run_evals.py --attribute --phoenix   # 评测 → 归因 → 双写
python scripts/run_optimizer.py --evaluate --yes    # 归因 → 候选 → 上机 → 晋级/回滚
```

复盘中心把第四条产品路径补齐：**建设过程/项目实践总结成 MD → 考点提炼 →
建题入池 → 建卡走审批 → 知识库变厚 → 下一轮评测**。知识资产化与进化闭环共用
同一套审批闸门与工具体系，Agent 通过第 9 个工具 ingest_retrospective 自动编排全程。

## 三、各期关键设计决策

### P0/P1 可观测：横切关注点走上下文，不走参数

- 5 类 span（AGENT/LLM/TOOL/RETRIEVER/CHAIN，OpenInference 语义）对齐
  Phoenix/Langfuse 的 UI 假设，换后端不用改埋点。
- 惰性装配：TRACING_ENDPOINT 不配 = 零开销，评测和测试不被拖死。
- 场景标签用 contextvars：观测不该污染业务函数签名。
- 坑：OTLP endpoint 必须带 /v1/traces；启动 20s 内导出 404 是就绪竞态。

### P2 评测双写：本地是唯一事实源，平台只是分析层

- 刻意不走 Phoenix client 的 run_experiment——那会让平台重跑业务逻辑，
  形成"评测第二执行路径"，评测结果必须只有一个出处。
- 坑密度最高的一段：upload?sync=true 返回 200 后立即 GET 可能 404
  （异步可见性窗口，官方 client 也栽）；404 路由返回 SPA HTML
  （HTTP 200 + text/html）必须验 content-type；inputs/outputs 不等长 422；
  experiment 不查重、成功 run 不可变（409 幂等）。

### P3 归因引擎：规则先行，LLM 后置

- 六类根因规则（检索未召回/召回低置信/没引用/工具选错/上下文降级/格式违规）
  + unattributed 兜底。v1 纯规则零 LLM，先把能确定性判断的判断掉。
- 跨层证据是核心价值：FTS+hybrid 双挂 → 知识缺口要补卡；FTS 挂而 hybrid 好
  → 分词问题不用补卡。同一句"没召回"，药方完全不同。
- 产出 optimizer_input（补卡清单/prompt 修复清单/校准观察名单），
  接口在 P3 设计时就为 P4 定好。
- 实测：57 案例 → 12 条失败，Top1 检索未召回 ×10（5 条真知识缺口进补卡清单）。

### P4 优化执行器：文件是事实源，表只是台账

- prompt = 源代码：改 prompt 就是改逻辑，所以要有版本表、生命周期
  （candidate/active/rolled_back/rejected/retired）和回滚。
- 确定性校验闸在 LLM 之后：占位符集合不变、花括号转义可渲染、
  schema 字段说明仍在、长度 0.5x~1.8x。违规候选落表 rejected，不碰运行文件。
- 晋级判据是 AND：scoped gate 通过 AND 基线对比无回归；评测中途炸也回滚。
- 坑：YAML block scalar |（clip）会补尾部换行导致往返不一致 → 用 |- 保往返。

### P5 业务线 spec：配置漂移让测试拦

- 唯一定义点 specs/business_lines.yaml，唯一读取入口 app/core/spec.py。
- test_spec 26 项三方漂移校验：spec↔config↔工具 enum↔评测数据。
- 顺手统一了三种不一致的默认 direction。

### P6 复盘中心：产物分层，闸门统一

- 四步流水线 ingest → extract_points → build_questions → build_cards，
  可分步跑也可 run_pipeline 一条龙；中途失败 error 落表不回滚已完成步骤。
- 产物分层：题目直入题池（题池本来就是待办池，面经抽题同款）；
  卡片绝不直写，一律经 draft_cards 产 create_card(pending) 进审批中心。
- ingest_retrospective 是第 9 个 MCP 工具（写工具受模式闸门），
  MCP/REST/内置 Agent 三条入口同一实现路径。
- 安全面：按路径导入限项目根内 .md，拒绝越界。
- 坑：prompt system 里的 JSON 示例必须 {{}} 双花括号转义，
  否则 .format 把 {"points"} 当占位符。

## 四、横切方法论（跨期复用的经验）

1. **单一事实源原则贯穿始终**：评测结果在本地（P2）、prompt 在文件（P4）、
   业务线在 YAML（P5）、记忆在卡片库——每类数据只有一个出处，其他都是派生。
2. **平台只做分析不做执行**：外部组件（Phoenix/评测平台）介入时，
   切断它能重跑业务逻辑的路径，避免第二执行路径。
3. **确定性优先，LLM 兜底创造性**：归因先规则后 LLM；改写先 LLM 后硬校验；
   格式类失败用确定性兜底修，不烧 token。
4. **写操作必须过人审**：卡片、记忆、prompt 晋级全部走审批或 gate，
   Agent 有提案权没有决定权。
5. **横切关注点不污染业务签名**：观测走 contextvars，配置走 spec，
   埋点用惰性装配。
6. **漂移靠测试不靠约定**：能被测试守护的一致性绝不靠人肉记住六个文件。

## 五、量化成果

- 全量回归 9 套件 79 项全绿（spec 26 + retro 19 + context 9 + mcp 6 +
  optimizer 5 + attribution 3 + tracing 3 + phoenix 3 + relations 5）。
- 评测 43 runs 双写 Phoenix，重推 0 条新 run（幂等闭环）。
- 归因 57 案例 → 12 条失败 → 5 条真知识缺口进补卡清单。
- 复盘中心实测：复盘文档 → 考点提炼 → 题目入池 → 卡片进审批，
  全链路真实 LLM 端到端可跑。
- 七期对应 7 个独立提交，全部推送远端，可按 commit 回溯每一期的证据。
