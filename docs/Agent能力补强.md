# Agent 能力补强：记忆 / 技能（含嵌套）/ 工具调度 / 编排（含续跑）/ 成本 / Harness 管理

> 写于 2026-11-12。补齐前先说清楚**原来的问题在哪**，否则容易变成堆概念。

## 一、缺口判断（改之前的实际状态）

| 能力 | 改之前 | 真实问题 |
|---|---|---|
| 上下文管理 | `context/assembler.py`：分区预算、固定降级序、锚定、摘要、轮内裁剪、账本 | 这块本来就比多数开源 agent 强，**不需要重做**。缺的是"记忆"没有独立通道接进来 |
| 记忆管理 | `memory_retriever` 只检索知识卡 | 知识卡是"我学过什么"，不是"用户是谁"。没有跨轮事实/偏好，用户一句叮嘱活不过 10 轮 |
| 工具调用 | 循环里 `for tc in calls: 直接调函数` | 参数不校验、全串行、不重试、结果硬截断（截了就再也看不到） |
| 技能调用 | 不存在。13 个工具平铺 | 每轮模型重新推导流程，同一件事两次步骤不一样，质量不可复现、无法评测 |
| 多 Agent | `multi_agent.py` 是"起草 + 审批"，不是编排 | 没有任务分解、没有角色分工、没有并行、没有汇总与自检 |
| 成本 | token 有统计，无单价、无台账 | 不知道一次技能调用/一次编排花多少钱，"值不值得"没法判断，也没法设预算闸门 |

## 二、十一个模块与关键取舍

### 1. 记忆层 `app/memory/`

```
store.py    写入与生命周期：版本、冲突消解、TTL、容量淘汰、审计
recall.py   读取与打分：词重叠 + 主题命中 + 时间衰减 + 置信度
manager.py  自动抽取（异步）+ 显式写入 + 上下文格式化
```

四条不变量：

- **同 key 只允许一条有效记忆**。用户说"目标岗位换成字节"，若只是追加，下一轮会同时召回"腾讯"和"字节"，
  模型就在两份矛盾上下文里编答案。新值替代旧值时旧行写 `superseded_by` 软失效——保留痕迹，不再参与检索。
- **低置信不覆盖高置信**（差 0.15 以上直接拒绝）。自动抽取会把"我同学在字节"记成"我在字节"，
  记忆被污染比记忆过时更难修。
- **相似值合并而非堆版本**（相似度 ≥ 0.82 视为同一件事的措辞变化）。
- **容量与过期都要有**：每 scope 上限 500 条，超了按"低置信 + 久未访问"淘汰；episode 90 天、task_state 14 天自动过期。

检索打分踩过一个坑：第一版把时间/置信度当独立加分项，结果**完全无关**的 query 也能拿
0.12(时间)+0.09(置信)=0.21 分越过阈值被注入——模型会把不相关记忆当前提，比没有记忆更糟。
现在相关性是"门"（为 0 直接判 0），时间/置信度只做修正系数。偏好类例外：只有几条且几乎总相关，
字面不中时给 0.30 基础相关性（`PREF_BASE`）。

### 2. 技能层 `app/skills/` + `skills/*.md`

技能 = **一组工具 + 分步 SOP + 验收契约**，不是换个名字的工具。文件即事实源（和 `prompts/` 一致）：

```markdown
---
name: weakness_diagnosis
when: 用户问"我哪里弱""接下来该补什么"
tools: [get_daily_brief, get_weak_topics, ...]
require_tools: [get_daily_brief]
risk: read
---
## 步骤 ...
## 输出契约 ...
```

命中技能后做三件事：SOP 拼进 system、**工具白名单收窄**、跑完用 `require_tools` 验收。

选择策略刻意保守：覆盖率 < 0.10 不选；第一名与第二名分差 < 0.03 不选。
理由：工具用错只是浪费一次调用，**技能选错会改写工具白名单**，把该做的事挡在外面且不易发现。
还加了停用 2-gram 表——第一版没有它，"今天天气怎么样"因为共享"怎么"选中了薄弱点诊断。

验收留了一个例外：本轮从长期记忆召回了内容时，缺 `require_tools` 不算失败。
实测第 2 轮"先复习哪几张卡"没调任何工具（靠第 1 轮抽取的记忆），答案依然准确——
**技能要求的是把事做完，不是必须调某个工具**。

### 3. 工具调度 `app/mcp/dispatch.py`

四个防护：

| 防护 | 做法 | 为什么 |
|---|---|---|
| 参数校验 | 轻量 JSON Schema（type/enum/required/maxLength），不引依赖 | 模型类型错了会在工具内部炸，报错是 `TypeError`，它看不懂只能瞎改；执行前拦下能一次改对 |
| 并发 | **按原序切段，连续只读并发（≤3），写操作串行** | 不能为并发打乱语义顺序；也不能并发写（建卡 A 与合并 B 可能互相影响） |
| 重试 | 只读工具重试 1 次；写工具绝不重试 | 写重试可能重复落库 |
| 可寻址 | 结果 > 3000 字落 `tool_results` 换 `ref`，返回 `_preview` + 提示 | 原实现 `json_safe(2600)` 截断后模型再也看不到后半段，只能重调同一工具——花两倍 token 换同一份数据 |

配套 `fetch_tool_result(ref, offset, limit)` 让模型"翻页"。截断从"信息丢失"变成"分页"。

### 4. 编排层 `app/agents/orchestrator.py`

```
plan（LLM 出 DAG，校验 id/依赖/环/步数）→ 拓扑调度（无依赖并行，≤3）
→ synthesize（合并而非拼接）→ critique（只找问题不改答案）→ 必要时重跑被点名步骤（≤1 轮）
```

四个角色不是提示词人设，是**工具权限 + 上下文可见性**的组合：

| 角色 | 工具 | 职责 |
|---|---|---|
| researcher | 只读工具 8 个 | 把事实取回来，不做判断（判断会污染下游） |
| analyst | **无工具** | 只基于上游结论推理（给了工具就会反复查证，实测连调 4 次 recall_memory，上下文被自己撑爆） |
| writer | 无工具 | 只写字（有工具的写手会顺手改数据） |
| critic | 无工具 | 只挑错（能改就等于给自己打高分） |

编排默认 `mode=assist`（只读）：一条 plan 里 4 步并行，任何一步写库出问题都难定位是谁写的。
编排的价值在分析类任务，真要改数据走单 agent + 人工审批更可控。

### 5. 成本层 `app/core/pricing.py`

**为什么要独立一张台账，而不是从 span 反推**：观测后端记的 token 是"运维视角"——
按 trace 散落、不折算钱、不归业务场景。回答"这个技能一次花多少钱""编排比单 agent
贵几倍"需要按调用逐行记账，且写入点必须在所有 LLM 调用的唯一咽喉（`llm._chat_json`），
否则总会漏掉某条路径（异步抽取就最容易漏）。

- 单价表按模型登记（CNY / 1M tokens，含缓存命中折扣价），`COST_PRICE_JSON` 可整体覆盖。
  未登记的模型按默认价估算并打 `estimated` 标记——**不返回 0**：0 元会让成本视图看起来
  "免费"，比算贵了更危险。
- 台账 `llm_usage` 每行一次调用：模型、场景、会话、轮次、trace_id、输入/输出/缓存 token、
  费用、是否估算、耗时。
- 编排的 plan 级费用 = 各步费用 + 主线程的规划/汇总/自检（`pricing.collect()` 收集器）；
  worker 线程里的步骤自己用 `msg["_usage"]` 记账，收集器收不到——正好不双算。
- 顺手修了个真隐患：`run_step` 原来读进程级 `llm.last_usage()`，三步并行时会互相覆盖，
  步费用串账。现在用量随返回值带回（`msg["_usage"]`），并行也准。

### 6. 向量召回 `app/memory/recall.py`

复用已有的 `core/embedder.py`（bge-small-zh-v1.5，ONNX，512 维）和 `embeddings` 表
（`entity_type='memory'`），不引入向量库。**融合是 max 取优，不是加权平均**：

```
rel = max(词面分, 向量分)      # 向量分先过绝对阈值
```

两路失效场景不重叠：词面擅长精确命中（用户真说了那个词），向量擅长改写
（"看懂代码却答不上" vs "学过但调不出来"，零 2-gram 重叠）。平均会让一路强命中
被另一路噪声稀释。

**最关键的一条：cosine 没有绝对零点，必须用绝对阈值。**
实测分布（8 条真实记忆 × 5 个 query）：

| 类型 | 例子 | cosine |
|---|---|---|
| 无关 | "今天天气怎么样" | 0.32 ~ 0.33 |
| 语义等价、措辞完全不同 | "看懂代码却答不上" vs "学过但调不出来" | 0.49 |
| 同主题改写 | "负载不均" vs "数据倾斜" | 0.55 |
| 直接命中 | "Flink 数据倾斜怎么优化" | 0.68 |

第一版凭感觉取 0.52，把 0.495 那条改写挡在门外——**向量通道存在的意义就是接住
词面接不住的改写，门槛定在"明显相关"之上等于自废武功**。现在取 0.45。

映射也不是线性归一：bge 分数挤在 0.3~0.75，归一后 0.55 只剩 0.22 分，再乘修正系数
就掉到阈值以下——"过门了却召回不到"比不过门更让人困惑。改成"过门即 0.22（刚好够格），
0.72 以上接近满分"。

索引增量维护（文本 hash 未变不重嵌）；模型加载失败在进程内永久降级到纯词面并记原因，
否则每次召回都要白等一次模型加载。返回结果带 `match`（lex/vec/both）与 `vec` 分值，
面板上"为什么想起这条"必须能答。

### 7. 技能嵌套 `skills/*.md` 的 `steps`

组合技能自己不写 SOP，只声明段落顺序：

```yaml
name: diagnose_to_cards
steps:
  - skill: weakness_diagnosis      # 只读：定位薄弱点
  - skill: gap_to_cards            # 写：针对主题补卡
```

执行时由代码分段串行，每段**重新装配上下文、重新收窄工具白名单**，段间只传结论摘要
（`HANDOFF_CHARS=800`），不传原始工具结果。

**为什么不是"技能 A 的 SOP 里写一句调用技能 B"**：模型在单轮里自己切 SOP 时，
工具白名单是静态的。A 的白名单里没有 B 的工具 → 报错；放开全局 → 等于没有白名单。
只有按段执行才能做到"第一段只能读、第二段才能写"。实测两段的工具集正是这样分的：

| 段 | 技能 | 实际调用 |
|---|---|---|
| 1 | weakness_diagnosis | get_daily_brief / get_weak_topics / recall_memory / get_top_questions / search_kb（**无 draft_cards**） |
| 2 | gap_to_cards | search_kb / get_top_questions / **draft_cards** / list_pending_actions |

只允许一层嵌套：3 段 × 3 段 = 9 次完整 agent 循环，成本和可解释性都会失控。
记账只记 parent 一条（子技能的表现留在 `segments` 里），否则一次组合会让
"技能调用次数"虚增 3 次。

### 8. 编排断点续跑 `orchestrator.resume`

```
读库 → 重建 PlanStep（含上次的 output/tokens/cost）
→ 已完成步骤的结论回填 Blackboard → 其余重置 pending
→ 复用原 DAG 执行 → 重新汇总 + 自检 → 更新同一行（费用累加）
```

三条铁律：

1. **复用原 DAG，不重新规划**。重规划会让已完成步骤的结论与新步骤的假设对不上，
   之前花钱查到的事实全部作废。
2. **回填的是结论，不只是 status**。没有回填，下游会收到"上游没有产出可用结论"，
   续跑等于重跑还多花一次汇总钱。
3. **费用与 token 累加不覆盖**。`base_*` 在加载时记下，只加"这次新增"的增量；
   直接覆写会把这条计划的历史花费抹掉。

`skipped` 的步骤必须重置为 pending：它当初被跳过是因为上游失败，上游恢复后它就该能跑。
同一 plan 用内存锁防并发续跑（SQLite 没有行锁）。允许续跑 `status=running` 的记录——
`_save` 只在结束时写库，库里出现 running 只可能是进程中途挂了，那正是最该续跑的情况。

### 9. Harness 管理台 `app/services/harness_admin.py`

改之前的问题不是"没有页面"，是**同一个事实有三份**：

- 工具清单在 `console_service` 和 `orchestrator` 里各手工拼一次
  `harness.TOOLS + agent_tools.SCHEMAS`。加一个工具要改三处，漏一处就是
  "面板上看不到，但模型能调"；
- 技能只能改文件，改完不知道有没有写错。`tools:` 里工具名拼错一个字母，
  路由选中它之后白名单被收成空集，模型什么都调不了，而日志里只留下
  "模型没调工具"——病因和现场隔着四层。

**工具只读不写。** 管理台没有"新建工具"接口：工具是代码（schema + 实现 + 读写属性），
能在这里加一个，就等于运行时能凭空长出一个能改库的入口。工具只能经代码评审进来。
技能本来就是文件，所以给它一个受控编辑器。

三个"全局豁免工具"（`remember` / `recall_memory` / `fetch_tool_result`）也收到这里。
它们原来是 console 里的一行硬编码，那是第三份事实。

**台账 `tool_calls`**：`dispatch.run_batch` 出口批量写一行/次，
连 `bad_json` / `invalid_args` / `unknown_tool` / `timeout` 这些早退路径也记——
参数错说明 schema 或描述没写清，超时说明工具本身慢，两类问题的修法完全不同，
混成一个 error 字符串就分不出来。和已有的 `mcp_calls` 不合并：那张是 MCP 客户端视角，
agent 调用可以不经过 MCP，MCP 也会被平台之外的东西直接调。

**体检的每条规则都对应一个真实故障**：

| 代码 | 触发条件 | 会出什么事 |
|---|---|---|
| `E_UNKNOWN_TOOL` | 工具名不在目录里 | 白名单收成空集，模型无工具可用 |
| `E_REQUIRE_NOT_ALLOWED` | 验收要求的工具不在白名单里 | 这一项永远不通过，技能永远"部分完成" |
| `E_EMPTY_BODY` | 正文空 | 注入后只有白名单，没有步骤 |
| `W_NO_WHEN` | 没写 when | 自动路由永远选不中，只能显式指定 |
| `E_STEP_UNKNOWN` / `E_STEP_NESTED` / `E_STEP_DISABLED` | 组合技能的段引用坏了 | 该段被静默跳过 |
| `W_NAME_MISMATCH` | name 与文件名不一致 | 下次改文件容易改错一个 |
| `E_NO_IMPL` | 有 schema 没实现 | 调用必报未知工具 |

分数 = 100 − 12×error − 4×warn。分数不代表功能坏了，代表"下一次改动更容易出事"。

**受控编辑的顺序是刻意的**：内存解析 → 单文件体检 → 备份 → 原子写 → 热重载。
有一条 error 就整份拒绝，不做"先存再提示"——存下坏版本，下次路由选中它时，
失败的现场（模型没调工具）离病因（白名单空集）太远。

**启停走文本级改 frontmatter**，不用 `yaml.dump`：dump 会重排字段、丢注释、
把长中文 when 折行；为改一个布尔值把整份重写，diff 会大到没法 review。

**路由试跑解释"为什么没选"**。选中与否只是结果，难查的是没选中的原因：
词元不够、分数不够、前两名打平、技能停用、组合技能缺段——五种情况分别给结论。

**实测抓到的一个真缺陷**：停用 `gap_to_cards` 后，组合技能 `diagnose_to_cards` 仍被路由选中，
但 `expand` 只展开出第 1 段——**只做了诊断、没补卡**，而答案不会自己承认漏了一半。
现在 `select` 用 `runnable()` 过滤：声明了几段就得能展开几段，缺段就不选，
由 `E_STEP_DISABLED` 让人去修。缺段跑一半比不跑更糟。

### 10. 版本管理与面板性能（2026-11-12 补）

管理台第一版能看能改，但有两个问题会在使用中放大：**改坏了只能靠时间戳猜**、
**面板随技能数变慢**。

**版本表 `skill_versions`**，与 `skills/.backup/` 是两件不同的事：

| | 备份目录 | 版本表 |
|---|---|---|
| 回答的问题 | "文件坏了能退回几分钟前吗" | "when 这一行是哪次改的、为什么改" |
| 内容 | 文件名 + 时间戳 | 正文 + 说明 + 来源 + sha |
| 能否 diff | 要自己按时间戳找两份文件 | 直接按版本号取 |
| 已知缺陷 | 同一秒两次保存会撞成一个文件 | — |

所以两者都留：备份是"绕过平台把文件改坏了"时的兜底，版本表是日常改动的账。

记录时机只有三个：保存、启停、回滚——它们都会改正文。**内容与上一版相同就不记**
（按 sha 判断），否则启停来回点会把历史刷满空版本，真正想看的那次改动被埋掉。

**v1 必须用改之前的正文。** 如果等第一次保存后才补 v1，历史的第一条就已经是改后的内容，
而"改之前长什么样"恰恰是最需要对比的那一份。因此保存流程是：
读旧文本 → 表里没有就先把旧文本记为 `v1(source=import)` → 写新文本 → 记为 `v2`。

**回滚是新版本，不是回退指针。** 文件是唯一事实源，把当前文件覆盖成旧正文之后必须再记一版，
否则历史会分叉：面板显示 v5、文件实际是 v2 的内容，下一次保存的父版本就错了。
现在回滚 v1 会产生 v3（`source=revert`），能再被回滚。

**diff 返回结构化行而不是统一 diff 字符串**：前端要按左右行号渲染红绿块，
字符串还得再解析一遍，解析错了没人会发现（看起来像 diff，其实是错位）。
相同段落超过 5 行就折叠成一行 `⋯ 未变的 N 行 ⋯`，只留改动前后两行上下文——
差异被大段正文挤出视口时，diff 等于没有。

**"磁盘内容不在历史里"要明说。** 手改 md、切分支、脚本生成都会绕过版本表；
不提示的话用户以为历史里有最新那份，而 diff 永远少一段改动，比没有历史更误导。
`version_board()` 比对磁盘 sha 与最新版本 sha，`dirty=true` 时抽屉顶部出现黄色警示。

**性能：先量再改。** 基线（5 个技能）`overview` 53.4ms，拆开看是三件事：

1. `overview` = `skill_entries` + `tool_entries` + `lint_all`，而 `lint_all` 内部又把前两个重算一遍
   ——同一份活干了两遍；
2. 每次 `get_conn()` 在本机是 **8.4ms**（connect + pragma + query + close，WAL 下 close 可能触发
   checkpoint），面板一次请求开了 7 个连接，50ms 花在连数据库上，比解析技能本身还贵；
3. 路由打分对每个技能重建一遍 doc 的 2-gram 集合，5 个技能 1.6ms 看不出，50 个就是 16ms，
   而且落在**每一轮对话**的入口。

对应三个改动：`snapshot()` 一次算齐（并让 `lint_all` 复用它）、`snapshot/board` 共享一个连接、
`gram → 技能名` 倒排索引（按 `load_all` 的 stamp 失效）。结果：

| 指标 | 改前 | 共享连接后 | 连接池后（第 11 节） |
|---|---|---|---|
| `overview` | 53.4 ms | 9.6 ms | **0.93 ms** |
| `lint_all` | 21.5 ms | 9.9 ms | **0.70 ms** |
| `registry.select`（每轮对话热路径） | 1.62 ms | 0.95 ms | **0.83 ms** |
| `route_preview` | 3.54 ms | 1.22 ms | **1.23 ms** |
| 面板整页（HTTP，旧 5 接口串行 → 新 1 接口） | ~78 ms | 17 ms | **9~11 ms** |
| 60 个技能时 `select` / `board` | — | 6.0 ms / 14.1 ms | — |

前端也从 5 个并发请求改成 1 个 `/api/harness/board`，旧的细分接口保留（外部调用与测试依赖）。
性能护栏写在 `tests/test_harness_perf.py`，断言的是**"干了多少次活"**而不是耗时：
快照只构建一次、整页只开一个连接、索引跨请求复用。时间断言在别的机器上只会乱红。

### 11. 对话流式与连接复用（2026-11-12 补）

**流式原来只做了一半。** `llm._consume_stream` 早就默认开启（`LLM_STREAM=1`），但它是
**内部消化**：边收边拼，拼完整条 message 才返回给上层，唯一产出是 TTFT 观测值。
所以模型明明在逐字吐，用户界面还在干等——一轮 6.5 秒，第一个字也要 6.5 秒才出现。

改成把 delta 转发出来后，端到端实测（真实 DeepSeek）：

| 场景 | 首字 | 整轮 | 事件序 |
|---|---|---|---|
| 单轮回答（无工具） | **780 ms** | 11 564 ms | `segment → delta×N → turn_end → done` |
| 带 6 次工具（4 轮 LLM） | **494 ms** | 6 512 ms | `turn_end` 序列 `[true,true,true,false]` |

首字提前 15~23 倍。事件协议（`POST /api/console/chat/stream`，SSE）：

| 事件 | 载荷 | 前端动作 |
|---|---|---|
| `segment` | index/total/skill/title/goal | 清空回复缓冲，显示"第 1/2 段 · 薄弱点诊断" |
| `delta` | text | 追加到气泡 |
| `tool` | tool/ok/error/cached | 往轨迹里加一行（实时显示"已调 N 次工具"） |
| `turn_end` | has_tools | **has_tools=true 就清空缓冲**（见下） |
| `done` | result（同 `/chat` 返回体） | 用完整结果覆盖：reply/trace/ctx |
| `error` | message | 气泡标红，已产出的文字保留 |

**最关键的一条：`turn_end(has_tools=true)` 必须清空已累计的 delta。** 模型调工具前常先说
"我先查一下记忆"，这段文字会以 delta 形式吐出来，但它不是回复。只有**无工具那一轮**的
内容才是最终答案（实测 `[true,true,true,false]` 验证了这个不变量）。不做这个清理，
用户会看到四段自言自语拼在一起。

**后台线程 + 队列**桥接两种模型：`chat()` 的事件是回调式的，SSE 生成器要的是可迭代序列。
选它而不是把 `chat()` 改成生成器，是因为对话循环里有 try/finally、span 上下文、早退分支，
重写成生成器会把"异常能不能穿过 yield"变成新的 bug 来源。`done`/`error` 由 job 的
try/except 保证必然出现，再加 5 分钟 idle 兜底防死等。回调抛异常一律吞掉——流式是体验增强，
不能打断正在跑的对话。

**连接池（`app/core/db.py`）** 是这轮性能提升最大的一处，也是改动最小的：

```python
class _PooledConn(sqlite3.Connection):
    def close(self): pass          # close 语义从"关闭"变成"归还"
```

全库约 140 处 `conn.close()` 分布在 36 个文件，逐处删要改一大片且 review 不动意图。
把 `close()` 覆写成归还 + `threading.local` 缓存，调用点零改动。三个必须处理的问题：

1. **上一个使用者忘 commit** —— 借出时 `in_transaction` 就 rollback。不回滚的话下一个
   使用者会读到别人的中间状态，且只在复用/并发时复现，是最难查的一类 bug；
2. **库文件被删重建**（测试/换环境）—— 借出前 `SELECT 1` 探活，失效就丢弃重建；
3. **Windows 句柄** —— 池里挂着临时目录的库连接，pytest 删 `tmp_path` 报 `WinError 32`
   （47 个测试一起挂）。收口在 `tests/conftest.py` 的 autouse fixture，不逐个改 10 个测试文件。

效果：`get_conn` 借出 + 查询 **8.4 ms → 0.003 ms**，面板从 17ms 再降到 9~11ms。

## 五、踩过的坑（都会复发，记下来）

1. **DeepSeek json_object 模式要求 prompt 里有 "json" 字样**，否则 400。
   无工具的 writer/critic/analyst 步骤必须 `json_mode=False`，否则整步失败。
   第一版写成 `json_mode=not tools`（空列表 → True），又错了一次。
2. **`for d in s.depends_on: s.depends_on.remove(d)` 会跳过下一个元素**，自依赖漏检，
   紧接着拓扑排序报出一个看不懂的"循环依赖"。清理依赖必须重建列表。
3. **"上游失败是否继续下游"** 第一版按"依赖已结束"放行，导致下游在没有输入的情况下硬跑。
   现在改为上游失败即 `skipped`——强行跑出来的东西是编的，比缺一块更危险。
4. **记忆检索阈值**：无关项靠时间/置信度也能凑够分（见前文）。
5. **进程级 `last_usage` 在并行下会串账**：编排三步并行时步费用互相覆盖。
   用量必须随返回值（`msg["_usage"]`）带回，不能用全局变量。
6. **线程不继承 contextvar**：异步记忆抽取在 daemon 线程里跑，不显式 `set_scene/set_session`
   的话，费用会落到 `scene=unknown`、没有会话归属，按场景聚合就缺一角。
7. **向量阈值不能拍脑袋**：第一版取 0.52，把真实相关的 0.495 挡在门外；而"过门却召回不到"
   源于映射区间取错（把 0.3~0.75 的分布按 0~1 归一）。阈值必须按实测分布校准，
   且要记录下这个分布——换了嵌入模型就得重新校准。
8. **记忆全写成 session 等于失忆**：抽取默认 `scope=session` 时，8 条记忆全是会话域，
   新开一个会话什么都不记得。现在按 kind 定默认（preference/fact → global），
   偏好类做了一次幂等回填。
9. **DEBUG 时用 `{k[:14]: v}` 打印字典会骗自己**：记忆 id 都是 `mem-20261112-10...` 前缀，
   切片后 key 相同，8 条被去重显示成 1 条，一度以为索引没建上。
10. **组合技能缺段仍会被选中**：`expand` 的"能展开几段就几段"用在展示上没问题，
    用在执行上是灾难——跑一半比不跑更糟，因为用户以为两段都做了。
    现在 `select` 先过 `runnable()`：声明几段就得展开几段。
11. **测试隔离不恢复会污染同批次的其它测试**：把 `registry.SKILLS_DIR` 指向临时目录后不还回去，
    后面跑的 test_skills 读到只有 demo_skill 的空目录，9 个用例集体报"技能全丢了"。
    真因（目录被换）和现象（技能消失）隔得很远，值得用 autouse fixture 兜住。
12. **`stamp` 只比文件名 + mtime 时，换目录会被判成"没变"**：两个临时目录里的同名文件
    在同一纳秒粒度内写入，指纹相同，路由就用了上一个测试的索引。
    现在 `_stamp()` 把目录路径也算进去，`load_all(force=True)` 额外清空索引。
13. **性能优化的第一嫌疑人是数据库连接，不是算法**：直觉上"面板慢"该优化循环，
    实际 8.4ms/次 × 7 次连接才是大头，Python 逻辑只占 14%。
    量之前不要动代码——否则会把 14% 优化掉，然后困惑为什么还是慢。
14. **CSS 里 `display:block` 救不了 grid 子元素**：diff 的折叠行放进 `display:grid` 的行里，
    只写 block 仍被塞进第一个 34px 列，渲染成竖排单字（"未变的12行"一字一行）。
    必须 `grid-column: 1 / -1`。这类问题功能测试永远抓不到，只能看一眼。
15. **flex 容器里的裸文字节点会被压成一字一行**：`<div class="segline"><span class=pulse/>薄弱点诊断
    <span>已调 4 次工具</span></div>` 里，文字节点自己成了 flex item，窄窗下被压成竖排
    （"薄/弱/点/诊/断"各占一行）。文字必须包进 `flex:1 1 auto; min-width:0` 的 span，
    操作数给 `flex:none; white-space:nowrap`，容器加 `flex-wrap: wrap`——
    挤压和换行是两种不同的失败，要让它换行而不是压扁。
16. **连接池在 Windows 上会咬测试**：池里挂着临时目录的库连接，pytest 清理 `tmp_path` 时
    `WinError 32`，47 个测试一起挂，报错信息（PermissionError）和真因（句柄没还）隔得很远。
    用 `tests/conftest.py` 的 autouse fixture 统一 `close_thread_conns()`。
17. **复用连接必须假设上一任没 commit**：`sqlite3` 默认在 `close()` 时回滚未提交事务；
    改成复用后这层保护消失，借出时不做 `in_transaction` 回滚，下一个使用者就会读到别人的
    中间状态——而且只在复用/并发时复现。
18. **流式回复里"先说再做"的文字不是回复**：模型调工具前常吐"我先查一下记忆"，
    它以 delta 到达，如果直接累积进气泡，一轮下来四段自言自语会拼在一起。
    判别依据只能是轮次结束时看它带没带 `tool_calls`，不能看文字内容像不像过渡句。

## 六、明确没做的（避免误以为已经覆盖）

> 2026-11-12 下午的 P0~P4 收口把下面四条做掉了（成本预算闸门、版本×运行联表、
> 单工具启停、流式断线续传），已移到第七节。这里只留仍然缺的。

- **向量索引的容量规划**：现在是全量加载后在 numpy 里算余弦（500 条以内毫秒级）。
  上万条要换成 ANN（faiss/hnsw），`embedder.search_similar` 是唯一改动点。
- **组合技能的条件分支**：`steps` 是固定顺序，不支持"如果上一步发现没有缺口就跳过第二段"。
  想要分支就该上编排层（那里有 DAG 和失败语义）。
- **续跑的步骤级重试上限**：`resume_count` 只统计次数，没有"连续失败 3 次就不再允许续跑"的熔断。
  现在靠用户看这个数字自己判断。
- **版本基线标记**：能选任意两版比差异，但没有"把某一版标记为基线、之后每次都跟它比"。
- **连接池本身仍无上限**：线程局部缓存意味着"每个工作线程最多一个连接"，
  没有 maxsize、没有 idle 回收。P4 加的是**上游并发闸门**（限制同时进行的重任务数），
  不是池的上限——多用户部署要换成有上限的池 + 归还超时。

## 七、P0~P4 收口：从"能跑"到"能管"（2026-11-12 下午）

上午那版的结论是"能力齐了，但管理是空的"。查真实使用数据时发现的问题比预想的严重：
技能一共跑过 10 次、5 个技能里 3 个零运行、5 个编排计划 3 个失败、复习停摆 16 天、
待复习 25 张卡而注入 prompt 的只有 3 张。**能力齐不等于用得上**，所以这一轮全部围绕
"让平台自己说清楚发生了什么"。

### P0 到期口径：一处 SQL，四个入口

原来「今日到期」在三处各算一次，注入 prompt 的那份写成 `srs_due IS NOT NULL AND srs_due<=今天`，
只算逾期、漏掉从未学过的新卡。结果是 prompt 说「3 张到期」而复习页有 25 张——
模型据此回答用户，那 22 张新卡永远进不了对话。

`review_service.due_stats()` 成为唯一口径，且区分两种"该做的事"：
新卡（`srs_due IS NULL`）要**学**，逾期卡要**测**。用 `COUNT(*)` 而不是 `len(due_cards(limit=100))`——
旧版卡片超 100 张会少报，而"少报"在复习场景里等于悄悄丢掉任务。

实测：`22 新 + 3 逾期 = 25`，最久逾期 16 天，prompt / `/api/daily` / 复习页三处一致。

### P1 为什么 60% 的编排会失败

不是 DAG 写错，是 **DeepSeek 的 `response_format=json_object` 要求 prompt 里出现 "json" 字样**，
否则直接 400。撰写/自检步骤没有工具、走了 json_mode，于是整步失败——而 `_fail()` 当时只报
`400 Bad Request`，把响应体（真正的错误原因）丢掉了。

两个修法都不是"绕过"，而是把信息留住：
- `_fail(resp, body)` 把响应体与请求摘要（messages 条数/字符数/tools 数/roles 序列）塞进 `LLMError`，
  并标 `retryable`（408/409/429/5xx）——不可重试的错误不该被重试三次；
- `_ensure_json_hint()` 在缺 "json" 时补一句声明。实测修复后连续 5 次编排全部 `done`。

同一个阶段还发现"补卡补错主题"：`draft_cards` 没传 topic 时按全池频次取前 50，
用户说「给实时数仓补卡」却起草出「归因引擎」。现在 topic 走双向包含过滤，
无匹配时**明确拒绝**（"题池里没有这个主题的题"），绝不退化成全池——

> 退化成全池不是"尽力而为"，是"用看似成功的输出掩盖"没找到"。

### P2 流式：先有续传，再谈长任务

SSE 断开（切标签页、锁屏）时后台任务还在跑，事件却全丢了。`app/api/sse.py` 抽出
`StreamBus`/`StreamHub`：事件带 `seq`，响应头 `X-Stream-Id`，重连用
`GET .../stream/{id}?after=<seq>` 补齐。锁只在块内持有——yield 时还持锁的话，
慢客户端会把 publisher 也堵住，表现成"后台任务卡死"。

编排实测事件序：`plan(2.1s) → step_start → step_end(8.3s) → … → synthesize → critique → done(20.6s)`，
2 秒内就能看到计划，而不是空等 20 秒。批量建卡（确认入库后自动起草）也接上了同一套：
`confirmed → draft_start/draft_end × n → done`，单张失败不影响后面继续。

### P3 版本 × 运行 × 成本：三张表终于对得上

原来 `skill_runs` 只有技能名，没有版本号——所有版本的表现被平均成一条线；
更糟的是 `tokens` 一直是 0（`record()` 没传），面板上"技能成本"永远显示 0 元。
**显示 0 元比显示贵更危险**：会让人以为这些技能免费。

- `skill_runs` 加 `skill_version`（NULL = 未进版本管理，不编造"第 0 版"）与 `cost_cny`；
- `chat()` 用 `pricing.collect()` 包住整轮，`_record_skills` 读 `snapshot()` 落账；
- `version_stats()` 按版本分组，`version_board()` 把 runs/成功率/耗时/费用挂到每个版本上；
- `ensure_baseline_versions()` 在启动时给没进版本管理的技能补一个 v1——实测 5 个技能里
  只有 2 个有版本记录，而 15 次历史运行**全部**没有版本号（都发生在基线建立之前）。
  这些历史记录不事后回填：无法证明那几次跑的就是现在这份正文，编造归属比留空更糟，
  面板上单独显示「另有 N 次运行发生在版本管理接入之前」。

顺带修掉一个隐蔽的口径问题：编排链路的 LLM 调用没设 scene，台账里 **49% 的调用挂在
`unknown`** 下，"编排比单 agent 贵几倍"这种问题根本答不出来。补上
`orchestrate:plan/step/synthesize/critique`、`card_draft`、`card_fill` 之后 unknown 归零。

实测（同一技能跨版本对比已可用）：

| 时间 | 技能 | tokens | 费用 | 版本 |
|---|---|---|---|---|
| 17:06 | diagnose_to_cards | 0 | ¥0 | — |
| 17:29 | diagnose_to_cards | 31088 | ¥0.0338 | NULL（基线建立前）|
| 17:44 | diagnose_to_cards | 29185 | ¥0.0330 | **v1** |

### P4 两个闸门：停用与预算

**单工具启停**：语义定成"三层同时生效"，因为只做一层都等于没做——
1. 工具清单（模型看不见）；2. 技能白名单过滤（技能限不住它）；3. **执行层拒绝**
（历史消息里的 `tool_calls`、编排的 `ROLE_TOOLS` 走这条路被拒，并在 `tool_calls`
台账记一条 `error_kind='disabled'`）。面板保留停用项，否则停用之后就再也开不回来。

实测停用 `get_top_questions` 后，模型被问「列出频次最高的题」时没有调用它，
而是诚实地回答"现有工具没有按出现频次统计题目的能力，检索返回的是相关度不是频次"。
**这正是想要的**：看不见 + 不编造，而不是拿别的工具凑一个假榜单。

**成本预算**：放在 `llm._chat_json` 这个咽喉上（所有调用都从这里过，包括编排 worker、
后台起草、记忆抽取）。放在各业务入口一定会漏掉某条旁路。默认 ¥5/天，因为事故形态是
"某一步反复重试把几分钱放大成几十块"，而个人复习一天 100 轮对话约 1 元。
关键细节：`pricing.record_usage` 每记一笔就 `budget.add_spend` 同步累加——
光靠"每 30 秒回库校准"的话，窗口内的连续调用会全放行，5 元的额度能花到 6 元。

**并发闸门**：`MAX_CONCURRENT_TASKS=3`（2C2G 单机上每个重任务 = 一个线程 + 一个连接 +
一个在飞的 LLM 请求）。**必须可重入**——对话线程里可能直接触发编排，不可重入时
外层占着名额等内层，直接死锁。这不是优化，是正确性。

### 验收

- 测试 198 → **223 passed**（新增到期口径 5、LLM 错误 7、主题补卡 5、对话流式 7、
  编排流式 4、建卡流式 6、版本联表 7、工具启停 5、预算/并发 7）；
- 真实链路：一轮命中技能的对话落账 `29185 tokens / ¥0.0330 / v1`；
- 预算面板：今日 ¥1.24 / ¥5.00，剩 ¥3.76，未触发闸门。

## 八、可观测作为自进化的基底（2026-11-12 晚）

### 问题：闭环的输入一直是"想象中的问题"

原来的自进化链是：手写 30 条用例 → LLM 自评打分 → 归因 → 改 prompt。
它有三个结构性缺陷，且互相放大：

1. **样本来源错**。评测集是手写的，不是用户真实问过的。优化出来的 prompt
   在"想象中的问题"上变好。实测时用户真实提了 82 条消息，一条都没进过闭环。
2. **信号类型错**。用 LLM 自评打分，而"评测通过"和"用户满意"是两件事。
3. **数据不全**。只有 trace（调用链），记了耗时和 token，没记"这轮到底好不好"。

结论：**自进化的上限由输入决定**。观测不厚，进化就是自嗨。

### 方案：一轮一行，四类信号分列

新表 `turn_facts`，一轮问答结束写一行（`(session_id, turn)` 唯一）：

| 类别 | 字段 | 作用 |
|---|---|---|
| 输入 | retrieval_n / memory_n / ctx_tokens / ctx_budget / dropped_msgs | 解释"这轮为什么难" |
| 过程 | llm_calls / tool_calls / tool_errors | 解释"它是怎么跑的" |
| 结果 | reply_chars / duration_ms / tokens / cost_cny / status | 解释"跑完是什么" |
| 质量 | feedback / followup_secs | **唯一的标签** |

前三类是解释变量，最后一类才是 label。把耗时当质量是最常见的错误——
它只能回答"快不快"，回答不了"对不对"。

**写入只有一处**（`console_service._chat_inner` 末尾），读取只认这张表。
散在六张表里现 join 的后果，就是又一次"待复习 3 张 vs 25 张"。

### 信号分级（决定归因权重）

1. `feedback = -1`：用户点踩。**最强证据**，不需要推断。
2. `followup_secs <= 90` 且未表态：答完一分半内又问，大概率没解决。
   **弱证据**，只能当辅因（用户也可能只是接着问下一个问题）。
3. 规则推断（空回复 / 工具报错 / 打到轮次上限）：是实现缺陷的证据，不是质量证据。

`PRIMARY_ORDER` 把强证据排前面。实测一行同时命中 `user_reject + run_failed`
时，主因取 `user_reject`——否则归因会被技术噪声带偏，改了三处 prompt，
用户的真实不满还在。

### 归因到动作：不是"失败 5 次"，是"改哪个文件"

`ACTION_HINTS` 把每条规则映射到一个**具体落点**：

| 规则 | 落点 | 处置 |
|---|---|---|
| user_reject | 看样本 | 判断知识缺口还是推理错误，确认后进回归集 |
| blind_answer | 改技能正文 | SOP 里写明"必须先调用 X 才能回答" |
| loop_exhausted | 缩小范围 | 降 top_k，或加"两次没查到就直说"的停止条件 |
| tool_error | 改工具 | 参数问题改 description，上游问题加降级 |
| ctx_squeezed | 调预算 | 提高预算或缩短材料；注意这会让"记不住上文"变成静默故障 |

### 回归用例只做半自动

`regression_candidates()` 交出可靠的部分——用户原话、当时调了什么、错在哪；
`must_mention` 和 `min_tools` **留空等人填**。

为什么 `min_tools` 不能填"当时调了几次"：实测有一轮问"复习哪些卡"，
路由却选中 `diagnose_to_cards` 并调了 6 次建卡工具。那 6 次正是出错的部分。
它和 `must_mention` 同理——是判断标准，不是观测值。

### 三条不做的边界

- **不回填历史**。2026-11-12 之前的 82 条消息没有 duration/tool_errors，
  硬凑出来的行会让"耗时分布"一半是 0 一半是真值。面板显示"自 X 起统计"。
- **长度不当质量**。`EMPTY_REPLY_CHARS=0` 只抓"完全没吐字"。
  40 字阈值会把"是，3 张"判成空回复——报警多了就没人看了，比没报警更糟。
- **弱信号不当主因**。`fast_followup` 排在最后，没有别的问题时才算数。

### 顺带修掉的一个真 bug

`test_dedup_same_args` 从偶发失败变成稳定失败，查下来不是测试问题：
批内去重靠两个并发线程互相看到 `cache`，并发时双方都判"未命中"，
同一个查询被跑两遍——**去重退化成概率行为**。

改成并发**之前**先按 `(name, args_hash)` 分组，每组只提交一次，其余复制结果并标
`cached=True`。跟随者连失败也复制：同参数再跑一遍大概率同样失败，白花一次调用，
还会让"工具报错"统计翻倍失真。连跑 4 次确认稳定。

### 验收

- 测试 224 → **247 passed**（新增回合事实 23）；
- 真实链路：一轮 `diagnose_to_cards` 落账
  `5 次 LLM / 6 次工具 / 2962 tokens / ¥0.0237 / 7.6s / 无标记`；
- 对那一轮点踩后，`failure_rule` 从 `None` 变 `user_reject`，
  面板"该改哪里"出现「看样本」建议，回归候选带出原话
  「今天该复习哪些卡？给我一个明确结论」；
- 面板：`/api/turns/quality|improvement|regression-candidates` 三个口径同源。

## 九、可观测的细度：从"有打点"到"能回答具体问题"（2026-11-12 夜）

第八节交付了 `turn_facts`，但那是**设计**。这一节是**体检**：把库打开，数清楚
到底记了什么、漏了什么，然后补掉真正的洞。

### 9.1 先说判据：细度不是"越多越好"

"打点越细越好"这句话一半对一半错。对的是一半：没有细粒度的调用级事实，
自进化只能在轮级结论上瞎猜。错的一半是：**存下来的每个字段都必须能回答一个具体问题**
——要么能进 `GROUP BY`，要么能进一条归因规则。否则它不是事实，是日志。

- 反例：把 prompt 全文存进事实表。表膨胀两个数量级，还是回答不了"改哪里"。
  需要看原文时去 `tool_results` / `console_messages` 按需取，别让事实表跟着内容一起涨。
- 正例：`finish_reason` 一个字段就回答"答案为什么短"——`length` 是撞了 max_tokens
  （要改预算），`stop` 是模型主动收尾（要改 prompt），`tool_calls` 是它还在查（要等）。

所以这一节的每个新增字段，都写了它要回答哪个问题。

### 9.2 体检结果（真实行数，不是设计意图）

| 表 | 行数 | 覆盖什么 | 当时的缺口 |
|---|---|---|---|
| `turn_facts` | 1 | 轮级四类信号 | 样本只有 1 条（表当日才建，历史不回填） |
| `llm_usage` | 194 | 每次模型调用 | **83 行 scene=unknown、turn=0、无 session、无 trace（43%）** |
| `tool_calls` | 130 | 每次工具调用 | 无 trace_id；46 行来自 `agent:researcher` |
| `ctx_traces` | — | 上下文分段与降级 | 只记"命中 3 条"，不记命中哪 3 条 |
| `mcp_calls` | 278 | MCP 客户端视角 | 与 agent 视角不合并（设计如此） |

最刺眼的是 `llm_usage` 里 95/194 行 `trace_id` 为空。查下来根因很明确：
`current_trace_id()` 直接读 OTel span context，而 OTel **默认没配 endpoint**，
于是永远返回空串。也就是说——**观测后端没开的时候，每一次模型调用都没有身份**，
三张事实表只能靠 `(session_id, turn)` 对齐，跨线程的调用（记忆抽取、编排 worker）
直接变成孤儿。这不是"细不细"的问题，是"能不能串起来"的问题。

### 9.3 修掉的四个洞

**① trace_id 走 contextvar，不再依赖 OTel 开关**

`agent_span` 进入时把 trace_id 塞进 `_TRACE`，`current_trace_id()` 先读它。
OTel 在场时两者同值，不在场时也有本地 uuid（32 hex，格式与 trace id 一致）。
配套加 `set_trace()`：后台线程不继承 contextvar，必须显式继承，
否则记忆抽取那笔钱永远归不到触发它的那一轮。

**② 失败的模型调用也落账**

原来 `record_usage` 只在成功后调用。后果不是"漏一个数"，而是**整类问题不可见**：
"这轮调了 5 次、其中 2 次 429 重试"在台账里只剩 3 行成功记录，看起来像"一次就成"。
现在失败走同一张表（`status='error'`，token 记 0——API 没返回 usage，不编），
并新增 `retried` 标记流式降级。归因新增一条规则 `llm_unstable`：
整轮成了但链路抖过 → 处置是改稳定性，**改 prompt 无效**。

**③ 轮级不再自己攒账，改成台账的投影**

实测抓到一次口径打架：某轮 `turn_facts.llm_calls=5`，同 (session,turn) 的
`llm_usage` 有 6 行——第 6 行是异步记忆抽取，它花同一轮的钱但不占主循环配额。
两本账各记各的，差值没人解释得了，而"这轮几次调用"正是判断"打到轮次上限"的依据。

现在 `record()` 里先按 `(session_id, turn) AND scene LIKE 'console%'` 聚合台账，
成功数/失败数/费用一起覆盖调用方传的值。**调用级是唯一事实源，轮级是它的视图。**
旁路（记忆抽取等）异步回填到 `llm_aux`，和主循环分开——混着记就说不清
"这轮绕圈了"还是"这轮刚好在抽记忆"。

**④ 工具台账补 trace_id**

`record_calls` 在主线程取一次 `current_trace_id()` 再写：工具执行在并发线程里，
contextvar 不跨线程，让每个 `_exec_one` 自己去取会全部拿到空值。

### 9.4 新增三个字段（连同它们要回答的问题）

| 字段 | 位置 | 回答什么问题 |
|---|---|---|
| `hit_ids` | turn_facts | 检索命中了哪张卡、分数多少、走哪条召回腿 → "哪张卡被检索到却从没被引用"（该改该删的依据） |
| `llm_aux` / `llm_errors` | turn_facts | 主循环几次、旁路几次、失败几次 → 区分"绕圈"和"抽记忆"、区分"内容差"和"链路抖" |
| `finish_reason` / `retried` | llm_usage | 为什么停、有没有降级重试 → 短答案的三种成因 |

### 9.5 覆盖率自检：先报分母，再报结论

所有"失败率 12%""点踩率 8%"都建立在分母正确之上，而分母是 `turn_facts` 的行数，
真实轮次在 `console_messages`。两者一差，面板上每个比例都是假的，而且**假得看不出来**
——漏掉的恰恰可能是失败最惨、根本没走到落账的那几轮。

`coverage()` 只做一件事：把这个边界报出来。分母取法踩过两个坑：

1. **按日期截断** → 建表当天的历史对话被算成漏账。实测 29 轮里 27 轮是建表前的，
   面板显示 6.9%，纯属虚报故障。
2. **按建表时刻截断** → 一轮里用户消息先落库、事实后落库，每轮把自己都排除了。

最终按**会话**判定：一个会话只要出现过事实行，它就在记账范围内，全部用户消息进分母；
从未出现事实行的会话不进分母，按建表时刻分成"升级前"（历史）与"升级后"（真漏），
两个数分开报。实测结果：记账范围内 2/2 = 100%，升级前 29 个会话，
升级后漏账 0 个——这才是可以拿去决策的陈述。

### 9.6 验收

- 测试 247 → **257 passed**（新增 10：台账覆盖调用方计数、失败调用可见、
  `llm_unstable` 让位于点踩、trace_id 往返、`bump_aux` 回填、hit_ids 落库、
  覆盖率三态）；
- 真实一轮（字节后端复习问）：`4 次 LLM / 6 次工具 / 18738 tokens / ¥0.0212 / 9.9s`，
  `turn_facts` 与 `llm_usage` 的 token、费用**逐位一致**，三张表同一个 `trace_id`；
  `finish_reason` 呈现 `tool_calls × 3 → stop`，能看出"查了三轮再收尾"；
- 面板新增"落账覆盖率"横条，排在四个比例**上面**——先看分母再看分子。

### 9.7 明确还不够细的（别以为已覆盖）

- ~~**没有 span 持久化**：`tracing.py` 默认 no-op，本地不存调用树~~ → **第十节补上了**。
  原判断的理由是"不想为了观测给每个请求加写盘"，这条理由站不住：观测的价值一半在事后，
  而事后往往拿不出一个后端。实测每 span 一次同步写约 0.2~1ms，一轮 30 个 span ≈ 10ms。
- **检索只到 id+分数**，没有"这条材料后来被引用了没有"——要做这个得比对回复文本，
  属于推断不是观测，先不做，免得又造一个"看起来有其实没有"的字段。
- **工具入参只存 hash 和摘要**，不存原文。面经正文动辄几千字，全存会把库撑大两个数量级。
- **没有时间序列 metrics**（Prometheus 那种）。现在全是 SQL 聚合，够用；
  等到需要"每分钟失败率曲线"再上。

## 十、span 持久化：把调用树变成"随时能翻的账"（2026-11-12 晚）

第九节结尾写了一句"没有 span 持久化，要看瀑布图得起 Phoenix"。用户当场回：
**"span 肯定要持久化的，你明知道不够细那你就继续细化。"** 这条要求是对的，而且
原判断的论据站不住——先把它推翻，再说怎么建。

### 10.1 为什么非要本地落库

原来 `tracing.py` 在没配 `TRACING_ENDPOINT` 时整个 no-op：不建 span、不记属性、不写库。
三个后果，一个比一个致命：

1. **事后查不了。** 出问题的通常是昨天那一轮。昨天没起 Phoenix，就什么都没有。
2. **崩的时候正好丢。** 观测本来就是为崩溃准备的，而崩溃那一刻 span 还在
   `BatchSpanProcessor` 的 5 秒队列里没导出去——最该看的那棵树没了。
3. **事实表只能靠 (session, turn) 对齐。** 三张表 join 一次就多一次口径不一致的机会，
   而且跨线程的调用（记忆抽取、编排 worker）直接变孤儿。

所以新原则：**本地 spans 表是主存，OTel 是可选旁路。**
没配后端也有完整数据；配了后端就多一份更好看的视图。

### 10.2 表结构：列和 JSON 的分工

```
spans(span_id PK, trace_id, parent_id, name, kind, session_id, turn, seq,
      start_ts, end_ts, duration_ms, status, error, attrs_json, events_json)
```

分界很明确：**要进 GROUP BY / ORDER BY / 建树的，必须是列**；其余进 JSON。

- 不用 OTel 自带的 SQLite exporter，就是因为它的属性全塞进一个 JSON 数组，
  查"哪个工具最慢"得先解 JSON。而 `name`/`kind`/`duration_ms` 是要直接排序聚合的。
- `attrs_json` 仍然保留：它是补充（哪条卡、多少分、什么 prompt），
  不是唯一入口。两者分工不能反。
- `seq` 是全局自增：ISO 毫秒精度下并发 span 大量撞车，只按时间排会出现
  "子 span 排在父 span 前面"这种看着像 bug 的图。

量级：一轮 29 个 span（实测 cs-span-5），每行 300~800 字节，一天 100 轮 ≈ 3MB。
保留 14 天，`prune_spans()` 收拾。

### 10.3 调用方零改动：LocalSpan 是鸭子类型

原来 `span()` 在 OTel 关着时 yield `None`，调用方全都有 `if s is not None` 保护。
那些被跳过的恰恰是最有价值的事实：工具输出长度、检索命中数、首 token 延迟、token 用量。
**"这些字段只有装了 Phoenix 才有"是本末倒置。**

现在 `LocalSpan` 实现 OTel Span 的最小子集（`set_attribute` / `add_event` /
`record_exception` / `set_status` / `get_span_context`），`span()` 永远返回真实对象。
OTel 开着就把属性双写过去，关着就只写本地。

结果：**17 处埋点、0 行改动**。所有 `if s is not None` 分支照常执行，只是现在真的记下来了。

### 10.4 选同步写，不选内存队列

直觉方案是"span 结束丢进 queue，单写线程批量刷"，理由是性能。这里刻意没那么做：

- **持久化的全部意义是崩溃可见。** 队列会重新引入丢失窗口（最后 200ms 的 span 没了），
  而那几毫秒恰恰是崩溃前最异常的调用。为了省 10ms 而丢掉最该看的数据，不划算。
- 实测 WAL 下每次 INSERT+commit 约 0.2~1ms，一轮 29 span ≈ 8~15ms，
  占一轮 18.58s 的 0.08%。这个量级不值得引入后台线程和关停竞态。

代价要写清楚：**busy_timeout 只给 500ms**，抢不到锁就丢这一行并计数
（`_STATS["fails"]`，暴露在 `/api/traces/health` 的最上面）。
宁可少一行观测，也不能因为观测把对话卡住——这条优先级不能反。

还有一个必须独立的点：**span 写库不复用 `db.get_conn()`**。
复用会撞上业务事务——`get_conn` 借出时发现 `in_transaction` 就 rollback（那是防腐设计），
而 span 是"随手插一行就 commit"，会把业务攒了一半的写事务提前结束掉。
**观测绝不能改变被观测对象的行为**，所以自己开一条连接。

### 10.5 上下文继承：三处线程池，一处都不能漏

contextvars 不下传 `ThreadPoolExecutor`。不显式继承的后果不是"少几个字段"，
而是**图在撒谎**：三个并行工具会变成三个独立的根，"并发执行"被读成"三次不相干的调用"。

- `dispatch.run_batch`：并发前 `capture()`，每个子线程开头 `adopt()`；
- `orchestrator._execute`：DAG 并行步骤同样处理，否则一条编排会显示成 N 次独立任务；
- `memory.extract_async`：只传 trace_id 不够——trace 相同但 parent 为空，
  `memory.extract` 会变成孤儿飘在根旁边。实测抓到过一次，改成传整份上下文。

`_end()` 里还加了一步**回填 session/turn**：根 span 是在 `chat()` 里开的，
而 session_id 和轮次号要等 `_chat_inner` 数完历史消息才知道。不回填的话，
调用树最顶上那行的 session_id 永远是空，按会话查树直接查不到自己那一轮
（实测踩到过，`agent.console` 的 session_id 是 NULL，子 span 却有）。

### 10.6 属性预算：裁掉内容，留住维度

"打点越细越好"这句话一半对。对的一半：没有细粒度事实，自进化只能在轮级结论上瞎猜。
错的一半：**存下来每个字段都必须能回答一个具体问题**，否则它是日志不是事实。

所以 `attrs_json` 有两道闸：

1. 单值 2000 字符（与 OTLP 侧一致）；
2. 整条 6000 字符。超了先保**维度键**（`tool.name` / `llm.scene` / `skill.name`
   这类会进 GROUP BY 的），剩下的按体积**从小到大**填。

按体积而不是按重要性排序，是因为重要性判断不了、体积能：小字段通常是维度
（条数、布尔、模型名），大字段通常是内容（prompt 全文、工具返回）。
填到最后没位置的必然是那几个大块头——正确。

裁了什么都写进 `_dropped_keys` 属性。**不写的话，"属性少"会被读成"没打这个点"**，
然后有人去补一个已经存在的埋点。

### 10.7 补的四个字段（连同它们要回答的问题）

| 字段 | 位置 | 回答什么 |
|---|---|---|
| `llm.finish_reason` | llm.chat | 答案为什么短：`length`=撞 max_tokens（改预算）/ `stop`=模型收尾（改 prompt）/ `tool_calls`=还在查（等它） |

## 十一、采样、全文入参、可折叠的树（2026-11-12 深夜）

### 11.1 先说清楚"采样"是什么，以及这里为什么不采

采样（sampling）是"只留一部分 span"。两种做法，差别在于**什么时候决定留不留**：

- **head-based**：span 一开始就决定（比如只留 10%）。成本最低，但决定的那一刻
  **还不知道这次调用会不会失败、会不会很慢**。所以按比例随机留，必然按比例丢掉
  一部分错误和慢调用——而观测的价值几乎全在长尾。
- **tail-based**：等 span 结束，看结果再决定（错的、慢的全留，正常的按比例留）。
  代价是必须"先把全部数据收下来"才有得选。

所以"失败和慢的永远不被采到"这件事，只发生在 head-based 上，而且它是**缺陷不是特性**。
本项目现在**没有采样**：`spans` 100% 落库。真到写盘瓶颈时也只会上 tail-based，
判据写在 `prune_spans` 的注释里。

实际起控量作用的不是采样，是**分级保留**：

| 类别 | 保留期 | 容量清理时 |
| --- | --- | --- |
| 普通 span（ok 且 < 5s） | 14 天 | 先从最老的开始删 |
| 错误 span（status=error） | 42 天 | 跳过 |
| 慢 span（≥ 5s） | 42 天 | 跳过 |

两档保留期而不是"错的永久留"：永久保留等于把证据变成债务，表无界增长后查询先垮，
那时候连新问题都查不了。3 倍是"够看清来龙去脉"和"不撑爆库"的折中。
被容量挤掉的条数记在 `_STATS["pruned"]`，健康接口可见——少了 trace 时，
得能区分"没采"和"被容量挤掉了"。

### 11.2 入参全文：换一张表，别挤属性预算

原来的做法是 `attrs_json` 里直接截 2000 字符。三个后果都不对：

1. **丢证据的顺序反了**。属性表有预算（8000 字符），一段 8000 字的 prompt 进去，
   为了腾地方会把 `tool.name`、token 数这些**维度键**挤出去——查询靠维度，内容只是线索。
2. **页面会卡**。一轮 30 个 span，光 prompt 就几百 KB，跟着树一起传给前端，
   每次点开 trace 都像下载文件。
3. **没法压缩**。同一份 system prompt 每轮都带，塞在 JSON 里既冗余又难单独压。

现在的分工：

```
spans.attrs_json    维度 + 800 字预览 + "…⟦全文 11819 字符⟧" 标记
span_blobs(span_id,key,text_len,gz_len,gz)   全文，gzip 存 BLOB
```

几处必须说清的判断：

- **阈值 800 是"展示上限"不是"存储上限"**。超过就转存全文，属性里留预览。
  预览里预留 40 字符给标记，保证"预览+标记"仍在 800 以内——否则
  `_shrink_attrs` 会二次裁剪，正好把标记切掉，前端就再也点不开全文。
- **`_blob_keys` 自述**。哪些键有全文写在属性里，前端读清单而不是猜正则。
- **预算裁掉的键，全文还在**。`_shrink_attrs` 裁的只是预览那一行，
  blob 里那份不受影响——裁证据和裁索引是两件事。
- **单条熔断 400k 字符**，但 `text_len` 记的是**原文**长度。只记截断后的长度，
  事后就分不清"原文就这么长"和"我们只存了一半"，这决定了要不要去别处找完整数据。
- **顺手放开了 5 处手写截断**（`dispatch` 的 `[:1200]`/`[:1000]`、`gateway`、
  `harness`、`console` 的 `[:2000]`）。那些截断写在 tracing 之外，等于
  在全文入库之前就把它切了——最典型的"埋点看着有，实际只有 1200 字"。

代价：gzip 后 44,932 字原文占 25,777 字节（1.7×），一轮 9 个附件约 25KB。
一天 100 轮约 2.5MB，14 天 35MB——比"看不到 prompt 原文"便宜得多。

### 11.3 树要能收起来

原来的瀑布图是**永远全展开**的一列行：16 个 span 就要占满一屏，30 个 span 时
滚动条比图还长，看不出层次。现在两级交互拆开：

- **点 `▸` 折叠/展开这棵子树**（结构）
- **点整行看属性与事件**（内容）

这两件事合成一个点击的话，想看某个 span 的属性就会顺手把它的子树展开，
或者反过来——拆开才有"先看形状，再看细节"的节奏。

配套的四个细节：

- **折叠后必须能看见"藏了多少"**：`+11` 是子树里的 span 数，
  带错误时额外标 `2!`。只折不给数，折起来就像"这步本来就没子步骤"。
- **引导线**：按 depth 画竖线，光靠缩进在多分支时看不出"嵌在第几层"。
- **只看错误分支**：把所有"整棵子树都没错"的节点收起来。一轮 30 个 span
  通常只有 1~2 条路径出错，平铺着看得靠肉眼扫。
- **详情区自己滚**：`max-height: calc(100vh - 240px)`。窗口不高时（768px 笔记本常见）
  上面 header + 列表已经吃掉大半屏，树必须能在自己的框里滚到底。
  同时单个属性值也封顶 150px——一条 300 字的 JSON 会把整页撑高十几行。

全文面板放在详情区**顶部**而不是树下方：点开就在视野里，不用先滚到底再滚回来。

### 11.4 验收

- 测试 273 → **281 passed**（新增 8 个：全文往返一致 / 短值不进附件 /
  执行中补的 output 也有全文 / 预算裁掉后全文仍在 / 单条熔断 / 缺失返回 None /
  清理保留错误与慢 / 压缩率与按 key 的容量账）；
- 真实一轮：16 span / 7.9s / 9 个附件 / 44,932 字 → 25,777 字节（1.7×）；

- 页面实测：折叠子树（`+11`）、全部展开/收起、行内属性、全文面板（1,910 字符全文）；
- 全量测试前后真实库 spans 97 / blobs 9 不变。

- ~~**事件属性仍然截断在 800**~~：`add_event` 里的长值不走 blob。
- ~~**树里没有搜索/过滤**~~：30 个 span 靠折叠够用，500 个就得上过滤框。

  保留粒度从"单行 span"改成"整条 trace"，等价于 tail-based 的判定单位。


## 十二、去重、事件全文、树内搜索、按 trace 保留（2026-11-13 下午）

第十一节列了四条"还不够"。这一节逐条收掉，顺带把"复习"意图的路由修了。

### 12.1 跨 span 去重：正文按内容收敛，引用各留各的

**问题**：只要有一层 span 把父层的入参再记一次，或者同一份工具返回被 CHAIN 与 TOOL
两层各记一次，同样的字节就会成倍重复。gzip 只省体积，不省"再压一遍、再存一遍、
读的时候再解一遍"。

**做法**：正文按 `sha256(正文)[:32]` 收进 `blob_texts`，`span_blobs` 只留 `hash` 引用。

```
blob_texts(hash PK, text_len, gz_len, gz, created_at)      -- 一段文本一份
span_blobs(span_id, key, text_len, gz_len, gz, hash, ...)  -- 一个 span 一条引用
```

三个必须说清的细节：

- **`text_len` 记在两个地方，含义不同**。`blob_texts.text_len` 是"实际存下来的字符数"，
  `span_blobs.text_len` 是"这一份原本多长"。两者不一致，正好是"存的时候被单条上限
  截过"的证据——只记一个数，就分不清"原文就这么长"和"我们只存了一半"。
- **读路径必须同时认两种形态**。老数据的正文还在自己的 `gz` 里（`hash IS NULL`），
  迁移只改新写入的行为。读的时候 `LEFT JOIN blob_texts`，`hash` 为空就用本行 `gz`；
  两条路都走不通时报"正文缺失"而不是返回空串——空串会被误读成"当时就是空入参"。
- **回收只看引用计数**。`blob_texts` 是共享的，`_purge_blobs` 只删"已经没有任何
  `span_blobs` 指着的"那批。跟着第一个引用一起删，就是"点开是空的"——这种损坏不报错，
  等发现时已经查不动了。

统计口径也跟着分成两个数：`blobs`（引用数，前端"附件 N 条"）、`texts`（正文份数）、
`saved`（被去重掉的份数）、`gz_bytes`（实际磁盘）。只报引用会高估占用，只报正文
又看不出"这轮到底产生了多少份证据"。

**收益要如实说**：上生产数据实测，43 条附件引用里只有 1 条重复（约 2%）。
原因是每次 `llm.chat` 记的 messages 都不一样，没有"同一段 prompt 被两层各记一次"
的情况。所以这一项现在的价值是"防"而不是"省"——机制便宜（写入多一次
`INSERT OR IGNORE`、读取多一次 join），但别指望它把附件体积砍一半。
真正的体积来源仍是 gzip 压缩率（1.7×），去重只是顺手把索引做对。

### 12.2 事件属性也走全文通道

`add_event` 原来对属性值只做 `_clip`（截到 800 字丢尾巴）。可排查时最想看的恰恰
是事件里的那一段：工具动作的完整 args、降级原因里的原始报错、首 token 带的思考片段。

现在事件属性和 span 属性走同一套判定（>800 字转存全文，属性里留预览 + 标记），
blob key 约定为 `e{事件下标}.{属性名}`：事件只 append 不重排，下标天然稳定，
前端渲染时手上就有下标，能拼出同一个 key。**不能用事件名**——同一个 span 里
"retry" 会出现好几次，key 会互相覆盖。

顺带保住了一条旧约束：数值属性不转字符串。转了之后 `ttft_ms` 变成 `"321.5"`，
后端就再也排不了序、求不了平均。

### 12.3 树内搜索

搜 span 名、属性键与值、事件名与属性，不区分大小写。三处判断值得记：

- **搜整棵树，不是当前可见行**。折叠是渲染层过滤；只在可见行里搜，折叠起来的分支
  就等于"不存在"，人会以为数据丢了。命中集合从完整树算，再把命中节点的祖先展开。
- **未命中的行压暗但保留**。把行删掉，就看不出"这个慢 span 在第几层、兄弟是谁"——
  树的结构本身是信息。
- **当前命中单独描边**。连着按回车跳过去时，光靠底色分不清停在哪一个。

### 12.4 保留粒度改成"整条 trace"

原来按行保留：14 天后每一行单独判断，error 和慢 span 豁免。问题是**只留那个慢 span，
它在瀑布图上周围全是空的**——"慢在哪一层、谁等的谁"恰恰要靠上下文回答，而上下文
被一起删了。留一行孤证等于没留。

现在：一条 trace 里只要有 error 或 ≥5s 的 span，整条留到 3 倍期（42 天）；
3 倍期后连证据一起放掉（有界才叫保留策略）。容量清理同样跳过受保护的 trace。

实现上先把受保护 trace 钉进临时表再删，不用相关子查询：同一条 DELETE 里边删边查自己，
结果取决于行的处理顺序——先删掉那个慢 span，兄弟行就会被判成"不需要保护"跟着删，
整条链路被连坐清空。

**这就是 tail-based 的答案**：判定的单位是"一条链路跑完之后的结果"，而不是"span 开始
时抽个签"。先全存、后按规则删，代价是磁盘，换来的是长尾一条不少。

### 12.5 "复习"终于有技能了

`skills/*.md` 的 `when` 是自然语言，路由靠 2-gram 覆盖率。中文短句的有效 gram 太少：
"复习"只有 1 个，低于 `MIN_QUERY_GRAMS=4`，覆盖率恒为 0——**最高频的意图从来没被
路由过**，一直是模型自己在通用模式下查了 `list_due_cards`。看起来答对了，但那是
运气，不是保证。

两处改动：

1. 新增 `skills/daily_review.md`：取到期卡 → **只出题不给答案** → 用户答完再逐条点评。
   `risk: read`——打分是用户点的，不能让模型替他决定排期。
2. `registry` 支持 frontmatter 的 `aliases`：命中即 +0.45 并**越过 gram 门槛**。
   这是"用户明说了"的信号，和"覆盖率碰巧高"不是一回事。

同时把 `diagnose_to_cards` 的 when 里"把薄弱点做成**复习**卡"改成"待审卡"——
它一直靠这三个字抢走复习意图。

实测路由（`registry.select`）：

| 问法 | 选中 |
| --- | --- |
| 复习 / 今天该复习什么 / 帮我抽背一下 | `daily_review` |
| 看看我哪里弱，顺手给我出几张卡 | `diagnose_to_cards` |
| 我最近总是挂，哪里弱？ | `weakness_diagnosis` |
| 今天天气怎么样 | 不选（走通用 agent） |

### 12.6 踩到的坑：迁移顺序把应用整死了

把 `CREATE INDEX ... ON span_blobs(hash)` 写进 `schema.sql` 之后，容器起来就崩：

```
init_db() → executescript(schema.sql) → sqlite3.OperationalError: no such column: hash
```

原因很简单，但很值得记：`executescript` 跑在**建表之后、补列之前**。新库的
`span_blobs` 自带 `hash`，老库没有——`CREATE INDEX IF NOT EXISTS` 只在"索引已存在"
时跳过，列不存在照样报错。于是**老库升级直接起不来**，而新库测试一路绿灯。

修法：索引从 `schema.sql` 挪到 `db._ensure_columns`（先 `ALTER TABLE ADD COLUMN`，
再建索引）。并补测试 `test_migration_adds_blob_hash_to_legacy_db`：手搓一个没有 `hash`
的老表，跑一遍 `init_db`，断言不抛、列和索引都在、老行还能读出来。

教训是"It works on my machine"的变种：**新库测一百遍也测不出老库的迁移问题**。
