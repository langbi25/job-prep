## 二、逐期复盘

### P0/P1 可观测：横切关注点走上下文，不走参数

- **5 类 span**（AGENT/LLM/TOOL/RETRIEVER/CHAIN，OpenInference 语义）对齐 Phoenix/Langfuse 的 UI 假设，换后端不用改埋点。
- **惰性装配**：`TRACING_ENDPOINT` 不配 = 零开销。观测必须是"配了才有"而不是"改代码才有"，否则评测和测试会被拖死。
- **场景标签用 contextvars**：观测是横切关注点，不该污染业务函数签名。
- 踩坑：Phoenix OTLP endpoint 必须带 `/v1/traces`；启动 ~20s 内导出 404 是就绪竞态不是 bug。

### P2 评测双写：本地是唯一事实源，平台只是分析层

- **刻意不走 Phoenix client 的 `run_experiment`**：那会让平台重跑业务逻辑，形成"评测第二执行路径"——评测结果必须只有一个出处。
- 坑的密度最高的一段：`upload?sync=true` 返回 200 后立即 GET 可能 404（异步可见性窗口，官方 client 也栽）；404 路由返回 SPA HTML（HTTP 200 + text/html）必须验 content-type；inputs/outputs 不等长 422；experiment 不查重、成功 run 不可变（409 幂等）。
- 方法论：遇到"看起来 id 错位"先怀疑自己读错了 base64，再怀疑系统。

### P3 归因引擎：规则先行，LLM 后置

- **六类根因规则 + unattributed 兜底**：归因引擎 v1 纯规则、零 LLM——先把能确定性判断的判断掉，judge 校准类的模糊失败进兜底台账，保证"每条失败都有归属"这个闭合性。
- **跨层证据是核心价值**：FTS+hybrid 双挂 → 知识缺口要补卡；FTS 挂而 hybrid 好 → 分词问题，不用补卡。同一句"检索没召回"，补卡和改分词是完全不同的药方。
- 产出 `optimizer_input`（补卡清单/prompt 修复清单/校准观察名单），直接成为 P4 的输入——归因和优化之间的接口在 P3 设计时就定好了。

### P4 优化执行器：文件是事实源，表只是台账

- **prompt = 源代码**：改 prompt 就是改逻辑，所以要有版本表、生命周期（candidate/active/rolled_back/rejected/retired）、和回滚。
- **运行时唯一事实源是 prompts/*.yaml 文件**，表只记生命周期与证据。这个决定避免了"表和文件谁是真相"的永恒之争。
- **确定性校验闸在 LLM 之后**：占位符集合不变、花括号转义可渲染、schema 字段说明仍在、长度 0.5x~1.8x——LLM 改写自由，落地上机前有硬门。违规候选落表 rejected，不碰运行文件。
- **晋级判据是 AND**：scoped gate 通过 AND 基线对比无回归。评测中途炸也回滚——文件状态与表状态一致是最硬不变量。
- 踩坑：YAML block scalar `|`（clip）会补尾部换行导致往返不一致 → 按文本是否带尾换行选 `|`/`|-`。

### P5 业务线 spec：配置漂移让测试拦，不靠人肉对六个文件

- 此前"有哪些业务线"散在 6 处：config 元组、两份工具 schema 的 enum、kb_tree 标签、API 默认值、eval 文件路径。加一条业务线要改五六个文件，漏一处就静默漂移。
- **唯一定义点 `specs/business_lines.yaml`，唯一读取入口 `app/core/spec.py`**；新增业务线 = YAML 加条目 + 灌数据，零代码。
- **一致性靠测试而非约定**：test_spec 校验 config 派生、工具 enum、eval 文件存在性、评测数据 direction 反向声明——三方漂移在测试期暴露。
- 顺手修了第三种不一致：agent_tools 默认 backend、API 默认 bigdata，统一为 spec 的 `defaults.direction`。

## 三、闭环现状（端到端一条命令）

```bash
python scripts/run_evals.py --attribute --phoenix   # 评测 → 归因 → 双写
python scripts/run_optimizer.py --evaluate --yes    # 归因 → 候选 → 上机 → 晋级/回滚
```

实测数据（2026-11-11）：57 案例 → 12 条失败，Top1 检索未召回 ×10（其中 5 条真知识缺口
已进补卡清单）；归因/优化器/可观测全链路测试 60 项全绿。

架构一句话：**执行（harness/工具）→ 观测（OTel spans）→ 评测（eval_suite）→ 归因
（规则引擎）→ 优化（prompt 版本 + gate）→ 再评测**，Phoenix 只是分析投影，
spec 是所有业务差异的单点配置。

## 五、可复用的面试考点（P6 素材预演）

- 为什么观测要走 contextvars 而不是函数参数？（横切关注点 vs 业务签名污染）
- 为什么评测双写不走平台的 run_experiment？（第二执行路径 = 结果不可信）
- 为什么归因 v1 用规则不用 LLM？（确定性优先 + 兜底闭合 + 成本）
- 为什么 prompt 优化以文件为事实源？（单一真相，表只做台账）
- 为什么 eval gate 要 AND 基线对比？（gate 只保底线，基线防回归，两者缺一不可）
- spec 化解决什么问题？（配置漂移的人肉成本 → 测试守护）
