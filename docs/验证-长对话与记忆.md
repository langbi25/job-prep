# 验证：长对话与记忆（真实链路，非 mock）

> 2026-11-15。此前 `conversation_summary` 长期为 0——压缩链路只有单元测试，
> 从未在真实对话长度下跑过。本次用 **20 轮真实对话**把这条链路跑通，并修出一个
> 实测才暴露的 bug：摘要越压越长。

## 1. 怎么跑的

`scripts/smoke_long_conversation.py`（容器内执行）：

- 走 `console_service.chat()`——与 API 同一条代码路径，唯一区别是摘要不靠
  `BackgroundTasks`，而是每轮后同步调一次 `summarizer.summarize()`（同函数、同参数）；
- 20 轮内容刻意设计：第 1 轮埋约束（"2C2G，不要 Redis/Kafka 集群"）、
  第 3 轮埋业务 id（`q-a1b2c3d4`）、中途多次回指（"我刚才说的机器配置…"）、
  最后一轮直接考约束复述（"我的机器配置和复习重点分别是什么"）；
- 每轮记录装配账本：`ctx_traces` 的 total/degraded/anchored/summary_id；
- 全部 `mode=assist`（只查不改），避免写库副作用。

成本：20 轮约 2 分钟、¥0.2 以内。

## 2. 结果（修复后）

| 指标 | 数值 |
|---|---|
| 轮数 / 消息数 | 20 / 40 |
| 摘要从第几轮生效 | 第 9 轮起注入（第 8 轮生成首条） |
| 注入过摘要的轮次 | 12 / 20 |
| 摘要条数 | 7（covered 区间连续、无重叠、无重复压） |
| 单条摘要长度 | 370 ~ 595 字（上限 600） |
| **累计压缩比** | **28 条消息 / 3998 字 → 590 字 = 6.8x** |
| 第 20 轮约束复述 | 正确（2C2G、JVM 堆 1~1.2G、方案只用单机轻量组件） |
| 本会话记忆 | 13 条（含 1 条 global 偏好"部署资源约束"，置信度 0.9） |
| 降级 | 全程无（预算占用 8.7% ~ 25.2%） |

第 20 轮回答节选：

> 机器：2C2G，内存是硬约束，JVM 堆最多 1~1.2G……方案优先单机轻量（本地文件/SQLite、内存队列、单机向量库）。
> 复习重点：3 张逾期卡优先（最久 19 天），Kafka 消息不丢失掌握度 0.5 排第一……

——约束、进度、数字都穿过了 7 次摘要重写，结论没漂。

## 3. 实测暴露的 bug：摘要越压越长

修复前 7 条摘要的长度序列：

```
377 → 410 → 480 → 468 → 574 → 756 → 863 字（单批压缩比 1.7 → 0.6）
```

问题有两层：

1. **prompt 里写"总长不超过 300 字"，模型不听**。每轮都是"上一版摘要 + 新对话"
   整体重写，模型倾向于保留细节，输出随时间单调变长；
2. **代码里的兜底 `text[:MAX_SUMMARY_CHARS]` 是从尾部硬切**，而"约束"段排在最后
   ——真到 1200 上限触发时，第一个被切掉的正是最不能丢的东西。

这类 bug 单元测试抓不到：它只在"摘要被反复重写"的真实节奏下出现。

## 4. 修法（双保险）

- **prompt v2**：明确"进度只写结论和产出，不写解题过程"、"总长不超过 300 字
  （约 15 行）"、"字数超了先删进度细节，约束一条都不能省"；
- **代码分段裁剪** `_trim_to_budget()`（`app/context/summarizer.py`）：
  超预算时按 **进度 → 事实 → 约束正文** 的顺序裁，每个 section 至少留 1 条，
  **约束段永不整段丢弃**；无三段格式时才退回硬切。上限从 1200 降到 600。
- 5 条回归测试（`tests/test_summary_trim.py`）钉住：短文本不动、进度先裁、
  约束完整保留、无格式硬切、分段往返。

## 5. 还没覆盖的

- **预算压力没触发**：本轮回复都很短，上下文只用到 8.7%~25.2%，
  `drop_retrieval / drop_memory / shorten_summary / drop_oldest_turn`
  这条降级链一次都没走。要验证得用 8k+ 字的长回答或大段材料。
- **锚定的边界**：`anchored` 只在部分轮次为 1——因为被摘要覆盖的消息会从历史里
  移出，第 1 轮的约束原文在第 9 轮后就不在历史里了，之后全靠摘要的"约束"段承载。
  这是设计如此（摘要必须可靠），也说明第 4 节的修复不是可选项。
- **跨会话**：本会话的偏好落的是 global 域，但"新会话是否主动想起"没在本次验证里
  单独跑（`recall` 的全局通道有单测覆盖）。
