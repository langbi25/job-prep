## 3. 平台设计与落地（微服务 / 调度 / 并发 / 容错 / 性能）

### 能讲的

**服务拆分是有边界理由的，不是为了拆而拆**（`docker-compose.yml`）
- `api`（纯请求面，`JOBS_ENABLED=0`）、`worker`（定时任务调度，`python -m app.worker`）、
  `mcp`（对外协议侧车，`profiles: ["mcp"]` 默认不启动）、
  `litellm`（LLM 统一出口）、`backup`（每日备份 sidecar）、`web`（nginx 静态 + 反代）——
  六个服务每个都有"为什么独立"的理由：故障面隔离（backup）、资源画像独立（worker）、
  协议边界（litellm/mcp）、交付形态（web）
- 依赖用 `depends_on: condition: service_healthy`，不是 sleep 猜时间；多个服务各有
  healthcheck；`restart: unless-stopped` vs `on-failure:3` 按故障性质区分
  （token 缺失这类错重启一百次也一样）
- 日志轮转（`max-size/max-file`）、观测栈走独立 `obs` 网络、对外端口只绑 `127.0.0.1`
- **跨进程协作有实弹机制**：调度互斥靠共享卷上的文件锁（跨容器成立，手动触发撞定时
  执行记 `skipped_locked` 不双跑）；SQLite 写竞争靠连接层 `busy_timeout` 排队
  （api/worker/backup 三进程并发写，日志零 locked 错误）

**并发控制做了三层，每层解决不同问题**
1. LLM 并发池：`BoundedSemaphore` + `acquire(timeout=30)`（`llm.py`）。无限等会把
   "上游过载"变成"请求堆积"，所以有超时就抛 `LLMConcurrencyError`；**可重入**是硬要求
   ——对话线程内触发编排、worker 再要额度，不可重入会自己锁死自己
2. 工具批次：批内按 `(tool,args)` 去重放在并发**之前**（两个线程同时查 cache 会都判未命中），
   线程池上限 3，`as_completed(timeout=90)`，单个工具超时只标该工具 `timeout` 不拖整批
3. 编排：依赖 DAG 按批次派发，同批并行 ≤3，批次之间串行（有真实依赖才串）

**容错按"该不该重试"分层，不是一律重试**
- `retryable` 白名单：408/409/429/5xx 才重试，400 透传（上下文超限重试必败）
- 重试只一次且**收窄上下文**（上游结论砍半 + 工具往返减 1），第二次还失败就认
- 超时/预算不足 → 终态 `timeout`/`capped` 单列，**不混进失败率**（两种处置相反：
  一个调预算，一个修 bug）
- 预算账本读不到按 0 处理："账本读不到不该把用户锁在门外"

**性能优化都对应过真实瓶颈**
- SQLite 放 named volume 而不是 `./data`：WSL2 的 `/mnt/e` 走 9p，WAL 会随机
  `database is locked` 且写吞吐掉一个数量级——这条是踩出来的，不是查出来的
- `workers 1` 是显式决策：SQLite 单写者，多 worker 只会互相抢写锁
- FTS5 外部内容表 + 启动时全量 rebuild（漂移时 MATCH 会静默漏召回，比报错难查）
- 工具结果缓存 + 批内去重；span 分级保留（普通 14 天，错误/慢调用 3 倍）+ 行数保险丝

### 不能吹的

- **任务调度是单机语义（但已做到进程级分离）**。通用 job runner（`app/core/jobs.py`，
  2026-11-16）：表驱动（jobs/job_runs 落库）、文件锁互斥、重试/超时、执行历史。
  阶段 A（2026-11-17）把调度循环搬进独立 worker 容器：api 变纯请求面，跨容器互斥
  靠共享卷文件锁、写竞争靠 busy_timeout 排队——"一个进程一种职责"成立，
  但没有 Celery/队列/分布式锁，多机部署时这套机制不成立，如实说是"单机调度器"。
- **没有分布式**：无队列、无分布式锁、无选主、无水平扩展（`workers=1` 是硬约束）、
  无灰度/滚动升级、无服务发现与配置中心。
- **没有跨服务超时预算传播**：deadline 只在编排内部传递，HTTP 入口到下游没有统一
  deadline 上下文。
- **容量有数据了（P2 压测）**：`scripts/load_test.py` 实测本机 /api/stats——
  并发 1：224 rps / P95 6ms；并发 4：291 rps / P95 23ms；**并发 8：吞吐反降到
  200 rps、P95 122ms / P99 218ms**——拐点在 4~8 并发，SQLite 单写者竞争。
  **瓶颈定位有实验证据（阶段 B）**：`docker update --cpus=1` 限额后三档吞吐
  几乎不变（291→294 rps@并发4）——瓶颈不在 CPU 在存储层，扩容方向是换库/
  读写分离而不是加核。
  **容量有趋势且有判定线（阶段 C，2026-11-17）**：`capacity_sample` 每 5 分钟
  采一次（写锁探测 `BEGIN IMMEDIATE` 计时 + 库/WAL 体积 + 热表写入量代理 +
  loadavg），面板直接给出"换 Postgres / 扩副本 / 加 CPU / 上 K8s"四项的
  当前读数与判定。当前实测：库 10.3 MB（上限 2048 MB）、写锁 P95 0 ms、
  被锁挡住 0%、load/cpu 0.05 → 四项全部未触发。**这就是"暂时不换"的依据**，
  阈值与判定逻辑在 `capacity_service.evaluate()`，28 条测试钉住。

### 面试口径

> 我做过的是**服务边界划分 + 闸门设计**：把 LLM 出口独立成网关、把对外协议做成
> 可选侧车、把备份拆成不影响在线的 sidecar；并发与预算是三层闸门，都放在"调用之前"
> 而不是事后统计。**分布式那块我没有生产经验**——单机 SQLite 是有意选择，不是能力上限，
> 换成 Postgres + 队列怎么做我能讲清，但没做过。

## 4. 网络 / 代理 / 外部接口（限流 / 超时 / 重试 / 隔离 / 三方稳定性）

### 能讲的

**代理网关是这轮最完整的"外部接口治理"案例**（`litellm/config.yaml` + compose）
- 统一出口：应用层说的本来就是 OpenAI 协议，指到网关零改动切换；换供应商/加 fallback
  只改 config，不动业务代码
- **职责边界写得很清楚**：记账/预算/并发池**不外移**（网关的 spend tracking 要背
  Postgres），网关重试只兜网络抖动/429/5xx，**400 透传**——不然应用侧"该不该重试"
  的语义被网关吃掉
- 密钥只在网关一处（`LITELLM_MASTER_KEY`），端口只绑回环，healthcheck 用免鉴权
  的 `/health/liveliness`

**超时是全覆盖的，不是只给主链路**
- LLM 90s（含流式）、工具 90s、并发池等待 30s、ingest 抓取 10s、healthcheck 5s、
  MCP socket 2s

**网络隔离有四层**
- compose 内部网络；观测栈独立 `obs` 网络（容器间服务名，不走宿主端口）
- 所有对外端口绑 `127.0.0.1`；MCP 默认不启动，且非本地监听强制要求 `MCP_TOKEN`
- CORS 从 `*` 收到白名单；API 层 `GuardMiddleware` 只拦 `/api/*`（`/health` 放行给
  healthcheck），SSE 用手写 ASGI 中间件避免 `BaseHTTPMiddleware` 破坏流式

**第三方稳定性都有降级路径，不是"挂了就报错"**
- Langfuse 导出失败：吞掉只打日志（观测不能影响业务）
- Phoenix 不可用：接口返回 `available: False` + 原因，面板显示降级提示而不是 500
- 向量模型缺失/下载失败：回退 FTS，检索仍可用
- rerank 失败：回落到未重排结果

**限流：令牌桶两层，只拦 /api**（`app/core/ratelimit.py`，2026-11-16 补）
- 全局桶保护整机（SQLite 单写者 + 4 路 LLM 池），按 IP 桶防单客户端独占；
- 只拦 `/api/*`：静态资源与 `/health` 放行（否则刷新页面/容器探活会被打成 429）；
- 被拒 429 + `Retry-After`（按令牌缺额算）；空桶惰性回收防内存炸弹；
- 两个真实边界有测试钉住：浮点容差（0.1×10=0.9999…）与时钟回拨（VM 挂起恢复）。

**熔断：三态机**（`app/core/circuit.py`，2026-11-16 补）
- 接在 `llm._chat_json` 并发池**之前**：打开期间立刻失败，不占池不耗 90s 超时；
- 只统计上游健康类失败：5xx/超时/连接错误。**429 与 400 不计入**（前者是限速、
  后者是我们请求不合法，误伤形态都写进测试）；
- 半开只放一个探针，探针失败退避加倍（30→60→…→300s），成功一次归零；
- 按 `上游|模型` 分键，换模型不互相牵连。

**SSRF 白名单**（`app/core/netguard.py`，2026-11-16 补）
- 协议/端口白名单 + **解析后**逐 IP 校验（私网/回环/链路本地/CGNAT/保留段全拒）；
- **逐跳校验重定向**（挡"公网 302 → 169.254.169.254"）；
- 限跳数、限响应体（2MB）；DNS rebinding 的残余风险如实写进模块注释。

### 不能吹的（已收窄）

- **没有跨实例共享状态**：限流桶与熔断状态都是进程内内存。单机够用，
  多实例时会各算各的（换 Redis 的接口和成本我能讲清，但没做过）。
- 没有连接池参数调优记录、没有 DNS/TLS 层的专项处理。
- 熔断只接在 LLM 调用上，没有覆盖到所有外部依赖（如 embedding 服务单独路径）。

### 面试口径

> 代理这块我能讲透：网关该承担什么、不该承担什么，重试语义怎么在网关和应用之间
> 分层不打架；限流和熔断我按"闸门放在哪一层、什么算失败"的思路落地过——
> 429 和 400 为什么不能计入熔断，这类边界都有测试和事故对照。

## 5. 质量 / 自动化测试 / 可观测 / 故障诊断 / 数据准确性

### 能讲的（最强的一条）

**测试盯的是"口径"而不是"覆盖率"**
- 46 个测试文件、**395 条**，全绿。典型的是口径类：指标四条口径（失败行入分母、
  失败行耗时不进分位、最近秩分位、软停单列）、上下文降级链 6 条、编排边界 10 条
- 双 CI 流水线（`.github/workflows/`）：`ci.yml` 全量测试 + 前端构建 + 树搜索，零 LLM
  成本每次 push 必跑；`evals.yml` 快检 + 全量评测**门禁**，13 项阈值
  （`evals/thresholds.json`），band_accuracy 还要看相对多数类基线的 lift——
  只报准确率的话"永远猜多数类"也能过
- 评测失败自动进料（`eval_intake`）：线上踩的坑变成下一轮评测用例

**可观测是"三层三视角"，不是只接了 APM**
- 调用树：OTel span 落本地表 + Phoenix/Langfuse 双写，`trace_id` 串起
  `llm_usage` / `tool_calls` / `turn_facts`
- 业务账：三张台账（LLM 用量含失败行 / 工具调用含 error_kind / 编排含逐步快照）
  + `turn_facts` 单行快照——"写入只有一处，读取只认这里"，避免每个面板各写一套口径
- 趋势：`GET /api/obs/metrics` 聚合三源（不依赖外部观测后端是否在线），8 条告警
  （错误率/慢调用/成本/工具失败/编排失败/库体积/写锁排队/库增速）带冷却窗与样本保护，
  webhook 送达失败率本身单独可查；判定在 worker 的 `alerts_check` job 里跑，
  检查本身有执行历史（不是"线程挂了没人知道"）；未配 webhook 时也落库并标未送达

**故障诊断有"可行动"的字段，不是只有堆栈**
- HTTP 错误体透传（`_fail` 截 800 字符）：线上 60% 编排失败率曾经只看到
  "400 Bad Request"，什么都定不了位
- `error_kind` 六分类：`invalid_args`（改 schema）/ `unknown_tool`（改注册表）/
  `timeout`（调超时）/ `bad_json`（改 prompt）/ `failed`（修实现）/ `policy_denied`
  （闸门在工作，不算失败）
- span 上带 `finish_reason`（为什么短）、TTFT（为什么卡）、`stream_fallback`（流式
  为什么退非流式）、`ctx_traces`（上下文怎么装配的）

**数据准确性有机制，不是靠小心**
- 单一写入点：所有 LLM 调用过 `llm._chat_json` 一个咽喉，台账漏不掉
- 幂等迁移：`_ensure_columns` 启动补列；`INSERT OR IGNORE` 去重；`foreign_keys=ON`
- 口径修正有记录：`policy_denied` 曾把 6 次被拒算成 100% 工具失败，修分类并**幂等
  回填历史行**——不然指标要带着假失败再跑 14 天
- 每日备份 sidecar + 保留 7 份 + 备份日志
- **恢复演练**（`scripts/restore_drill.py`，2026-11-16 补）：取最新备份 → 解压 →
  `integrity_check` → 关键表行数对账（对照在线库查"空壳"）→ 抽样读真实内容 →
  新鲜度检查（>48h 说明备份循环停了）。四类失败各有测试：损坏 gzip、空壳备份、
  过期备份、文件缺失。真实数据跑过：9.5MB / 37 卡 / 530 条 LLM 台账，PASS。

### 不能吹的

- **压测已有（P2）**：`scripts/load_test.py` 阶梯加压，429 单列、限流主导阶段
  只判错误率、最近秩分位数；实测拐点见第 3 条。仍缺：长期容量监控、
  端到端自动化（smoke 脚本不在 CI）
- **混沌是"单机实弹"不是平台**：`scripts/chaos_drill.py` 三场景（进程崩溃 RTO、
  网关死亡验熔断三态、CPU 限额压测）实测过且挖出 4 个真 bug/坑；但没有故障
  注入平台、没有演练编排与定时执行——是"手工 drills"不是 chaos engineering 体系
- **端到端没有自动化**：20 多个 smoke 脚本是手工跑的，不在 CI 里
- 备份已是三层快照（micro 5min/hourly/daily，RPO ≤5min）+ `restore_pitr.py` 按时间点
  恢复（实弹双向验证）；秒级真 PITR 需要 Litestream（决策 D7），高可用没有

### 面试口径

> 质量这块我能给具体机制和事故：指标上线第一天抓到两个假数据问题（策略拒绝被算成
> 失败、unknown 场景占 21% 费用），都是靠"口径写在文档里、测试钉住"暴露的。
> **混沌做过实弹**：容器化之后跑了三个演练（进程崩溃量 RTO、停网关验熔断三态、
> CPU 限额压测），挖出 4 个真 bug/坑（详见 docs/容器运行.md 第 12 节）——
> 我对混沌的理解是"演练必须挖出东西才算数"，不是跑个脚本看个绿。
> **没做过的**：长期容量监控、演练编排/定时化——我知道怎么做，缺的是动手时间。
