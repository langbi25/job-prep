# 验证：上下文预算打满后，降级链实际怎么走

> 2026-11-15 · 对应脚本 `scripts/stress_context_budget.py` · 会话 `cs-20261115-212004-9078`

## 0. 为什么还要跑第二轮

第一轮 20 轮真实会话只把预算用到 **8.7%~25.2%**，`drop_retrieval / drop_memory /
shorten_summary / drop_oldest_turn` 这条降级链**一次都没走过**——等于只有单元测试
证明它"代码上存在"。

这一轮反过来：少轮次 + 每轮要求 3000 字长回答 + 两段真实材料（岗位描述、面经），
把 12k 预算顶到 100% 附近，看它到底先丢什么、后丢什么、丢完还对不对。

## 1. 四段实验

| 段 | 做什么 | 花 LLM 吗 |
|---|---|---|
| A | 11 轮真实对话，每轮要求 ≥3000 字，第 7 轮粘 JD、第 8 轮粘面经 | 是 |
| B | 拿 A 的真实历史做预算阶梯扫描：cap 从 12000 降到 2000 共 11 档 | 否 |
| C | 单轮粘 14291 字材料 | 是（外加一次缩小预算的装配探针） |
| D | 合成 8 条 ×4800 字工具结果，验证轮内裁剪 | 否 |

B 段不能省：真实链路只告诉你"这轮降到了第几级"，告诉不了"预算降到多少才会触发
shorten_summary"。临界点必须扫出来。

## 2. A 段：真实链路逐轮

| 轮 | 回复字数 | 上下文 token | 占用 | 降级 |
|---|---|---|---|---|
| 1 | 3281 | 1191 | 9.9% | — |
| 2 | 6232 | 2824 | 23.5% | — |
| 3 | 3577 | 5674 | 47.3% | — |
| 4 | 4800 | 7422 | 61.9% | — |
| 5 | 4482 | 9837 | 82.0% | — |

| 7 | 857 | 11029 | 91.9% | drop_retrieval, drop_memory, **drop_oldest_turn** |
| 8 | 833 | 11852 | 98.8% | drop_retrieval, drop_memory, drop_oldest_turn |

三点观察：

1. **五级全走到了**，顺序与设计一致：检索 → 记忆 → 摘要（先缩后丢）→ 最旧轮次。
2. **没有一轮超过 12000**。第 9 轮的回落是摘要生效（覆盖更早消息），不是降级。
3. 第 7、8 轮是"粘了大量材料"的轮次：单轮 user 就有 314/321 token，触发了
   `drop_oldest_turn`——这是唯一会真正丢掉用户历史的一级。

**约束有没有被丢没**：第 1 轮的"2C2G / 不要 Redis 集群"在第 7 轮被
`drop_oldest_turn` 挤出去了。但最后一轮（第 11 轮）仍然准确答出
"2C2G、堆 1~1.2G、assist 模式只查不改"，原因是第 6 轮的回复里复述过这条约束，
并且摘要的"事实"段一直带着"用户机器为 2C2G"。**这里的存活是侥幸不是保证**——
如果中间几轮没有复述，丢轮次就等于丢规则。这是已知风险，见第 5 节。

**总额是单调的**：预算调小，留下的 token 只能更少，不会更多——这是本轮修出来的
性质（见 4.2）。

阶梯给出的临界点（对这份历史）：
- **9000 左右**开始丢检索与记忆（它们合计约 600 token，属于"锦上添花"，先动它们最便宜）；
- **9000 以下**开始缩/丢摘要，并动用 `drop_oldest_turn`；
- **3500 以下**只剩 2 轮（4 条消息），此时再小也无轮可丢（循环条件是 `len(kept) > 2`）。

## 4. 这一轮修掉的三个问题

三个都是"单元测试抓不到、只有打满才暴露"的。

### 4.1 P0 约束把助手回复也算进去了

`window.key_hits` 原先对 user 和 assistant 一视同仁。技术讲解里"必须""只能"
满篇都是（"必须先开 checkpoint""只能做到 at-least-once"），于是：

```
12 轮里 11 轮被判成约束轮 → _drop_oldest_soft 扫完全部跳过
→ drop_oldest_turn 从没触发 → 预算 106% 了还只报 keep_constraint
```

修法：**P0 只认用户自己说的话**，assistant 只参与 P1（业务 id / 评分结论，
那是"提到过什么"而不是"要求什么"）。修完 12 轮里只有第 1 轮是约束轮。

### 4.2 摘要降级不单调

旧判据是"缩短后比原来短就留、没短就整段丢"。结果：

```
cap=3500 → drop_summary（整段丢，total 3900）
cap=2000 → shorten_summary（留下 237 token，total 4137）
```

预算更紧，反而留下了更多东西。根因是判据看的是"能否变短"，而不是"还装不装得下"。

修法：按**当前超出量**裁（`want = 现有 - over - 40`），缩完仍超就整段丢。现在是
"缩 → 丢 → 丢轮次"的单向阶梯。

### 4.3 丢轮次时保护没有上界

`window.select` 有"最近 4 条约束轮受保护"的上界，`_drop_oldest_soft` 没有。
而"不要说教，直接讲"这种句式每轮都会出现——只要用户习惯这么说话，一轮都丢不掉。

修法：两处用同一套规则，只有最近 `MAX_P0`（4）条约束轮受保护，更早的按普通轮处理。
对照组（每轮都带"不要"）实测：

| cap | total | 保留轮数 | 降级 |
|---|---|---|---|
| 12000 | 8175 | 8 | — |
| 9000 | 8175 | 8 | — |
| 7000 | 6644 | 7 | drop_retrieval, drop_memory, drop_oldest_turn |
| 5000 | 4754 | 5 | ×3 |
| 3500 | 3809 | **4** | ×4 + keep_constraint（CTX_KEEP_CONSTRAINT） |

最后停在 4 轮 108.8%——这是**有意为之**：保护上界内宁可不守预算，也不丢用户
刚说过的规则，而且如实记账（`fallback=CTX_KEEP_CONSTRAINT`），不假装守住了。

## 5. 结论：预算其实有两道闸

```
第一道：window.select      history 分区 6600 token，按"最近 6 轮 + 锚定"挑
第二道：降级链             仅当"最近 6 轮 + 锚定轮"本身超预算时才启动
```

A 段第 10 轮 `dropped=2` 就是第一道闸在起作用——窗口自己丢了两条消息，
总预算根本没超。所以真实场景里**降级链是第二道防线**，大多数压力由滑窗吸收。

这解释了为什么第一轮 20 轮对话一次都没降级：不是降级链没用，是没轮到它。

## 6. 还没覆盖的

1. **单轮材料的上限**：`MAX_MESSAGE_CHARS=20000` 卡住了"一条消息压垮预算"的极端场景。
   C 段用 14291 字只能到 74%，要触发 `CTX_USER_OVERSIZE` 必须在已有历史的会话里
   粘大材料，或者缩小预算（本次用 `assemble@6000` 探针验证：`fallback=CTX_USER_OVERSIZE`，
   `content_intact=true`——一个字没裁）。
2. **约束在丢轮次后的存活是概率性的**：本次靠"第 6 轮复述过"侥幸活下来。
   要真保证，得让 `_drop_oldest_soft` 在丢轮前把该轮的约束写进摘要——目前没做。
3. **轮内裁剪只测了合成数据**：真实 ReAct 里 8 步工具结果堆积的情况没触发过
   （现有工具返回都不大）。D 段结果：29233 → 6756 token，7 条裁到 612 字，最后一条
   保留 5200 字（"保护最后一条"是有意的）。
